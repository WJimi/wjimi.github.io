## 先回答“清缓存后重建会执行什么”

日常使用你根本不会触发“构建”。这里有两个完全不同的动作，先分清：

| 动作 | 命令 | 做什么 | 耗时 |
|---|---|---|---|
| 构建 build | `docker compose build` / `up --build` | 按 Dockerfile 把源码变成镜像 | 几分钟到几十分钟 |
| 启动 up | `docker compose up -d` | 用现成镜像开容器 | 几秒 |

你现在镜像已经有了，日常 `up -d` 走的是“启动”，跟构建缓存没关系。缓存只在“构建”时有用：Docker 会检查每一步的输入变没变，没变就直接复用上次的结果。

如果清空缓存再构建，它会从零重做整套：

1. 重新拉 `node:22`、`golang:1.26.3`、`python:3.12-slim` 这几个基础镜像
2. 重新 `npm ci` 下载前端依赖，重新 `next build`
3. 重新 `go mod download`，重新编译 Go 后端
4. 重新 `apt` 装工具、`npm` 装 Playwright、下载 Chromium

也就是把你刚经历的“慢”再体验一遍。

所以你的判断是对的：不改源码、不升级版本，清掉缓存完全合理，日常没有影响。唯一代价是将来某天你要升级 ARTEX 版本重建时，会慢一次。想清就清，不用留。

## Docker 不是虚拟机，那它是什么

一句话：**容器就是宿主机上被“关起来”的普通进程。**

- **虚拟机**：虚拟出一整套硬件，里面装一个完整操作系统，隔离强。
- **容器**：直接用宿主机的内核，只是给进程套了几层“隔离罩”：
  - 独立的文件系统（看起来像一台新机器）
  - 独立的网络（自己的 IP、端口）
  - 独立的进程列表（看不到宿主机的进程）
  - 资源限制（限制 CPU、内存）

所以它启动是秒级的，因为它根本没“开机”，只是启动了一个进程。

它能不能和物理机互通？能，但只通过你开的“门”，也碰不到你的进程。常见的门就三种：

1. **端口映射**：`-p 8787:8787` —— 把宿主机的 8787 接到容器的 8787，你在浏览器访问 `localhost:8787` 就是在访问容器里的服务。
2. **目录挂载**：`-v ./data:/app/data` —— 把宿主机和容器里的目录绑在一起，两边是同一份文件。你刚加的 `jwt.key` 就是这个。
3. **环境变量**：`-e KEY=value` —— 把配置传进去，比如数据库连接串、API Key。

除此之外，容器还能主动访问外网，同一网络里的容器也能互相访问（比如 artex 用 `postgres:5432` 连数据库，靠的是服务名解析）。

一句话总结：**隔离的是“能看到什么”，不是“能不能通信”；通信必须经过你显式开的门。**

## 用户怎么操作容器里的东西

有两个入口：

### 入口一：进容器开个 shell（像 SSH，但不用装 SSH）

```bash
cd ~/ARTEX-0.3.15
docker compose exec artex bash
```

进去之后就是那台“迷你 Linux”：可以 `ls /app`、`pwd`，跟你在一台机器上操作一样。`exit` 退出。注意：退出不会影响服务，服务还在跑。

### 入口二：走它的网络服务

ARTEX 有 Web UI，你日常就是用浏览器访问它。

## 几个实用案例（都基于你这个项目）

### 1. 日常启停

```bash
docker compose up -d        # 启动（有镜像，不重建）
docker compose stop         # 停止（容器还在）
docker compose start        # 再启动
docker compose restart artex
docker compose ps           # 看状态
```

### 2. 看日志（排错第一招）

```bash
docker compose logs -f artex        # 实时跟，Ctrl-C 退出
docker compose logs --tail=100 artex
```

### 3. 临时执行一条命令，不进去

```bash
docker compose exec artex curl -s localhost:8
docker compose exec artex ls /app/data
```

### 4. 宿主机和容器之间拷文件

```bash
docker compose cp artex:/app/data/traffic ./traffic-backup
docker compose cp ./some-file.txt artex:/app/data/
```

### 5. 备份数据库

```bash
docker compose exec -T postgres pg_dump -U artex artex > backup.sql
```

### 6. 看谁占资源

```bash
docker stats            # 实时 CPU/内存
docker system df        # 镜像/容器/缓存各占多少
```

### 7. 停止并删除容器（数据还在）

```bash
docker compose down
```

它删容器和网络，但 `pgdata` 具名卷和 `./data` 目录还在，下次 `up -d` 数据原样回来。只有 `docker compose down -v` 才会连数据卷一起删——这个别随手敲。

### 8. 改了 `.env` 后生效

改完直接 `docker compose up -d`，compose 会自动重建受影响的容器（不用 `--build`，因为镜像没变）。
