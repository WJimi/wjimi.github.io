# 乱码是怎么来的

## 来源

给 [[knowledge-base/03_projects/web/ivn-duty-challenge|IVN 值班日志]] 出题时，
把一份泄露的 `.bak` 源码交给浏览器显示，中文注释全变成乱码；用 curl 拉下来却是好好的。

## 它解决的问题

文件明明没坏，为什么浏览器里显示成乱码？

## 当前理解

一个文本文件就是**一串字节**。这串字节本身不带「我是 UTF-8」这个信息，
字符集是**解码规则**：同一串字节用两套规则去解，出来就是两种字符。

> 乱码 = 编码和解码用了两套规则。

那浏览器怎么决定用哪套规则？按优先级：

1. HTTP 响应头的 `charset`
2. 文件内部的声明（HTML 的 `<meta charset>`、CSS 的 `@charset`）
3. 都没有 → 按系统 / 浏览器的默认编码猜（中文 Windows 上通常是 GBK）

还有一个点能解释「为什么只有中文乱、URL 和标签却好好的」：
ASCII 字符在 GBK 和 UTF-8 里编码完全一致，纯 ASCII 内容怎么解都对，
只有中文部分会因为规则不同而崩掉。

### 排查三步

1. F12 → Network → 看这条响应的 `Content-Type` 有没有带 `charset`
2. 查文件本身的实际编码：`file -i 文件名`
3. 两边对不上，就是它

## 相关问题

- HTTP 响应头的 charset 和 HTML 里的 meta charset 冲突时，浏览器听谁的？

## 实践

nginx 上我加了 `default_type text/plain;`，让 `.bak` 直接显示而不是下载成文件，
但**没带 charset**，于是浏览器按 GBK 去猜 UTF-8 的内容，中文全乱。
补一行 `charset utf-8;` 之后，响应头变成 `Content-Type: text/plain; charset=utf-8`，问题消失。

一个顺带的好处：`charset utf-8;` 也会给没写 charset 的 PHP 页面补上。
首页原来是靠 `<meta charset="utf-8">` 兜底的，现在响应头里也是明确的了。

教训：改 Content-Type 的时候要把 charset 一起想一遍，这两件事太容易被拆开忘掉。

另外，这个坑是"用浏览器打开看一眼"才发现的——curl 拿到的字节全对，
自动化测试永远测不出来。
