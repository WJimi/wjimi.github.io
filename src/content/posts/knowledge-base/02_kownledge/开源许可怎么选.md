# 开源许可怎么选

## 来源

准备把 [[knowledge-base/03_projects/automation/tradeup-material-sourcing|CS2 炼金配方的自动取材]] 开源时，
卡在"选 MIT 还是 Apache-2.0"上——因为根本不知道这两个词在决定什么。

## 它解决的问题

我把代码放到公开仓库，别人到底能拿它做什么？

## 当前理解

### 最反直觉的一条：不放 LICENSE = 别人**法律上不能用**

著作权是**代码写出来就自动产生**的，不需要申请。
默认状态叫「保留所有权利」（all rights reserved）——**别人可以读，但没有权利复制、修改、分发**。

所以"我放在 GitHub 上" ≠ "我开源了"。**开源 = 我主动给出授权**，
而 LICENSE 文件就是那份授权的正文。

```text
没有 LICENSE   →  公开可见，但别人用了是侵权
有 LICENSE     →  我在里面写清"允许做什么、要求什么"
```

### 常见几种在"放弃什么"上不同

不谈法条，只说**我交出了什么、换回了什么**：

| 许可 | 允许别人 | 要求他们 | 我保住了什么 |
| --- | --- | --- | --- |
| **MIT** | 做任何事，包括闭源商用 | 保留我的版权声明 | 署名（名声） |
| **Apache-2.0** | 同上，几乎一样宽松 | 保留声明 + **标注修改过** + 明确的**专利授权** | 署名 + 不被专利反咬 |
| **GPL 系列** | 可以用、可以改，但**改完的作品也必须开源** | 传染：用了它就得跟着开源 | 代码永远保持开放 |
| **不放许可** | 什么都不允许 | —— | 全部权利 |

两个关键区别：

- **MIT vs Apache-2.0**：宽松程度几乎一样。Apache 多的是"专利条款"
  （贡献者不能事后拿专利起诉使用者）和"修改需标注"。**公司法务偏好 Apache**，
  个人项目 MIT 更常见——因为它最短、最好懂。
- **GPL 的"传染"**：如果用了 GPL 的代码，我的项目也可能必须 GPL。
  想闭源商用的人会因此绕开我的项目。**选 GPL 是一种立场，不是疏忽。**

### 许可证不改变的事

- **不保证质量**：所有常见开源许可都带"按现状提供，不担保"。
- **不免责**：代码被用来做坏事，责任不会因为开源就消失——这正是要写免责声明的原因。
- **不发工资**：开源不是商业模式。它的回报是署名、影响力和协作。

### 文化：开源不是"把代码扔出去"

更接近**一份协作的默认协议**：别人能读、能提 issue、能提 PR。几条不成文但很硬的规矩：

- **署名是硬通货。**对个人项目，名字被人记住比钱重要；对别人，保留版权声明是底线。
- **"我的代码被用了"不是损失。**被 fork、被抄进别的项目，是影响力在扩散。
- **提 PR 之前先问。**大改动先开 issue 说清动机，比直接甩一个巨大的 diff 礼貌得多。
- **不要提交别人的东西当自己的。**哪怕是 AI 写的，也要说清来源。

## 相关问题

要不要给这个项目选许可，是个**判断**，不是知识——取决于"我希望别人拿它做什么、
我最怕什么"。而这个项目有几条**特有的顾虑**（和普通工具库不一样）：

1. 它带着**凭证文件**（`token.txt`、`.browser-profile`）。开源前必须确认这些没进仓库。
2. 它**绕过了平台的限制**（绕过 cs2up 的订阅墙取数、自动化操作 BUFF 界面）。
   开源等于把"怎么绕"写给所有人看——可能违反站点条款，也可能伤到这个玩法本身
   （公开信号会自我消解）。
3. 它涉及**钱**。别人照着跑亏了钱，法律上有免责声明兜着，但观感上是我的事。

所以顺序应该是：**先决定开不开源，再决定选哪个许可。**
如果开，MIT 或 Apache-2.0 都行，但 README 里要有一节写清用途边界和免责声明。
