# 一切皆文件：目录为什么也是文件，硬链为什么链不了目录

## 来源

为了让桌面端和 WSL 共用一套技能，需要把 WSL 的 `~/.codex/skills` 变成指向 Windows 侧目录的软链。过程中冒出两个问题：软链能不能链目录？为什么有人说"Linux 一切皆文件"、目录也算文件？

## 它解决的问题

- 复制一份目录就有两份数据，之后必然要人维护一致性；软链让"一个目录、两个入口"成立。
- "一切皆文件"常被当口号背下来，但它真正的含义是**接口统一**，不是"所有东西本质相同"。分不清就会以为目录能像普通文件那样读，或者以为目录可以建硬链。

## 当前理解

### 目录也是文件

`ls -l` 第一列的字符就是类型：`-` 普通文件、`d` 目录、`l` 软链、`c` 字符设备、`b` 块设备、`p` 命名管道、`s` socket。它们都是文件系统里的对象，都有 inode（编号、权限、属主、时间戳），都能在目录树里挂名字。目录这个"文件"的内容是**一张 名字 → inode 编号 的表**；`ls` 读的是目录的内容，`cat` 读的是文件的内容，同一个动作作用于不同对象。

### "一切皆文件"指的是接口统一

内核给这些对象提供同一套系统调用：`open` / `read` / `write` / `close` / `seek` / `ioctl`。所以 `echo hi > /dev/tty` 能写终端、`/dev/null` 是个文件、读 `/proc/cpuinfo` 就是 read 一个文件、管道和 socket 都用文件描述符表示。

它解决的是**减少特例**：如果每加一种资源就发明一套 API，shell 的重定向、管道和 `cat`/`grep`/`dd` 这些工具就得为每种资源重写一遍。取舍是"只要能 open/read/write 就当文件处理"，换来一套通用工具。

边界（口号不是定理）：

- 目录不能像普通文件那样 `read`，内核返回 EISDIR（"Is a directory"），遍历要走 `getdents`/`readdir`。原因是目录项的格式与具体文件系统强相关，内核不愿把它固化成标准字节流。
- 进程、网络接口、cgroup 本身不是文件；`/proc` 是把内核数据结构伪装成文件的样子，所以有些能写、有些只读、行为也不完全一致。
- 设备文件是"操作的门"，不是"数据的容器"。

### 硬链禁止目录，软链可以

硬链的本质是"同一个 inode 挂两个名字"。允许给目录挂两个名字就能造出环（`a/x` 指回 `a`），于是 `..` 变得无解、引用计数失效、`fsck` 崩掉，所以内核直接禁止（`hard link not allowed for directory`）。软链只是一串路径，环由解析跳转次数上限兜住（超了报 ELOOP），因此不受限制。结论：**链文件夹只能用软链**。

### 操作要点

- `ln -s 目标 链接名`，参数顺序是目标在前。
- 链接名位置若已经是真目录，`ln -s` 会在**它里面**建链接（变成 `skills/skills`）—— 所以要先 `mv` 腾空，或用 `-T`。
- `ls -ld` 看链接本身，`ls -l <链接>/` 看目标里的内容，`readlink` 打印目标路径。
- `rm` 链接只删那串路径记录，不动目标；目标被移走或删掉，链接就悬空，访问报 No such file。
- 备份与同步工具对软链的处理不一致：有的跟进去复制成实体，有的直接跳过。

## 实践

- 把 WSL 的 `~/.codex/skills` 换成指向 `C:\Users\wjimi\.codex\skills` 的软链（原目录先 `mv` 成 `skills.bak-<日期>`）。源放在 Windows 侧，因为 Linux 建软链不需要特权，而 Windows 建符号链接要开发者模式或管理员权限。
- 验证"一更新即同步"的办法：在 Windows 路径下 `touch` 一个探针文件，再从 WSL 路径 `ls` 出来；反方向再写一个文件、从 Windows 路径读回去。两个方向都通，说明是同一份数据，而不是两份恰好长得一样。
- 复制方案的代价这次是量出来的：`cp -r` 之后没几个小时，`diff -r` 就发现两边已经有分叉 —— `.system` 下有 45 个文件不一致（WSL 的 codex 是 0.160/0.161，桌面端运行时是另一个版本），`learning-system/SKILL.md` 的描述和章节也不同。分叉不是"以后可能会发生"，是"马上就会发生"。
- 顺带一个发现：`codex doctor` 报 `config could not be loaded — entity not found`，而日常 CLI 照样能跑。用"逐个 section 去掉再试"（leave-one-out）的方法定位到 `~/.codex/config.toml` 里那条 `[projects."/mnt/c/users/wjimi"]`（全小写的 `users`）：`ls` 能列出这个路径（drvfs 大小写不敏感），但 Codex 内部解析会失败，于是整份配置的加载检查不通过；删掉它 doctor 就变绿，而同一目录的 `[projects."/mnt/c/Users/wjimi"]` 是好的。两条并存，是某个客户端按当时会话 `cwd` 的拼写自动写进去的。
- 教训：配置里的**路径**写错不会在平时暴露，只会让"加载配置"这一步悄悄失败。以及 leave-one-out 是个便宜好用的定位手法：把可疑文件按 section 拆开，每次只去掉一块跑一次，哪次变绿就是它。
- 退出机制：`rm ~/.codex/skills && mv ~/.codex/skills.bak-<日期> ~/.codex/skills`。
- 共享是整个目录的粒度，没法对子目录做例外。想只共享自己的技能、把 `.system` 留在各自本地，就只能逐个链接子目录。
