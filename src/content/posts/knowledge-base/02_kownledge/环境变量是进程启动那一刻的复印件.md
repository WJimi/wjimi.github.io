# 环境变量是进程启动那一刻的复印件

## 来源

给 Codex CLI 换密钥时产生。`~/.codex/config.toml` 里明文写着 `experimental_bearer_token = "sk-..."`，
我想改成让 Codex 自己去读环境变量，于是先得弄清楚：环境变量到底是怎么到程序手里的？

## 它解决的问题

同一份程序，在不同机器、不同密钥下要表现不同，又不想改代码、不想把密钥写进配置文件。
环境变量的作用就是：**让外部在程序启动之前把配置塞给它**。

## 当前理解

每个进程挂着一块叫"环境"的数据，内容是一串 `KEY=value`。进程创建子进程时，操作系统把这块数据
**复制**一份给子进程。所以变量更像"发下去的复印件"，不是大家共用的一块黑板。

两条推论，比定义有用得多：

- 子进程启动之后再改父进程的变量，已经跑着的子进程不知道。这就是"改完 `.bashrc` 必须重开终端"的原因。
- shell 内部的变量（`GRADE="vip"`）不会进入子进程；加了 `export` 才会被写进环境块、跟着复制下去。

书写规则只有一条：**赋值时写名字，取值时加 `$`**。变量后面紧跟别的字符时用 `${GRADE}1` 划边界，
否则 shell 会去找一个叫 `GRADE1` 的变量，结果是空。

引号也只做一件事——决定里面的内容解不解释：双引号解释变量，单引号原样保留，
不加引号时连空格都会被当成参数分隔符（`没有 引号` 会变成两个参数）。

## 实践

- 演示脚本 `~/ovo/shell-demo.sh`。第 5 段是这套机制的直接证据：子进程读到"第一次"，
  而父 shell 已经被改成"第二次"了。
- 给 Codex 换密钥时做的四步：密钥只留在 `~/.config/codex/secrets.env`（权限 600）；
  `.bashrc` 只写一句 `. ` 引用它；`config.toml` 里把 bearer token 换成
  `env_key = "DEEPSEEK_API_KEY"`（配置只写变量名，值由环境提供）；
  最后用 `codex doctor` 看到 `provider auth env var DEEPSEEK_API_KEY (present)`，
  再让 codex 真跑一次才算验证通过。
- 踩过的坑：我以为"环境变量里是旧密钥、配置文件里是新密钥"，实际两个值 `sha256sum` 完全一致，
  是同一个密钥漏在了两个文件里。判断"是不是同一个值"要算哈希，不能看前缀。
