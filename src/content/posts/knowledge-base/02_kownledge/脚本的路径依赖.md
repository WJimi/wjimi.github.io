# 脚本的路径依赖

## 来源

2026-10-04，我想把 buff-trade 里的 .py 脚本全收进 `src/` 目录，方便辨认。
我担心的是一句很模糊的话：「感觉要改动的地方很多，而且可能出 bug」。
AI 把这句话拆成了一个具体问题：**脚本平时是靠什么找到自己的文件的**。

## 它解决的问题

项目换一个目录、或者换个命令行位置启动，就报「找不到 token.txt」「没有 lists 目录」。
这类问题怎么在动手之前就看出来，而不是搬完再逐个试。

## 当前理解

### 三个「位置」不是一回事

```text
当前工作目录（CWD）  你敲命令时所在的目录，不是脚本住的地方
__file__            脚本自己的位置，从哪启动都不变
sys.path            去哪找模块：python src\shell.py 会把 src\ 加进去
```

`cd C:\ && python C:\wbog\buff-trade\src\shell.py` 的 CWD 是 `C:\`，
而 `__file__` 仍然是那个 `.py`。两者混用，就会出现「在我机器上能跑」。

`sys.path` 那条顺便解释了为什么脚本能平铺：`python src\shell.py` 会把 `src\` 放进搜索路径，
于是同级的 `import recipe_ids` 成立。再往下分一层，就得处理包导入和入口，
这就是「`src/` 里保持平铺」的原因。

### 相对路径是一种隐式输入

`open("lists/x.md")` 是相对 CWD 解析的。同一份代码，两种启动方式两种行为——
程序没坏，只是看错了地方，这类 bug 最难查，因为输入没写在参数里。

### 用 `__file__` 也算错过：错在假设

`Path(__file__).parent / "lists"` 在「脚本和数据同目录」时完全正确。
脚本一旦搬进 `src/`，同一行就指向了 `src/lists`。
所以搬家的真正障碍不是路径写法有错，而是这个隐含假设：

```text
脚本所在目录 == 数据所在目录
```

### 收敛到一处，收益是「改动半径」

buff-trade 的做法是新增 `src/paths.py`：

```python
SRC = Path(__file__).resolve().parent      # src/
ROOT = SRC.parent                          # 项目根：数据都在这里
LISTS = ROOT / "lists"
```

其他脚本只写 `from paths import ROOT`。关键不在少打几个字，而在
**同一个事实只写一遍**：写 15 遍，改一次目录结构就是 15 个出错点；写 1 遍，改动半径是 1。
之前「不能搬」，正是因为「数据在根目录」这个事实隐含在 15 个脚本各自的 `Path(__file__).parent` 里。

### 两个顺带的点

- **候选取并集，不取一个**：令牌文件可能放在项目根、脚本目录、当前目录，
  查找时按优先级把三个位置都列出来，才不会被启动方式绑住。
- **搬家搬的是状态，不只是代码**：`.browser-profile/`（登录态）、令牌、账本这些才是容易忘的。
  代码放哪都行，状态文件找不到就等于换了一台机器——重新登录、重新填余额。

## 实践

2026-10-04 实际做的：

```text
git mv 14 个 .py → src/           保留改动历史
新增 src/paths.py                  SRC / ROOT / LISTS / REPORTS / FILTERS / LEDGER / PROFILE / 两个令牌
11 个文件里的 HERE = Path(__file__).resolve().parent → from paths import ROOT
recipe_ids.py 的令牌查找          加上「项目根」这个候选位置
```

可复用的自检（改完路径相关代码就跑一遍）：

```powershell
python -m py_compile src\*.py                       # 语法
cd C:\                                              # 故意换到项目外
python C:\wbog\buff-trade\src\budget.py 60          # 结果要和在项目根跑一样
```

在项目外跑仍然读得到 `lists/` 和令牌，才算真的与 CWD 无关。
