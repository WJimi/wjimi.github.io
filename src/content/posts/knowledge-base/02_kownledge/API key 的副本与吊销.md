# API key 的副本与吊销

## 来源

给 Codex 换 DeepSeek 密钥时反复出问题：改了本地文件、也吊销了旧密钥，结果仍然连不上，
我对"为什么会这样"的第一次推理是错的。

问题本身记在 [[密钥换掉了，为什么还是用旧的？]]。

## 它解决的问题

服务器怎么知道"这次请求是谁发的、该扣谁的钱"？它不认识你这个人，只看请求里带的那串字符。
API key 就是那串字符。

## 当前理解

它作用上等于"账号 + 密码"合体：**谁拿到这串字符，谁就能用你的余额**。

用钥匙和锁对应：

| 现实 | 对应 |
| --- | --- |
| 你的账号（锁后面是钱） | 一把锁 |
| 一个 API key | 一把钥匙 |
| 后台"新建 API key" | 配一把新钥匙（同一把锁可以配很多把） |
| 删掉本地文件里的密钥 | 把你手里那把钥匙扔了 |
| 吊销 / revoke | **换锁芯** |

我一开始想错的地方在这里：安全的判断标准不是"钥匙藏在哪"，而是两件事——

1. 这串字符一共有多少副本、在谁手里；
2. 它还能不能作废（服务商那边还能不能把它从"有效清单"里划掉）。

所以"放在 600 权限的文件里"只是让副本变少，**不等于安全**。真正兜底的是吊销：
吊销之后，即使有人手里还攥着副本，那串字符也换不到服务了。

反过来同样要记住：**删掉本地文件、改掉配置文件，都不会让服务器停止接受那串字符**。
这正是"我明明换了密钥，为什么它还在用旧的"的机制。

## 实践

- 一台机器一把钥匙：哪台机器泄露了，只吊销那一把，不影响其他机器继续用。
- 换密钥的顺序是：先配新钥匙 → 把用它的地方都换好 → 最后再吊销旧钥匙。
  反过来做会把自己关在门外（我踩过）。
- 判断"两处的值是不是同一个 key"，用 `sha256sum` 比对，不要看前缀。
