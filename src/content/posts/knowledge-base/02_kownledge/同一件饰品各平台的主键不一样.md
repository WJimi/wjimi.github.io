# 同一件饰品各平台的主键不一样

## 来源

拼 BUFF 链接时撞上的：配方给的是**名字**，URL 要的是**数字**。
顺着找映射，又发现第三方数据站有它自己的一套 ID。
背景见 [[knowledge-base/03_projects/automation/tradeup-material-sourcing|CS2 炼金配方的自动取材]]。

## 它解决的问题

跨平台做数据或自动化，第一步该让什么当「钥匙」？
选错了，后面每一步都要靠模糊匹配，错一件就全错。

## 当前理解

同一件东西——`MAC-10 | 风暴迷彩 (久经沙场)`——在四个地方有四种身份：

| 平台         | 主键                     | 长什么样                                  |
| ---------- | ---------------------- | ------------------------------------- |
| Steam      | `market_hash_name`     | `MAC-10 \| Storm Camo (Field-Tested)` |
| cs2up（配方站） | 没有 ID，只有名字             | 同上 + 中文名                              |
| CSQAQ（数据站） | `goodId`               | `301`（它自己从 1 开始编的内部号）                 |
| BUFF       | `goods_id` / `buff_id` | `1115547`（商品页 URL 里的那个数）              |

机制：**ID 是平台内部的，跨平台不通用。**
每个平台为了自己查得快，给自己的表编了主键；它们之间没有任何约定。
能跨平台对齐的只有「名字」这种自然键——而名字本身也不保险：
英文名带磨损后缀 `(Field-Tested)`、中文名写成 `(久经沙场)`，写法一变就对不上。

所以这类项目的第一个设计问题不是「怎么爬」，是：

```text
钥匙选谁？映射谁来维护？
```

| 选谁当钥匙 | 好处 | 代价 |
| --- | --- | --- |
| 名字 | 各家都给，人能看懂 | 写法必须严格一致，改名就断 |
| 某一家的 ID | 稳定、短、好索引 | 出了这家就得转一次，转到哪家就得维护到哪家的映射 |

这次的解法值得记下来：**别人的映射表，比自己去爬一遍便宜得多。**
CSQAQ 已经维护好了 `market_hash_name → 它的 goodId → BUFF 的 buff_id`，
我们只是借用，不用自己建。

一个引申出来的判断标准：看一个第三方数据源值不值得依赖，
就看它是不是**同时给了「两边的键」和「数据本身」**。
只给一边的键，你还是得自己对；两样都给，它就替你吃掉了整个映射成本。
