# 403 的目录里文件为什么还能访问

## 来源

做 [[knowledge-base/03_projects/web/ivn-duty-challenge|IVN 值班日志]] 那道新手题时，
第一关故意让 `/dev/` 返回 403，却要求选手还能访问它下面的 `/dev/query.php`。

这也是 day01 写下的「有时访问网页就是访问一个服务器里的一个文件或文件夹」的延伸。

## 它解决的问题

一个目录返回 403，为什么目录里的文件还能正常访问？403 到底拦住了什么？

## 当前理解

HTTP 请求的 URL 和服务器上的文件之间是一条**映射**，不是等价关系。

nginx 拿到 `/dev/` 这个 URI，做两件事：

1. 按 `root` 拼出文件系统路径：`/var/www/html/dev/`
2. 发现它是个**目录**，于是按 `index` 指令去找目录里的默认文件（`index index.php;`）

第二步找不到能用的 index，又没开 `autoindex`（列目录），nginx 只能回 403。
它的意思是「这个请求我没法给你结果」，而不是「这个目录被封了」。

而 `/dev/query.php` 是一个**具体存在的文件**，nginx 直接把它交给 php-fpm 执行，
根本不走"找 index"那条路。所以目录 403、里面的文件 200，可以同时成立。

反过来，如果真想用 403 挡住整个目录，得写成：

```nginx
location /dev/ { deny all; }
```

这样连 `/dev/query.php` 也会被拦——拦截发生在 location 匹配阶段，比"找 index 还是找文件"更早。

一句话：**403 描述的是「这次请求的结果」，不是「这个路径的权限」。**

## 实践

**出题时**：把「被禁的目录」和「目录里忘了删的备份」分开设计，就能做出
「访问目录是 403，但扫出文件能下载」的效果。而且这是 nginx 的自然行为——
目录里不放 index 文件、也不开 autoindex，就自动成立，不用写任何额外配置。

**做题时**：扫到 403 不等于这条线断了。应该继续用带后缀的字典去撞具体文件名
（`.bak` / `.zip` / `.swp` / `.old`），而不是直接放弃。

我这次是靠 `.bak` 命中 `/dev/index.php.bak` 的。注意一个工具细节：
**dirsearch 默认是替换最后一个点后面的扩展名**（字典里的 `index.php` 配 `-e bak`
只会试 `index.bak`），要试出 `index.php.bak` 必须加 `-f`（`--force-extensions`）；
gobuster 的 `-x` 是追加式的，不用额外开关。这个区别我当时写错了，是实测才纠正过来的。
