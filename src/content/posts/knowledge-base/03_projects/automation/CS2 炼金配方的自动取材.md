# CS2 炼金配方的自动取材

## 来源

2026-09-27 一天里目标改了两次，如实记下来——「目标怎么变的」本身就是这个项目的知识：

1. 立项：想在 BUFF 上自动筛饰品、自动买入，以为要抓包、逆向。
2. 看到开发者接口文档：以为要走官方 API（¥300 / ¥1000 两档）。
3. **真正的目标（现在是这个）**：从 cs2up.cn 找炼金（汰换）配方 →
   按配方在 BUFF 上把材料一件件找出来 → **加进收藏** → 剩下的由人做。

最关键的差别：**程序不花钱**。它只负责「看」和「点」，付款是人按下去的。
所以这不是 API 客户端项目，是**界面自动化**项目。
前两轮查到的官方 API 知识不作废，但退出主线，见文末。

## 它解决的问题

把「照着一份炼金配方去 BUFF 一件件找材料」这件重复劳动交给程序。

完整流程，标出每一步是谁在做：

| 步骤 | 谁 |
| --- | --- |
| 挑一份 ROI 合适的配方 | 程序从 cs2up 取（或人挑好，程序只负责取） |
| 把配方翻译成若干条 BUFF 采购条件 | 程序 |
| 在 BUFF 上找出符合条件的那一件 | **程序——本项目的主体** |
| 加进收藏 | 程序 |
| 付款 | **人** |
| 在游戏里做汰换 | **人** |

## 当前理解

### cs2up 有公开 JSON 接口，配方是结构化的（2026-09-27 确认）

`tradeup.html` 是个 Alpine.js 前端，数据来自两个接口：

- `GET /api/recipes?mode=spot&...` —— 配方广场列表，可按 ROI、成本、收藏品、品质筛
- `GET /api/recipe-detail?mode=spot&id=<detail_id>&version=<version>&bucket=...` —— 配方详情

详情里每份配方给出 `inputs[]`，每条材料长这样：

```text
name        MAC-10 | Storm Camo (Field-Tested)   ← 英文 market_hash_name
cn          MAC-10 | 风暴迷彩 (久经沙场)
collection  The Ascent Collection
count       7                                     ← 这一项要买几件
wear        0.174                                 ← 目标磨损
bin_lo/hi   0.15 / 0.18                           ← 要求的磨损区间
min/max_float 0.0 / 0.637288                      ← 这个皮肤自身的磨损范围
unit_price  0.02
```

**这一行就是给 BUFF 的采购条件**。所以「找配方」这一步几乎不需要界面自动化，
真正的难点全部落在 BUFF 那一侧。

#### 配方是有保质期的：几分钟就作废

列表接口每次都带一个 `version` 字段，实测是 `1790524216228-base-all` 这种形状——
前面那串就是**当前时间戳（毫秒）**。后端重算一次配方，这个值就变一次。

cs2up 的前端代码里专门有一个分支处理这件事：拿旧 `version` 去问详情，
会返回 `RECIPE_VERSION_MISMATCH`，页面就提示「配方已更新，请刷新列表后重试」——
也就是用户看到的「每隔几分钟要求刷新界面」。

对我们的含义（重要性不比技术低）：

- **配方不能被缓存下来慢慢执行。** 每次跑都得重新拉，拿到什么版本就用什么版本。
- 配方里的成本和期望收益都是「几分钟前那个时刻」的价格算出来的。
  等你把 10 件凑齐，这份配方的经济性可能已经变了。
- 这和「收藏不锁货」其实是同一个问题的两面：**这个项目的产出天生是短时效的。**
- 还有一个更阴的：**`detail_id` 只在同一个版本里有意义。** 实测 44856 这个编号，
  22 点多返回的是「炙热沙城 II × 攀升武器箱」（成本 0.2、ROI 106%），
  零点再查同一编号，返回的是「列车 × 攀升武器箱」（成本 1.22、ROI 13.6%）。
  编号只是当前版本列表里的一个位置，不是配方的身份。
  所以拉详情必须带着当时那个 `version`——cs2up 自己的前端就是这么做的。

### BUFF 那一侧要做什么

把 `(该饰品, 磨损区间, 价格上限, 数量)` 变成「一次筛选 + N 次点击」。

**2026-09-27 已确认：能。** BUFF 的在售列表支持自定义磨损区间，列表上每一件的
磨损和价格都是精确值，可以逐件关注。所以不需要「打开每一件去读 float」，
候选集在筛选器里就已经被限定好了。

这个答案把项目从「识别界面」（难）推到了「设置筛选条件 + 点关注」（工程量）。
它同时也说明：**真正要自动化的是"操作序列"，不是"图像理解"。**

### 筛选条件能拼进 URL——但参数在 `#` 后面（2026-09-27 实测）

真实样例（用户从地址栏复制）：

```text
https://buff.163.com/goods/1115547?from=market#tab=selling&min_price=1&max_price=31&page_num=1&sort_by=price.asc&min_paintwear=0.28&max_paintwear=0.35
```

拆开看，配方的每一个字段都有对应的位置：

| 配方给的 | URL 里的位置 |
| --- | --- |
| 饰品 | 路径里的 `/goods/<goods_id>` |
| 磨损区间 `bin_lo` / `bin_hi` | `#` 后的 `min_paintwear` / `max_paintwear` |
| 价格区间 | `#` 后的 `min_price` / `max_price` |
| 「取最便宜的」 | `sort_by=price.asc` |
| 翻页 | `page_num` |

**注意一个容易吃亏的地方：这些参数在 `#` 后面，不在 `?` 后面。**
浏览器不会把 `#` 后面的内容发给服务器，所以那段筛选是前端 JavaScript 算的
（见 [[knowledge-base/02_kownledge/url-fragment|URL 的 # 后面是什么]]）。
推论：这个 URL 能用浏览器打开成"筛选好的页面"，但**纯 HTTP 请求拿回来的是未筛选的空壳**。
所以程序这一侧要的是**真实浏览器**（Playwright 一类），不是 requests。

**关于这几个参数，我下过一次错的结论，过程和更正都留着（这是这轮最值得记的一课）。**

一开始看到保存下来的页面：第一行磨损是 `0.3461`，不在 `0.18~0.21` 里；
页面里 `min_paintwear` 出现 0 次，磨损区间控件是空的。
再去读前端脚本，看到构造请求时它读的键叫 `float_range`。
于是我的结论是：**`min_paintwear` / `max_paintwear` 是死参数，只有 `float_range` 才有用。**

**这个结论是错的。** 后来真实跑 `focus_buy.py` 时，两页各 10 行，**全部**落在
`0.18~0.21` 区间里——如果参数真的没生效，10 行全命中的概率几乎为零。

回头再看脚本里另一段才知道为什么：

```js
if (a.min_paintwear || a.max_paintwear) {
  var p = rangeKeyParser.deparse(a.min_paintwear, a.max_paintwear);  // "0.18-0.21"
  $(x + " .w-Select-Multi[name=float_range]").attr("value", p).find("h3").text(p);
}
```

也就是说：URL 里的 `min_paintwear` / `max_paintwear` 会被**还原进界面控件**，
控件有了值，构造请求时读 `float_range` 才读得到。**两者是一根链条，不是互斥的。**

那第一次那份页面为什么是空的？因为那一次是 `peek.py` 打开页面 → 发现没登录 →
**人在窗口里登录了一遍**，登录过程中的跳转把 `#` 里的参数丢掉了，
落回来的是"什么都不筛"的原始列表。（`#` 后面的东西本来就不发给服务器，
页面一跳转就没了——又是 [[knowledge-base/02_kownledge/url-fragment|URL 的 # 后面是什么]] 那一课。）

**这一课的教训比参数本身重要：一次观察 + 一段代码，不足以定案。**
我当时手里的证据是"这一份页面没筛"，却推成了"这个参数没用"——
两句话之间差着一个"登录时 hash 会丢"的机制，而那个机制我没想到。
正确的态度是：结论先标成"待验证"，然后设计一个能把它证伪的观察。

收藏页是 `https://buff.163.com/user-center/bookmark/sell_order?game=csgo&from=nav`，
**按时间顺序**排。这解决了「付款的人怎么知道该买哪几件」——刚关注的就在最前面。

### 名字 → BUFF goods_id：借 CSQAQ 的映射（2026-09-27）

`docs.csqaq.com` 是一份开放的 CS2 饰品数据 API（37 个接口，Apifox 托管）。
接口清单和样例存到了 `C:\wbog\buff-trade\csqaq_api.md`。接入方式是
请求头带 `ApiToken` + 绑定本机 IP 白名单，限速 1 次/秒。

链路上缺的那一环它正好补上，两个接口就够：

```text
market_hash_name ──POST /api/v1/goods/getPriceByMarketHashName──> goodId（顺带给 BUFF 参考价）
                 ──GET  /api/v1/info/good?id=goodId──────────────> buff_id
```

`buff_id` 就是 `/goods/<这个数>` 里的那个数。官方文档里写得很直白：
这个接口覆盖 网易BUFF、悠悠有品、Steam、C5、IGXE、ECO、R8。

它顺带解决了两件事：

- 配方的**经济性校验**有了外部参照（`buffSellPrice` / `buffSellNum`）。
- 但它给的 `buffSellPrice` 是**全磨损区间的最低价**，而配方要的是
  「磨损 0.15–0.18 这一小段里的最低」。两者不是一回事，直接拿来算收益会偏乐观。

### 必须提前想清楚的机制风险：收藏不锁货

### 「关注」按钮的真实结构（2026-09-28 从保存的页面里读出来）

没有猜，是把 `peek.py` 存下来的渲染结果翻开看的。列表里每一行长这样：

```html
<span class="add-bookmark" data-target-type="3" data-target-id="4151405076-B7C7-166245251"
      title="关注饰品" style="cursor:pointer;"><i class="icon icon_focus"></i></span>
<span class="delete-bookmark" data-target-type="3" data-target-id="4151405076-B7C7-166245251"
      title="取消关注" style="display:none;"><i class="icon icon_focus"></i></span>
```

三个值得记的点：

1. **`data-target-type` 是这条路的陷阱。** `3` 是「关注这一件在售」，`2` 是页面上方那个
   「收藏」——收藏的是**整个商品**。名字都叫 `add-bookmark`，选错就默默收藏了错的东西。
2. **点成功的信号是那对 span 互换显示状态**：`add-bookmark` 隐藏、`delete-bookmark` 出现。
   所以程序不用猜有没有生效，点完看一眼就行。
3. `data-target-id` 的格式（`4151405076-B7C7-166245251`）和官方 API 文档里
   `sell_order_id` 的例子（`1085743363-1EA0-137401908`）是同一种东西——
   页面上「这一件」的身份，就是 API 里的「在售订单ID」。

更好的消息：**每一行本来就带着结构化的数据，不需要"看图"**。
`<tr>` 上有三个 JSON 属性——`data-asset-info`（含 `paintwear`、`paintseed`、`assetid`）、
`data-order-info`（含 `price`、`bookmarked`）、`data-seller`。
于是"找出磨损落在 0.18~0.21 里、最便宜的那几件"可以完全在本地算，
不用相信任何筛选器：

```text
读出所有行 → 解析每行 paintwear 和 price → 自己按区间过滤 → 按价格排序 → 只点该点的
```

这条"本地核对"的写法，正是上面那个死参数踩坑之后想明白的：
**筛选器是找路用的，核对必须自己做。** 筛选错了会安静地给你一堆不该买的东西。

炼金要凑齐 **10 件**，少一件整套作废。而「加收藏」只是记下来，**不锁库存**——
你从第一件加到第十件的过程中，前面几件可能已经被别人买走。

所以真正的难点不是「找得到吗」，是 **「找得齐吗、找齐之后还买得到吗」**。

## 当前焦点（下一步）

第一个里程碑（配方 → 筛选页）已经跑通。接下来的分叉只有一个：
**自动化程序在哪台机器上跑、用哪份登录态？** 这决定了后面所有代码的形状。

三种可能的形态：

| 在哪跑 | 登录态从哪来 | 代价 |
| --- | --- | --- |
| 你自己的 Windows | 你日常那个已经登录 BUFF 的浏览器 | 要在这台机器上装好浏览器自动化工具；跑到一半你会看到鼠标自己在动 |
| 这个 Linux 环境 | 你手动登录一次，把登录态导出来复用 | 这里可能没有图形界面，登录这一步会别扭 |
| 一台服务器 | 手动登录一次导出登录态 | 长期最稳，但第一步的登录还是要人来做 |

## 更早的焦点记录（已完成）

```text
cs2up 配方 ──✅──> 名字 / 磨损区间 / 价格 / 数量
              └──✅──> CSQAQ ──✅──> BUFF goods_id ──✅──> 拼筛选 URL ──❓──> 点关注
```

链路在纸面上已经通了，但**一次都没实测过**。现在缺的是一次端到端的验证，
而不是新的知识。要验的是这一串：

1. 注册 CSQAQ，拿到 `ApiToken`，绑定本机出口 IP（这一步只有你能做，需要你的账号）
2. 用一份真实配方的材料名字，换出 `goodId` 和 `buff_id`
3. 用 `buff_id` 拼出那条筛选 URL，在浏览器里打开，看它**是不是真的落到筛选好的页面上**

第 3 步是整个项目的"断点"：如果 URL 拼出来打不到目标，后面所有自动化都是空谈。

一个要先有心理准备的小坑：**绑定 IP 意味着换网络就会失效**。
家里的宽带出口 IP 通常是动态的，断了重连可能就变了，
这时 API 会开始报错，得重新绑一次。这是真实的运维问题，不是 bug。

## 被放弃的路线：官方开发者 API（记录，不作废）

它解决的是「程序替你花钱」，而现在要的是「程序帮你找、你自己花钱」，所以退出主线。
留着的原因是：如果采集端以后被风控，**或者**你想拿到「每一件确切 float」，
`/api/market/enterprise/goods/sell_order` 是唯一正规途径（5 秒更新、只对企业 API 开放）。

已知事实（来自本地保存的开发者页面，离线副本 `C:\wbog\buff-trade\buff_openapi.json`）：

| | 开发者 API ¥300/月 | 企业 API ¥1000/月 |
| --- | --- | --- |
| 数据 | 全站最低价（5～10 分钟刷新）、固定磨损分档的最低价/在售数/流通性 | 多求购最高价、区间前十均价、**指定饰品在售订单列表（5 秒）** |
| 下单 | 只能买标品（武器箱/印花/通行证…），一次最多 20 个 goods_id | 多一个「按订单号买非标品」，限在售最低价 3000 元以下的枪类 |
| 买不到的 | 刀、手套 | 刀、手套 |

前置：API KEY（`Authorization: Bearer`）+ **公网 IP 白名单（最多 5 个）** + 签实名承诺函。

### 2026-09-28：买来的饰品有 7 天冷却——这条把项目的性质改了一半

实测：BUFF 买到手的饰品有 **7 天冷却期**，冷却结束后才能参与汰换、才能上架出售。

（2026-09-28 澄清：这条对**买进来的所有饰品**都成立；而**汰换的产物可以立即上架**。
所以周期就精确地是 7 天：第 0 天买材料 → 第 7 天汰换 → 当场卖掉。
7 天里的价格波动由操作者自己承担——它从"待解决的问题"变成了**已经接受的设计前提**。）

由此，7 天里**风险的位置**很清楚了：
材料的价格在第 0 天就锁死了（0.33 元），而产出物的价格要到第 7 天才知道。
**整个玩法的收益完全取决于第 7 天那一下。**

**"等待汰换"在等什么**，这个从立项起就挂着的问题，答案就是 7 天。它带来三个后果：

1. **周期是 7 天**，不是"看到便宜就买、买了就卖"。一年最多五十几轮。
2. **真正的风险换了位置。** 之前以为风险是"买贵了"（0.21 变 0.33）；
   现在最不确定的是**7 天之后产出物还能卖多少钱**。配方算的期望产出 0.4268 是**当下**的价，
   而钱要到 7 天后才收得回来。
3. 所以这不再是"薅当下的差价"，而是**押 7 天后的价格**。认知上完全换了一件事。

顺带冒出两个新问题：

- **持有期波动**：7 天里产出物价格能变多少？CSQAQ 有 K 线接口
  （`/api/v1/info/simple/chartAll`），拿历史数据就能回测"过去每个 7 天窗口涨跌多少"。
  这才是把"押注"变成"估算"的办法。
- **带冷却的饰品更便宜吗？** BUFF 每一行的 `data-asset-info` 里就带着
  `has_tradable_cooldown` 和 `tradable_unfrozen_time`。既然买到手无论如何都要等 7 天，
  那么"买一件本来就带冷却、因此更便宜"的，等待时间并没有变长——
  如果这个折扣真的存在，它是白捡的。这是个可以用现有数据直接验证的假设。

### 2026-09-28：串成一条命令（方向一收尾）

原来的三个脚本合成一条链：

```text
run_pipeline.py --top
  ├─ ① 取当前 ROI 最高的配方        （cs2up）
  ├─ ② 名字 → goodId + BUFF 参考价  （CSQAQ 批量接口）
  ├─ ③ goodId → buff_id → 筛选 URL  （CSQAQ 单件接口）
  ├─ ④ 开浏览器、逐行核对磨损、点关注 （Playwright，Windows 上跑）
  └─ ⑤ 写出 buy_list_<配方id>.md     （人照着付款的清单）
```

工程上值得记两点：

- **浏览器那一段延后 import**。前面几步只发 HTTP，不需要 Playwright；
  这样在没装浏览器的机器上也能跑到"出 URL"为止，报错也指明缺哪一步。
- **失败不占额度**（见上一节那条 bug）已经合并进主流程。

后来又加了 `shell.py`：一个交互式界面，改条件、看列表、看详情都不用重敲参数，
条件存进 `filters.json`。

这里踩了一个"看起来是同一个需求、其实是两件事"的坑，值得记：
提的需求是「每次刷新像按 Ctrl+L，让条件块回到第一行」。我先做成了**擦屏**
（`\033[2J`），结果把上面的历史一起抹掉了——那不是他要的。
他要的是**顶上去**：内容滚出可视区，但还在滚动历史里，往上滚能看回来。

差别就在一行代码：

| 想要的效果 | 写法 |
| --- | --- |
| 真擦掉（历史也没了） | `\033[2J\033[H` |
| 顶进滚动历史、光标回左上 | 输出 N 个换行，再 `\033[H` |

所以现在 `ui.scroll_off(n)` 走第二条路（n 取终端高度减一），
并把条件块同步压成两行——原来竖排 14 行，一屏放不下，条件本身就被挤出视线了。
**"让第一行是条件"和"保留历史"这两个要求同时满足时，屏幕预算就得重新算。**

两个判断还是保留着：是不是真终端、Windows 的 VT 有没有打开。
输出被管道接走时整个跳过，免得转义字符写进文件。

同一轮还收了三个小反馈，都记一下，因为它们是同一个毛病：

- **详情头部散着**：标签和值之间靠空格凑，没对齐。改成按列算宽度（中文按两字宽）。
- **成本放错位置**：原来单独占头部一行，现在挪到"要买材料"表格的最后一行、
  只填在「小计」栏，前面留空——**合计本来就属于表格，不属于标题。**
- **看完 BUFF 比价马上被顶屏盖掉**：因为按完 `b` 直接 `continue` 回主循环，
  新一轮先把屏幕顶上去。加了一句"按回车回到列表"。
  **凡是"打印完就继续循环"的地方，都要想想人看不看得完。**

`README.md` 也写了：一条命令怎么用、要装什么、这一路踩过哪些坑。

### 「在网页上自己挑一份配方，再交给程序」——查了三条路

1. **从网页上抄 `detail_id`**：走不通。翻它的模板看到，配方卡片是
   `@click="openDetail(recipe, 'summary')"`，`detail_id` 只活在 JS 变量里，
   不渲染进 DOM；页面地址也不会因打开配方而变化（整站只有 `#login` 用 hash）。
   所以没有"看一眼就能抄下来"的编号。
2. **分享链接**（`share.html?sid=…`）：能读到，但只够一半。
   它背后的接口是 `GET /api/share-payloads?id=<sid>`，
   返回的是配方快照：材料名、数量、目标磨损、单价。**没有磨损区间。**
   而区间不能从磨损反推——试过一个公式（按 0.03 分档），第二个样本就出现反例
   （`wear=0.142` 对应 `0.11-0.15`，不是 0.12-0.15）。
   → 又是一个"一次观察不足以定案"的例子。
3. **把筛选面板搬到命令行**（采用）：给 `--list` 加上成本区间、ROI 区间、
   收藏品、产物名、排序方式等参数，挑配方这一步就完全落在链路里。

```text
python run_pipeline.py --list 10 --cost-min 5 --cost-max 30
python run_pipeline.py --list 10 --roi-min 20 --roi-max 60
python run_pipeline.py --list 10 --sort-by cost --output-name "AWP"
```

后来把常用的三维也接上了：**品质**（`--rarity 军规级,受限级`）、
**保本率**（`--break-even-min 50`）、**最高倍数**（`--max-multiple-min 2`），
外加一个通用区间口 `--filter 字段:下限:上限`（字段共 8 个：roi、cost、expected_profit、
max_output、max_output_multiple、break_even、eco_break_even）。
接口参数名一律是 `sort_<字段>_min` / `sort_<字段>_max`，百分数字段要先除以 100——
这是从它的前端脚本里读出来的（`SORT_OPTIONS` 里的 `scale`）。

实测对照（2026-09-28）：

| 条件 | 结果 |
| --- | --- |
| 不筛 | ROI 90%、保本 66.7%、倍数 4.83、成本 0.22 元 |
| 军规级 + 保本≥50 + 倍数≥2 | ROI 35%、成本 9.6~10 元 |

第一行和第二行的对比很说明问题：**越往"看起来靠谱"的条件走，成本越高、ROI 越低。**
便宜又高 ROI 的那些，正是最不可执行的——它们假设每件都按最低价买到。
保本率和倍数比 ROI 更接近风险的语言。

**（流动性字段已去掉：列表数据里 `liquidity_rank` 大多是空的，拿它筛会一个都不剩。
顺手把 `--list` 的呈现换成了对齐表格 + 保本率横条，`--show <id>` 展开成"材料表 + 产物表"。
好看不是目的——横条让 60% 和 50% 一眼分得出，表格让"要买几件、买哪个磨损区间"不用再读句子。）**

### 顺手把 cs2up 的三个指标算法验出来了

列表接口给了保本率/倍数，**详情接口却不给**。于是拿一份配方的产物明细自己算，两边对得上：

```text
保本率 = 价格 ≥ 成本的那些产物的概率之和
倍数   = 最贵产物的价格 ÷ 成本
期望   = Σ(产物概率 × 产物价格)
```

（验算例：成本 10.04，产物里 28.44/17.20/16.80 三件≥成本，概率各 20% → 保本率 60%，
最贵 28.44 ÷ 10.04 = 2.83 倍，Σ概率×价格 = 13.50——和接口给的数完全一致。）

好处是**不用"信"这些汇总字段**：`--show` 里现在就是自己算的，
并且会顺手核对期望值，对不上会报警。这套"原始数据自己算一遍"的习惯，
和前面"不要相信筛选器"是同一件事。

（产物表的呈现也定了：只给**磨损档位**（崭新出厂…），不给具体磨损值。
理由是产物磨损本身就是个期望值，实际落点由 10 件材料的平均磨损决定、会在档位内浮动——
写一个精确到小数点的数字反而误导。材料表相反，必须给**磨损区间**，
因为那是要照着筛货的条件。）

### 脚本自己的坑：失败会占掉额度（2026-09-28 修）

第一次真实跑的日志：Tec-9 要 9 件，点了 9 次，8 次成功、1 次失败就停了；
MP9 要 1 件，第一次没点上，于是**一件都没点到**。

原因是脚本里那句"点够 want 件就停"把失败也算成了一件——**失败根本不该占额度**。
改法：只有成功才计数，失败就往后找下一件，直到凑够或者没得可点。

还有一层：那两次失败**为什么**失败，当时的日志答不上来，只写了"点了但状态没变"。
现在脚本会监听页面上所有跟 bookmark 有关的请求，把服务端的原话打出来——
"订单已被别人买走"和"重复关注"是完全不同的两件事，不能用同一句废话盖过去。

这也带出"会改东西的脚本"的第一条纪律：**失败要有原因，不能只有结论。**

### 第二次真实跑：429（点太快被限速）

同一份清单里又出现一条失败，原因这次打出来了：

```text
| — | — | — | `4150486833-B7D5-166245361` | 失败：服务端 HTTP 429：<html>429 Too Many Requests</html> |
```

**429 不是"这件买不到"，是"你问得太急了"。** 把它们混成同一句"失败"，
就会得出完全错误的结论（以为市场没货，其实是自己被限速）。

修法两条：每次点击之后固定歇 2.5 秒（`--pause` 可调）；
碰到 429 就等 5/10/20 秒重试最多三次（`--retries` 可调），
而且重试期间**不占用"还差几件"的额度**——它压根不算一次尝试失败。

顺带把清单的形态也定下来了：统一放 `lists/`，去掉付款入口，
开头固定一行给人回填的账：

```text
- 本次计划 10 件，实际 10 件，合计 ￥2.03，售出 ￥______
```

`售出` 留空是因为它属于**7 天之后**的信息——这份清单从"采购单"变成了一条完整的账，
把"花了多少"和"收回来多少"记在同一条记录里。这正是整个项目最需要的那个反馈闭环：
**有了这一行，才知道配方估的 ROI 到底偏了多少。**

### 第三次踩版本这个坑：开着页面抄下来的 id，过一会儿就不是那份配方了

试 `--show 88599` 时拿到 cs2up 的拒绝：

```json
{"ok":false,"error":"当前账号无权查看该配方详情。"}
```

一开始以为是"付费配方"，差点当成新发现。但对照一下版本号才看清：

```text
人跑那份 162747 时：version = …-triple-all
现在再查同一个 id ：version = …-base-all
```

**版本档位变了**（`triple` → `base`），id 指向的东西跟着换了一批。
所以"看不了"很可能不是那份配方被锁，而是**那个编号现在属于别的东西**——
和之前"同一个 44856 换版本变成另一份配方"是同一个坑的第三次出现。

处理方式：不猜、不崩。拿不到详情就把 cs2up 的原话原样报出来，让人换一份继续。
提示语也改了——原来所有 403 都被归到"令牌不对/白名单"，那会把注意力引到完全错误的方向。
**同一个状态码在不同服务上含义不同，提示不能写死。**

### 把两种"失败"分清楚（2026-09-28 用数据定的案）

上一节那个 403 我当时归给了"版本变了"，后来又出现一批 **409**，于是专门做了两组测试
把两者钉死：

| 现象 | 真正的意思 | 证据 |
| --- | --- | --- |
| `409` + `RECIPE_VERSION_MISMATCH` | **配方列表过期**（我们拿着旧版本号查详情） | 用两小时前的版本号查 41286 → 409，`current_version` 指着新版本；换成新版本号 → 200 |
| `403` + `当前账号无权查看该配方详情` | **真的没权限**（订阅/付费配方） | 同一版本下反复查 162747 → 一直 403，而同时段 20 份其它配方全 200 |

**"对方拒绝"和"你的数据过期了"是两回事**，混在一起就会朝错的方向修。
（这和之前 429 那次是同一条教训的第二次出现：429 不是"这件买不到"，403 不是"版本过期"。）

### 付费配方长什么样：60 份实测

拿当前版本、按 ROI 降序取 60 份，逐个拉详情（遇到 409 就换新版本重试）：

```text
能看 37 份   被拒(403) 23 份

能看：成本 0.22 ~ 14.24 元（中位 0.43）
      bucket  two:20  one:3  three_consumer:7  three_industrial:7
被拒：成本 14.08 ~ 15.22 元（中位 14.30）
      bucket  清一色 three_industrial
      品质    清一色 工业级 → 军规级
```

所以付费墙**大致落在"更贵、更复杂的三收藏品配方"这一带**；便宜的两收藏品基本都能看。
但别把它当成字段规则：**同一类 three_industrial 里也有 7 份是能看的**，
说明被锁的更像是站点标定的一份集合，而不是"成本大于某个数就锁"。

### 订阅权限怎么交给程序

读了 cs2up 自己的 `js/core/api.js`，机制很清楚：

```js
const token = getSessionToken();               // 从 localStorage 读
if (token) headers.Authorization = `Bearer ${token}`;
```

令牌存在 localStorage，键名 `csgoup_auth_token_v1`；**订阅状态挂在它对应的账号上**。
所以"把权限给程序"就是把令牌交给程序——写了 `cs2up_login.py`：
用同一个浏览器配置打开 cs2up，人登录一次，脚本把令牌读出来写进 `cs2up_token.txt`；
`recipe_ids.py` 之后请求 cs2up 会自动带上这个头。

顺带一个设计取舍：**没有令牌时照常匿名请求**，不报错、不提示。
这样"有没有订阅"不会变成代码里的分支，只影响服务器给不给数据。

### 订了之后实测：池子翻了 3.4 倍（2026-09-28）

把令牌放进 `cs2up_token.txt`，先验它认不认（`/api/auth/me`）：

```text
subscription_active = True    到期 2026-10-28 21:44
software_subscription_active = False   （那是桌面软件的另一档，与本项目无关）
```

然后拿同一批 60 份配方（按 ROI 降序）跑同样的测试：

| | 匿名时 | 订阅后 |
| --- | --- | --- |
| 列表里的 `premium` | false | true |
| 可见配方总数 | 4,717 | **15,993** |
| 60 份样本里 403 的 | 23 | **0** |
| 之前被锁的 162747 | 403 | 200 |

两个结论：

1. **订阅不是"开放几份"，而是把可挑的池子从 4717 份扩到 15993 份**（约 3.4 倍）。
   多出来的正是上一节测到的那些"更贵、更复杂的三收藏品"——也就是**原来根本不在视野里的选项**。
2. 这也说明"付费配方长什么样"这个问题，匿名视角永远答不准：
   你只能看到免费那一半，看见的规律（比如"成本 14 元以上被锁"）其实是半个样本推出来的。
   **要判断一个数据集的形状，先确认自己看到的是不是全集。**

顺带一句工程上的好处：因为当初写成"有令牌就带、没有就匿名"，
订阅这件事**一行代码都没改**，只是多放了一个文件。

### 情报中心是什么（付费后才看得到）

`/intelligence/` 是一个**观点流**，不是数据：实测 3930 条、每页 20 条，
作者是网名（"老杨""霸王""siri"…），等级标 `advanced`。
正文大多是这类东西：

```text
9.26老杨市场分析：今天大盘依旧一般般走震荡趋势…目前只有个别单品能走出行情
我18号喊兄弟们80～90进的野蛮剑齿虎已经到了 cd 了，可以拿去炼金，记得提前模拟磨损度
已知有庄小件：幸存者 30 求、FN57 斯康里娅 30 求、毛细血管 awp 40 求
```

所以它的内容是：**大盘判断、选品推荐、炼金机会提示、庄家/求购盘情报**。

价值要分开看：

- 对**判断方向、情绪、谁会拉盘**有参考价值（人是靠这个吃饭的）；
- 但**不可验证、不可回测，作者动机不明**（有人在喊单）。
  对"配方分析师"这个角色来说，它是输入之一，不能替代数据。
- 特别是"庄在收货"这类——跟着做等于把决策权交给一个不认识的人。

### 一条更硬的机制：公开信号会自我消解

想清楚一件事之后，"找绝佳配方"这个目标本身就得改写：

**配方广场是公开的。一份配方被标成高 ROI，就有几千人同时看到同一份。**
大家按同一份清单去买同一批货，材料价被抬上去，那份 ROI 当场消失——
而且消失的速度取决于它有多"绝佳"。

我们早就撞见过它的微观形态：配方按"每件都买最低价"算成本，
而那个价位**只有一两件**，要凑 9 件必须往上一档买（实测 0.21 → 0.33 元）。

所以真正的优势不在"找到别人没看到的配方"（不存在），而在
**比别人更快更准地判断一份公开配方在 BUFF 上还能不能执行**：

```text
cs2up 不知道的事           我们知道的事
────────────────────       ────────────────────────────
那个磨损区间里有几件货      逐行读 data-asset-info.paintwear，数得出来
要凑齐 N 件的真实成本       按区间内的实际挂单算，而不是按最低价
7 天后产出卖多少钱          可以拿 K 线回测这个窗口的历史波动
```

**这三格就是"配方分析师"真正能创造价值的地方**——不是找配方，是算得出配方能不能落地。

### 50 块订阅的回本算术

不粉饰，直接算：

```text
订阅          50 元 / 月（到 2026-10-28）
每批利润      成本 × 真实 ROI
要回本        累计利润 = 50 元

若真实 ROI 约 20%  → 需要累计投入成本约 250 元
一个月约 4.3 个 7 天周期 → 每个周期要投入约 58 元
```

而目前三批合计投入是 `0.33 + 2.03 + 14.44 ≈ 17 元`，是要求的四分之一不到，
而且是**一个月里**要持续做到。

结论：**按现在的规模，订阅在纯财务上不可能回本。**
要么把它当学费/信息费，要么就必须把单批规模提到几十元档——
而那个档位直接撞上深度限制（便宜货区间里只有十件）。

这不是劝退，是把账摆在桌上：**它现在是这项目的成本项，不是收入项。**

### 阶段闭环（第一个里程碑）

**解决了什么**：从一份炼金配方走到 BUFF 上"筛选好、按价格升序"的页面，
全程不用手点筛选器。工具是 `recipe_ids.py`。

**现在真正理解了什么**：

- URL 的 `#` 后面不发给服务器，所以筛选页只能由浏览器执行（[[knowledge-base/02_kownledge/url-fragment|URL 的 # 后面是什么]]）
- 每个平台用自己的主键，跨平台要靠第三方维护的映射（[[knowledge-base/02_kownledge/cross-platform-item-ids|同一件饰品各平台的主键不一样]]）
- IP 白名单绑的是**出口地址**，不是设备；NAT 和 VPN 都会换掉它
- 配方是短时效的：版本一变，`detail_id` 指向的东西就变了
- 配方的 ROI 偏乐观：实测原料成本 0.21 → 0.30 元，ROI 103% → 42%

**产生了什么新问题**：

- 自动化程序要用哪份**登录态**？在哪台机器上跑？
- 「关注」按钮在页面里怎么被程序认出来、点下去怎么知道点成功了？
- 10 件怎么凑齐？关注不锁货，被抢走怎么补？

**下一步最重要的问题**：在哪儿跑、用哪份登录态。它决定了后面所有代码的形状。

### 换个问题：这个项目到底在练谁（2026-09-28）

问到这一句的时候，项目已经能一条命令跑完全程了，但提出了一句更扎心的话：
**「python 代码里涉及了很多我不懂的基础知识，我根本没提升过代码能力，一直在写提示词而已。」**

这个判断是对的，得承认：项目里的代码几乎全是 AI 写的。
人写的是**判断和需求**——否定按 ROI 挑配方、发现筛选链接其实没生效、
提出「要在网页上自己挑配方」、指出命令行不好用。这些都是工程判断，
但确实不等于会写代码。

**岔口在这**，而且是这次才被摆到台面上：

| 走法 | 项目推进 | 代码能力 |
| --- | --- | --- |
| 人提需求 → AI 写代码 → 人验收 | 快 | 不动 |
| 人先写 → AI 指缺口 + 验收 | 慢 | 才是人的 |

第一轮选的是第一条（没人明说，默认就滑过去了），所以「项目在长，人在原地」。
这不是工具的问题，是**协作方式从一开始就没定**。

学到的那点东西也是真的，只是它们不是语法：URL 的 `#` 不发给服务器、
白名单绑的是出口地址、配方有保质期、汇总指标要拿原始数据自己算一遍。
**这些是判断力的积累；缺的是把这些判断落到自己手指底下的那部分经验。**

所以接下来的动作不是"再学一门课"，而是把下一个功能交还给人写。
最小、最安全、反馈最快的起点是 `ui.py`——六十行，没有网络、没有业务逻辑，
改一个数字就能在列表里看见结果。
