# CS2 炼金配方的自动取材

## 来源

我想学 Web 安全、自动化、计算机基础和编程，但不知道从哪开始，硬啃教程又坚持不下去。

后来换了个做法：先定一个**真实目标**，让目标自己制造问题（纲要第 11 节）。
我选的目标是 CS2 炼金（汰换）的自动取材，因为这条链路上该遇到的问题基本都躲不掉：

```text
配方网站 → 读结构化数据 → 平台之间的主键映射 → 核对真实盘口 → 浏览器自动化 → 记账与复盘
```

四天做下来（2026-09-27 ~ 09-30），每一环都真实地撞过一遍。

## 它解决的问题

**我要做的事**：从 cs2up 读一份炼金配方，按配方在 BUFF 上把 10 件材料按指定磨损区间找出来，
加进收藏；之后由我自己付款、自己汰换。

**我给自己划的边界**：程序不付款、不下单、不碰汰换。它只负责「看」和「点」，
花不花钱由我决定。

做完之后才发现，更值得记的是另一点：cs2up 给的配方是按它自己的价源算的，
它不知道推荐的磨损区间里 BUFF 上到底有几件货、真实要花多少钱。
**所以这个工具真正回答的，是配方站自己回答不了的那个问题：这份配方在真实盘口上还能不能执行。**

## 当前理解

### 做出来的东西

```powershell
python src\shell.py        # 主入口：改条件、看列表、k 智能搜、t 进推荐、v/r 看详情/关注
python src\scan.py         # 批量可行性扫描（逐份去 BUFF 核对真实成本与深度）
python src\verify.py <id>  # 验价：产出的报价是不是真的、卖不卖得掉
python src\settle.py       # 把 lists/ 里的采购清单汇总成账本，回头看评分准不准
python src\budget.py 60    # 看在途和回款排期，算这几天每天能花多少
```

脚本都放在 `src/` 下平铺，数据文件（lists、reports、令牌、`.browser-profile`）留在项目根目录，
由 `src/paths.py` 一处算出根目录——所以脚本从哪个目录启动都能跑（见
[[knowledge-base/02_kownledge/script-paths-and-cwd|脚本的路径依赖]]）。
只用 Python 标准库，唯一的外部依赖是浏览器自动化需要的 playwright。
怎么装、怎么用、每个字段什么意思，都写在项目目录的 `README.md` 里，这里不重复。

### 这个项目让我弄明白的机制

每一条都来自一次具体的失败或核对，第三列写的是「当时是怎么知道的」。

| 机制 | 说明 | 怎么知道的 |
| --- | --- | --- |
| 配方有保质期 | `version` 是个时间戳，后端每隔几分钟重算一次；`detail_id` 只在同一版本内有效 | 同一个编号隔两小时指向了另一份配方，我踩了三次 |
| `#` 后面的参数不发给服务器 | 所以筛选页只能由真实浏览器执行，用 requests 请求拿到的是没筛选过的空壳 | 我用 requests 请求筛选链接，拿回了未筛选的列表 |
| 但筛选器也不能全信 | `min_paintwear` 需要页面带着 hash 加载才生效，中途一次登录跳转就丢了 | 保存下来的页面里第一行磨损是 0.346，而我要的是 0.15~0.18 |
| 页面本来就带结构化数据 | 每一行在售都有 `data-asset-info.paintwear`，不需要「看图」 | AI 翻页面 HTML 时找到的，从此改成逐行本地核对 |
| 各平台的主键不一样 | 同一件饰品：cs2up 用名字、CSQAQ 用 goodId、BUFF 用 buff_id | 拼链接时发现配方给的是名字，而 URL 要的是数字 |
| 买来的饰品有 7 天冷却 | 产物可以立刻上架，所以周期正好是 7 天，风险落在第 7 天的价格上 | 我实际买了才知道；这条把项目的性质改了一半 |
| 成本偏差跟价位有关 | 1~3 元档真实成本是配方价的 1.24~1.35 倍；14~16 元档接近 1.00 倍 | 两次扫描对比出来的 |
| 保本率对成本是悬崖函数 | 成本涨 28%，保本率可以从 94% 掉到 26% | 同一批配方，两个成本口径各算一遍 |
| 汇总指标可以自己算出来 | 保本率、倍数、期望都能从产物概率表算，和接口给的一致 | 程序按概率表算一遍，和接口返回的汇总字段对得上，从此不信汇总字段 |
| 四个指标其实只有两根轴 | 头号占比与 σ、倍数 的相关系数 0.96（冗余）；保本率与倍数 −0.71（同一根轴的两端） | 拿 25 份真实配方算相关系数 |
| σ/期望 决定「能不能学会」 | `n ≈ (1.96σ/E ÷ 0.1)²`：0.5 约 96 次（三周），4.65 约 8300 次（二十多年） | 想验证 ROI 时算出来的 |
| 手续费必须扣 | 不扣费的期望是虚的；扣到 5% 能把保本率从 100% 打到 75% | AI 后来补的，之前一直漏 |
| 公开信号会自我消解 | 配方广场是公开的，而便宜货的深度只有十件，越「绝佳」的消失得越快 | 实测 0.21 元的配方，真买要 0.33 |
| 三种「失败」要分开 | 429 是请求太快、409 是列表过期、403 才是真没权限 | 三种各踩一次；提示语写错会把注意力引到错的方向 |
| 现金只有一个来源：我填的那个数 | 程序看不到我提现、也看不到我在别处花钱，所以不许拿"已买/回款"去推现值。**只做一次减法**：每关注成功一份，就按清单里的真实成本扣掉这次的实付；**回款不自动加回来**（钱到没到、有没有提现只有我知道）。自填写后的买卖只作一句提醒 | AI 先后算错过两次：先拿余额减在途，又拿"已买/回款"去推现值，填 53 却显示 7.32；最后才定成"我填 + 下单时扣" |
| 记录里只留"以后还用得上"的 | 清单里每件材料的磨损和实付必须留（将来算产出磨损要用）；但「在售订单ID」是 BUFF 的临时在售单号，付款后失效、7 天后必查不到，所以只留在**关注失败**的行上——那时它是排错用的 | 我问"在售订单ID 是什么、有必要留吗"，AI 给出上面这条判断，于是清单瘦了一圈 |
| 文件名也能当状态用 | 文件名里的分隔符跟着**内容**走：填齐「汰换产出 + 售出」是 `…-1757x50282.md`，还欠着就是 `…-1757_50282.md`。不用打开文件，扫一眼列表就知道哪几份没结算 | 我提的需求；AI 把它做成"从内容推导"，所以手改清单在下次刷新时也会自动对齐，而不是只在下单流程里改一次 |
| 副作用的"落点"要跟它花没花钱一致 | 演练（只看不买）的结果也写在 `lists/` 里，标题写着"演练"，但账本只认**文件名**——于是它被当成一份真买过的记录，混进「该汰换了」；更糟的是演练和真跑同名同目录，同一分钟会互相覆盖（我有一份真跑就这么被盖成了演练） | 演练改写到 `tmp/dryrun_*.md`，并在解析层拦一道"标题带演练的不算账本"；我贴出那条 `w` 输出时才发现 |
| 约束要分软硬 | 「单份上限」是我希望的价，不是我能花的钱的极限；一份真实成本 ¥7.06、单份上限 ¥6、当天额度 ¥12 的配方，程序原本直接剔掉——它买得起，该由我决定要不要多花那一块。现在：超单份上限只扣分并标 ⚠，超过"今天总共能花多少"才剔 | 我贴出 k 的拒绝清单说"理由很肤浅"，AI 把这两种约束拆开 |
| 一批全不过关 ≠ 这档没货 | 候选池有 40 份，看一眼前 6 份就宣布"都不赚钱"不成立。现在一批全没过关会自动再拉一批（跳过已实测的，最多 3 批），到顶才下结论，而且**按类别**给原因（钱不够 9 份 / 不赚钱 3 份 / 凑不齐 2 份），不是甩 18 条"超预算" | 同一次反馈 |
| 会话状态和落盘状态必须是同一份 | 详情页里关注成功要扣现金，那里写的是 `spend(load_conf(), …)`：改的是**新读出来的**配置，主循环手里那份没动 → 下一次扣款按旧余额算，把上一次的扣款覆盖回去（21.4 买 5 → 文件 16.4，再买 3 → 文件 18.4，正确是 13.4）。修法：把会话里那份 conf 传进详情页 | 代码评审（`/review`）的另一个模型挑出来的，我复核后确认是真的 |
| 用不可信的数据做筛选，会把"可交给我判断"的候选也筛掉 | 预判分只用配方站报价，而低价档的报价偏差最大（真实成本 1.24~1.35 倍）——纸面上最漂亮的 6 份，一进浏览器核价就全线崩，三批都白跑；表现就是"k 又筛不出东西了"。现在：预判分按价位打可信折扣（低价档 ×0.75）、拉候选放宽到 1.5 倍、全不过关时先给"差一点"清单再问要不要用**已经核过价的数据**放宽重排（不用再开浏览器） | 我说"k 筛不出配方了、有点心灰意冷"，AI 顺着算下来定位到"预判分用了最不可信的那一档数据" |
| 真约束是滚动现金流 | 买进来的东西 7 天内不回血，所以「过去 7 天的支出」都还压着 | 我在对话里推出来，后来用 `budget.py` 量化 |
| 订阅只是「带不带令牌」 | cs2up 的订阅状态挂在 localStorage 的令牌上，请求带 `Bearer` 就行 | AI 读它前端代码发现的 |
| 判断「卖不卖得掉」要看求购 | CSQAQ 的 `turnover_number` 是 Steam 成交量、`period_at` 显示停在 2025 年底；BUFF 的求购单才是「能立刻脱手」的证据 | 我说「BUFF 页面只显示最近 10 单成交」，AI 去查字段才发现原来标错了 |
| 归零点要挑有意义的口径 | 单件产物算出来的归零价可能是负数，意思是其他产物已经盖住了成本，不是「跌到 ¥-0.46」；「所有产物一起跌 X%」这个口径永远有意义 | 我看到 `¥-0.46` 和 `inf` 去问，才把两种口径分开 |
| 时间尺度要跟持有周期匹配 | 我持有约 7 天，所以只看 14/30 天价格；半年前的价格对判断卖价没有意义 | 我自己定的，180 天那个数字看一次就删了 |
| 路径要从一处来 | 同一个「数据在项目根目录」的事实，如果写在十五个脚本里，改一次目录结构就有十五个出错点；收敛进 `paths.py` 后改动半径是 1 | 我想把脚本收进 `src/` 时，AI 指出这就是「路径从哪来」的问题 |
| 算收益的两端必须是同一个市场 | 买入端用 BUFF 实测成本、卖出端用 cs2up 报价，得出的 ROI 必然偏乐观；`y` 验价之所以每次都让推荐"掉价"，就是因为它才是第一个把卖出端换成 BUFF 现价的地方 | 我说「k 出来的配方经 y 一验就没说服力」，AI 去翻代码，确认两边口径不一致 |
| 求购单是「有人接」，不是「能卖到现价」 | 求购是挂在低位的买单；有它说明抽到就能立刻脱手，卖多少钱仍要看现价 | 我盯着 `8 单` 问这是什么意思 |
| 测试要能脱网跑 | 把联网的接口整段换成假数据，几毫秒就能验一条链路；否则每验一次都要花十几分钟和真实调用 | 改完智能搜的算分，AI 先用假数据跑通才敢交给我 |
| 顺序也是正确性的一部分 | 「核价 → 剔除 → 排序」少一步或换顺序，程序不会报错，只会安静地按旧口径算：结果是一份扣费后 ROI 为 −1% 的配方排在第一，还进了今天的采购建议 | 我看输出时发现"排第一的那份居然是负收益"，AI 去查才发现排序跑在核价前面，于是把三步封成了一个函数 |
| 微利等于噪声 | 买进到卖出隔着 7 天冷却，价格漂一两个点就把几个点的利润吃掉；所以智能筛的底线设成"扣费后 +5%"而不是 0 | AI 把底线写成一个常量 `MIN_ROI`，并说明改哪里 |
| 基准不同就是两个结论 | 同一份配方，"成本"按配方价算是 ¥4.84、按 BUFF 实测是 ¥5.60；基准换一下 ROI 就从 +26% 变成 +6%。所以每个数字旁边都得写清基准是什么 | 我看 kv 详情里的 ROI 和推荐表对不上，AI 查出两边基准不同 |
| 同一件事别查两遍 | 推荐时已经查过产价，详情又查一遍，两张表的时间点和数字都不一样，看起来像两个结论；把结果存下来重画，既省调用又不会自相矛盾 | 我提出"kv 和 y 是不是冗余了" |
| 控制台不是 Markdown | 在终端里写 `**加粗**`，看到的就是两个星号——渲染规则是渲染环境的，不是写法的 | 我的输出里出现了"所有产物价格 \*\*一起跌 17%\*\*"，用户指出来 |
| 一屏只回答一个问题 | 详情页原来把配方站口径、核价原始列、结论混在一屏，45 行里有 30 行和"买不买"无关 | 用户说"我只关心值不值采购"，于是压成两表一结论 |
| 一列里不能既放单价又放总额 | 材料表逐行是单价（0.35/0.35/0.37/0.43），合计行直接把单价相加得 ¥1.50，和乘过数量的 ¥3.72 一比，凭空多出"差额 −2.22"。**单位不同就不能相减**，哪怕它们并排放在同一列 | 我贴出表格问"合计一栏有误"，AI 才看出是单价和总额混在一列 |
| 情报中心是观点流 | 3930 条网名作者的行情、选品、收货情报，不可回测 | 订阅后我拉出来看的 |

### 我走过的弯路

| 时间 | 当时的做法或判断 | 结果 | 现在改成 |
| --- | --- | --- | --- |
| 09-27 | 以为要抓包、逆向 APP | 平台有官方付费 API，第一版根本不用逆 | 先问「有没有正规入口」 |
| 09-27 | 把官方 API 当主线 | 目标不需要程序花钱，整条路线作废 | 目标一变，路线要敢整个扔 |
| 09-28 | 把筛选链接当输入 | 参数在 `#` 后、还依赖页面状态 | 不信筛选器，逐行核对 |
| 09-28 | 把点关注失败当成「没权限」 | 其实是 HTTP 429，请求太快 | 失败要给出原因，不能只给结论 |
| 09-28 | 把 403 当成「配方被锁」 | 里面混着 409（列表过期） | 同名状态码在不同服务上含义不同 |
| 09-28 | 按 ROI 从高到低挑配方 | 高 ROI 全是靠一件过期报价撑起来的彩票 | 排序口径决定了你会看到什么 |
| 09-29 | 改成按「预期利润」排序 | 这个排序专门挑彩票 | 指标之间会共线，先去量相关系数 |
| 09-30 | 要求推荐必须当场操作 | 根因是推荐要算十几分钟，比版本寿命还长 | 把推荐连材料清单一起缓存 |
| 09-30 | 让程序推荐「最不亏的那份」 | 结果推了 5 份全是负收益的配方 | 没有合格项就是一个结论，不该被排序掩盖 |
| 09-30 | 界面标签写「30 天成交」，拿它判断卖不卖得掉 | 那个字段是 Steam 的成交量，还停在一年前 | 换成 BUFF 求购深度 |
| 10-04 | 归零价直接打印单件口径的结果 | 出现负价和 `inf`，看不出任何信息 | 先给「统一跌幅」，单件口径算不出意义就不显示 |
| 10-04 | 智能搜的收益一直按 cs2up 的产物报价算 | `k` 的 ROI 总比 `y` 好看，看一次 y 就不敢信这个推荐 | 推荐前把产出全换成 BUFF 现价，分数改用真实口径 |
| 10-04 | 改了口径，但没改顺序：先排序、后核价 | 分数和剔除仍按报价算，界面显示现价，出现"−1% 排第一" | 把「核价 → 剔除 → 排序」封进 `smart.select()`，顺序不再由调用方决定 |
| 10-04 | `v` 详情里还留着 `b 买料比价` | 同一份材料表看两遍（`v` 里一遍、`b` 里一遍），多按一次键、多一屏文案 | 把 BUFF 参考价并进材料表，撤掉 `b` |
| 10-05 | 表格直接交给终端排版 | 窗口一窄，续行就跑到行首，列全散了；条件编号 17 项挤成一条长龙 | 表格自己按终端宽度折行、先丢可省列；编号行分组、长句带缩进折行 |

### 健壮性现状

「健壮」不等于「不出错」，而是出错以后会怎样：能不能发现、会不会误报、重跑一次会不会更糟。
按这个标准盘一遍：

| 方面 | 现状 | 还差什么 |
| --- | --- | --- |
| 网络请求 | 网络层错误重试两次并退避；HTTP 状态码不重试，直接带着原因报出来 | 没有全局超时预算，批量跑遇到持续限速只能靠人看着 |
| 断点续跑 | `scan.py` 每扫完一份就落盘，可以 `--resume` 接着跑 | 智能搜的推荐只存在内存里，退出就没了（这是有意的：版本会变，缓存过期反而会误导） |
| 数据时效 | 配方带 `version`，过期就报 409 并提示重拉 | 会话期间版本变了，界面里的旧编号会指向别的配方，只能靠用户重跑 |
| 路径 | 收敛到 `paths.py`，脚本从任何目录启动都能找到数据 | 本地跑通了；复制到另一台机器还没试过 |
| 读清单 | 靠正则解析 markdown 清单 | 清单格式一改（比如我手写时漏了字段），只会少读一条，不报错 |
| 凭证 | 明文文件 + `.gitignore`，程序不做加密 | 没有过期提醒；令牌失效时表现为「查不到数据」，不是「令牌坏了」 |
| 页面结构 | 磨损和价格从 `data-asset-info` 里读，不依赖像素 | BUFF 改结构时，表现会是「一行都没读到」，而不是明确报错 |
| 状态操作 | 关注是幂等的：重复点不会重复关注，所以重跑安全 | 它仍然依赖页面上「已关注」的状态判断，改版后会误判 |
| 测试 | 有了第一个离线自测：把 CSQAQ 接口替换成假数据，几毫秒跑完，覆盖推荐里的产出核价 | 只有这一条链路有测试，其余功能仍旧靠手动跑一遍 |
