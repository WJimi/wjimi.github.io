# CS2 炼金配方的自动取材

## 来源

我想学 Web、自动化、编程基础，硬啃教程坚持不下去。
于是换个做法：**先定一个真实目标，让目标自己制造问题**（纲要第 11 节）。
目标选的是 CS2 炼金（汰换）的自动取材，因为这条链路上该踩的坑基本都在：

```text
配方网站 → 读结构化数据 → 跨平台主键映射 → 核对真实盘口 → 浏览器自动化 → 记账复盘
```

## 它解决的问题

从配方站读一份配方，按指定的磨损区间在 BUFF 上把 10 件材料找出来、加收藏。
付款和汰换我自己做：**程序不付款、不下单、不碰汰换。**

做完才发现更值得记的一点：配方站的价是它自己的口径。
它不知道那个区间里 BUFF 上到底有几件货、真买要多少钱。
**所以这个工具真正回答的是配方站回答不了的问题：这份配方在真实盘口上还执行得了吗。**

## 现在长什么样

```powershell
python src\shell.py       # 主入口：改条件 / 看列表 / k 智能搜 / t 进推荐 / v, r 看详情、关注
python src\scan.py        # 批量可行性扫描（逐份去 BUFF 核对真实成本与深度）
python src\verify.py <id> # 验价：产出的报价是不是真的、卖不卖得掉
python src\settle.py      # lists/ 里的采购清单汇总成账本，回头看评分准不准
python src\budget.py 60   # 看在途与回款排期，算这几天每天能花多少
```

脚本平铺在 `src/`，数据和登录态留在项目根目录，根目录由 `src/paths.py` 一处算出。
只用标准库，唯一外部依赖是 playwright。
字段含义和算法写在项目目录的 `README.md` 里，这里不重复。

## 这个项目让我弄明白的机制

每一条都来自一次真实的失败或核对。第三列是「当时怎么知道的」。

### 取数与口径

| 机制 | 说明 | 怎么知道的 |
| --- | --- | --- |
| 三个源是三种观测面，不是一份数据的三个副本 | 配方站给候选、CSQAQ 给跨平台价与历史、ECOSteam 给可执行的在售。用哪个数，先问它是谁在什么口径下产生的 | 拼链接时发现配方给的是名字，而 URL 要数字 |
| 汇总字段要自己算一遍 | 保本率、倍数、期望都能从产物概率表推出，且与接口汇总字段一致。之后不再信汇总字段 | 自己算一遍对得上 |
| 算收益的两端必须是同一个市场 | 买入用 BUFF 实测成本、卖出用配方站报价，ROI 必然偏乐观 | 详情核一次价，推荐就"掉价" |
| 基准不同就是两个结论 | 同一份配方成本按配方价 ¥4.84、按实测 ¥5.60，ROI 从 +26% 变 +6%。每个数字旁边都要写基准 | 详情页和推荐表的 ROI 对不上 |
| 一个档位一个价，不等于这件产物就值那个价 | 产物磨损是**分布**：同一件皮肤会落到相邻两档，而两档价常常差一倍。期望要按各档概率加权 | 本地算出"略有磨损 40% / 久经沙场 60%"，而配方站只按一档报价 |
| 缓存要分开对待 | 配方站的编号几分钟换一批，但**材料、产物构成与概率分布不变**——变的只是价格与区间。所以结构可长期留，价格必须限期 | 同一个编号隔两小时指向了另一份配方 |

### 时间与生命周期

| 机制 | 说明 | 怎么知道的 |
| --- | --- | --- |
| 配方有保质期 | `version` 是时间戳，后端每隔几分钟整体重算；编号只在同一版本内有效 | 编号指到别的配方，踩了三次 |
| 买来的饰品有 7 天冷却 | 产物可立刻上架，所以周期正好是 7 天，风险落在第 7 天的价格上 | 自己买了才知道，这条把项目性质改了一半 |
| 真约束是滚动现金流 | 买进来的东西 7 天不回血，过去 7 天的支出都还压着 | 对话里推出来，再用 `budget.py` 量化 |
| 时间尺度要跟持有周期匹配 | 我持有约 7 天，所以只看 14/30 天价格；半年前的价格对判断卖价没意义 | 180 天那个数字看一次就删了 |
| 机会是时效性的 | 便宜货深度只有十件，越"绝佳"的配方消失越快。于是有了守夜模式：每 N 分钟重新拉一轮、核价、记录 | 实测 0.21 元的配方真买要 0.33 |

### 工程与判定

| 机制 | 说明 | 怎么知道的 |
| --- | --- | --- |
| `#` 后面的参数不发给服务器 | 筛选页只能由真实浏览器执行；用 requests 请求拿到的是没筛选过的空壳 | 用 requests 请求筛选链接，拿回未筛选的列表 |
| 筛选器也不能全信 | `min_paintwear` 要页面带着 hash 加载才生效，一次登录跳转就丢 | 保存的页面里第一行磨损是 0.346，而我要 0.15~0.18 |
| 页面本来就带结构化数据 | 每行在售都有 `data-asset-info.paintwear`，不需要"看图"，按行本地核对更可靠 | 翻页面 HTML 时找到的 |
| 失败要给出原因 | 429 是请求太快、409 是列表过期、403 才是真没权限。提示写错会把注意力引向错的方向 | 三种各踩一次 |
| 顺序也是正确性的一部分 | 「核价 → 剔除 → 排序」换顺序不会报错，只会安静地按旧口径算，于是出现"扣费后 −1% 排第一" | 看输出发现"排第一的居然是负收益" |
| 单位不同不能相减 | 材料表逐行是单价，合计行直接把单价相加，和乘过数量的总额一比就多出"差额 −2.22" | 我贴出表格问"合计栏有误" |
| 约束要分软硬 | "单份上限"是我希望的价，不是我能花的极限。超上限只扣分并标注，超"今天总共能花多少"才剔 | 我贴出拒绝清单说"理由很肤浅" |
| 一批全不过关 ≠ 这档没货 | 一批全没过关要自动再拉一批（跳过已实测的，最多 3 批），并按类别给原因，不是甩 18 条"超预算" | 同一次反馈 |
| 用最不可信的数据做筛选，会把可判断的候选也筛掉 | 预判分只用配方站报价，低价档偏差最大，纸面最漂亮的 6 份进浏览器全崩 | 我说"k 筛不出配方了"，顺着算下来才定位到 |
| 会话状态和落盘状态必须是同一份 | 详情页扣现金改的是**新读出来的**配置，主循环手里那份没动 → 下次扣款覆盖上一次 | 代码评审挑出来，复核确认是真的 |
| 离散网格要用格心，不是左边界 | 按格子左边界取值，每件材料少算半格；格子粗、产物又压在档位分界上时会偏几个百分点——而取价是按档位质量加权的 | 构造"压在 0.15 分界上"的算例，本应 50/50 算成 56/44 |
| 平均要按件，不是按行 | 配方里一行带 `count`（`9 + 1` 很常见），分母必须是 10——按行平均把 0.177 算成 0.224，产物直接跨档 | 用它算出的档位和配方站报的对不上 |
| 跨源名字的空白也是身份 | 配方站写 `USP消音版`、CSQAQ 写 `USP 消音版`，一个空格让同一款变成两个键，整款皮肤的档位价都查不到 | 第一次真跑就撞上：输出写着"搜不到全套档位" |
| 控制台不是 Markdown | 终端里写 `**加粗**`，看到的就是两个星号——渲染规则属于渲染环境 | 我的输出里出现了 `**一起跌 17%**` |

## 走过的弯路

| 当时 | 做法 | 现在改成 |
| --- | --- | --- |
| 09-27 | 以为要抓包、逆向 APP | 先问「有没有正规入口」——对面有官方 API |
| 09-27 | 把官方 API 当主线 | 目标一变（程序不替人花钱），路线整个扔，不留恋沉没成本 |
| 09-28 | 按 ROI 从高到低挑配方 | 排序口径决定你看到什么：高 ROI 全是靠一件过期报价撑起的彩票 |
| 09-29 | 改成按"预期利润"排序 | 指标会共线，先去量相关系数再决定用哪个 |
| 09-30 | 拿"30 天成交"判断卖不卖得掉 | 那字段是 Steam 成交量且停在一年前；换成 BUFF 求购深度 |
| 10-04 | 改了口径却没改顺序（先排序后核价） | 把「核价 → 剔除 → 排序」封成一个函数，顺序不再由调用方决定 |
| 10-13 | 把浏览器窗口挪到屏幕外来避免挡视线 | 任务栏只剩缩略图，点不开也关不掉，还占着登录配置让后面全报错。改成**最小化**打开 |

## 健壮性现状

「健壮」不是不出错，而是出错之后会怎样：能不能发现、会不会误报、重跑会不会更糟。

| 方面 | 现状 | 还差什么 |
| --- | --- | --- |
| 网络请求 | 网络层错误退避重试；HTTP 状态码不重试，直接带原因报出来 | 没有全局超时预算，持续限速时只能靠人看着 |
| 数据时效 | 配方带 `version`，过期就报错并提示重拉；推荐连材料清单一起缓存 | 会话期间版本变了，旧编号会指向别的配方，得重跑 |
| 读清单 | 靠正则解析 markdown 清单 | 清单格式一改（手写漏字段）只会少读一条，不报错 |
| 凭证 | 明文文件 + `.gitignore`，登录态同理（曾误提交过 303 个浏览器文件，已从索引摘掉） | 没有过期提醒；令牌失效表现为"查不到数据" |
| 页面结构 | 磨损和价格从结构化数据读，不依赖像素 | 站点改版时表现为"一行都没读到"，不是明确报错 |
| 测试 | 三套自检：离线单元测试、合规自检、引用自检（文档提到的路径必须真存在） | 浏览器那几步只能真跑，脱网测不了 |

## 实践

**被放弃的路线**：官方开发者 API。它解决的是"程序替我花钱"，而目标变成了
"程序帮我找、我自己花钱"，所以退出主线。留着的原因：以后想拿每件的确切 float 时，
`/api/market/enterprise/goods/sell_order` 是唯一的正规途径（5 秒更新，仅企业 API）。
离线副本在项目目录的 `docs/buff_openapi.json`。

**这次学习的闭环**

解决了什么：从"想学技术但不知道学什么"，变成一条能跑完的链路——
配方 → 采购条件 → 真实盘口核对 → 关注 → 我付款 → 记账。

真正理解了：上面那些机制。其中最跨界的三条是「汇总指标要自己算一遍」
「约束往往不在我以为的那个维度上」「失败要给出原因」。

下一步最重要的问题：把采购清单的结果填回去。否则前面所有"智能"都只是信念，不是知识。
