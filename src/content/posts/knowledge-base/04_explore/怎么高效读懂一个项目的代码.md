# 怎么高效读懂一个项目的代码

## 来源

做 [[knowledge-base/03_projects/automation/tradeup-material-sourcing|CS2 炼金配方的自动取材]] 时，
项目一直在长，代码却全是 AI 写的。想自己动手改，第一步就卡住：
**打开文件夹，十几个 `.py`，不知道从哪一行开始看。**

这件事不只是这个项目的问题——它更像一个通用技能：面对一个自己没写过的项目
（或者三个月前自己写的），怎么在不逐行读完的前提下，达到"能改"的程度。

整条线暂时不推进项目，所以放进待探索。

## 它解决的问题

> 代码能跑，但不是我写的。想改，却不知道从哪一段下手；
> 硬着头皮从头读，读了三页就失去上下文。

和 [[knowledge-base/04_explore/python-syntax-for-reading-scripts|读懂 Python 脚本需要的语法点]] 是一对：
那篇补的是**语法**（这个符号什么意思），这篇补的是**方法**（先看哪、再看哪、怎么算读懂）。

**2026-10-04 更新：项目里已经有一张现成的地图了**，门槛比之前低很多——
`C:\wbog\buff-trade\README.md` 第十节《代码地图》里有：

```text
每个文件干什么、import 谁、碰哪些数据（一张表）
一张分层关联图（谁在下面、谁在上面）
两条最值得先看懂的调用链
"第一次读代码就做这三件事"的三步
读之前要会的 Python 语法，每条都指到项目里的真实函数
```

所以这篇笔记的正确用法是：**先照着那张表找到"最下面一层"的函数，再回来用下面的方法往下读**。
不要再从"打开文件夹，十几个 .py，不知道从哪开始"这一步开始。

## 当前理解

### 一、从"入口"进，不要从"第一个文件"进

程序的入口通常只有一两个：

```text
if __name__ == "__main__":     →  main()     →  它调的第一个函数
```

沿着**调用链**读下去：入口 → 主流程 → 主流程调用的函数 → 再下一层。
按文件名的字母序读（`budget.py`、`cs2up_login.py`…）是最没效率的读法——
读到第五个文件时，你已经不知道它在服务谁了。

但入口只解决"方向"，不解决"从哪个函数下手"。**先按依赖分层再选点**更省力：
项目里 `paths.py` / `ui.py` / `ledger.py` 不联网、不碰浏览器，是最好读的一层；
`focus_buy.py` / `shell.py` 在另一头，跑一次一分多钟，出错了最难定位。
细节见项目 README 第十节的关联图。

### 二、先问"数据长什么样"，再读代码

最省力的切入点是**数据结构**，不是函数体。

在一个程序里，绝大多数函数只是"把一种结构的数据变成另一种"。所以先把几个关键结构问清楚：

```text
一份配方（recipe）字段里有什么？      → inputs[] / outputs[]，每个 input 有 bin_lo/bin_hi
BUFF 页面上的一行在代码里长什么样？    → tr[data-asset-info]，里面有 paintwear
采购清单里有什么？                    → 生成时间 / 合计 / 售出 / 汰换产出
```

**看清两三个结构，一半的代码就不用逐行读了。**反之，不知道数据长什么样时读函数，
看到的全是 `dict["xxx"]`，什么都记不住。

### 三、按"谁调用谁"画一条小链，不用画全

不要画整个项目的地图，只画**你要改的那条链**：

```text
shell 里按 k  →  smart.discover  →  scan.scan_plans  →  focus_buy.run_material
```

四个名字，就够解释"按一下 k 之后发生了什么"。链条画出来，改动就不会牵一发动全身。

### 四、跑起来、改一处、看结果——比读十遍有用

理解代码最快的手段是**制造一次可观测的变化**：

```text
把某个数字改掉 → 跑 → 输出变了吗 → 那你就知道那一行在干什么
```

进阶：在关键位置插 `print(type(x), x)`，看**真实的数据**长什么样。
猜结构是最容易出错的一步——比如我一直以为 CSQAQ 的 `sell_price_30` 是"30 天前的价格"，
后来打出来看才发现是"相对 30 天前的涨跌额"。

### 五、优先读"纯函数"，最后读"有副作用的"

| 类型 | 例子 | 好不好读 |
| --- | --- | --- |
| 纯函数：不联网、不操作界面，输入输出确定 | `ui.bar()`、`smart.pack()`、`pearson()` | **最好读**：改错了立刻看得见，不牵连别的东西 |
| 只读外部数据 | `parse_lists()`、`metrics()` | 较好：能自己造输入来试 |
| 有副作用 | `focus_buy`（会开浏览器、会点东西） | 最难：跑一次一分半，出错了不知道错在哪 |

**所以起点应该选纯函数。**这也是为什么练习材料里把它排在最前面。

### 六、找"名字最长的"和"被调用最多的"

- **名字很长的函数**通常说明它承担了好几件事——理解它能拿到最多信息，
  也最可能从中拆出可以单独理解的小块。
- **被调用最多的函数**一般就是整个项目的核心概念（这里是 `get_json` 和 `metrics`）。
- 反过来，**只被调用一次的小函数可以先跳过**。

### 七、"读懂"的验收标准不是"能看懂"

```text
陌生  →  知道名字  →  能解释  →  能改  →  能重写  →  能排错
```

"看得懂"是幻觉——眼睛跟着字走一遍，合上文件什么都留不下。
**能删掉它、自己从空文件写回来、跑起来结果一样**，才算这一格过了。

但别一上来重写整个项目：**重写最小可测单元**，纯函数优先。

### 八、这种时候 AI 该怎么用

错误用法是"这段代码是什么意思"——那是让 AI 替你读，读完你还是不会。

正确用法是让 AI 指出**缺口**：

```text
我理解成这样：……，对吗？
要改这里，我必须先弄懂哪一行？为什么是它？
这个函数如果删掉，谁会坏？
```

对应纲要第 14 节：AI 是问题拆解器和缺口发现器，不是答案机器。

### 练习材料（就在本项目的代码里）

选材标准：短、不依赖外部、背后有一个真概念、改错立刻能看出来。
行号会随代码变化，**按函数名找**。项目一共十六个 `.py`（2026-10-04 的规模），
但真正值得动手的还是下面这些——**新增的多半是"把已有函数组合一遍"**。

**第一档：纯函数，改一个数就有反馈**

| 片段 | 在哪 | 学什么 | 为什么从它开始 |
| --- | --- | --- | --- |
| `bar()` | `ui.py` | 默认参数、条件分支、字符串乘法 | 全项目唯一"改个数字立刻看到画面变化"的地方 |
| `pad()` / `dwidth()` | `ui.py` | 为什么中文在终端占两格；遍历字符串 | 解释了一个真实 bug：中文列永远对不齐 |
| `wear_tier()` | `ui.py` | 元组列表 + 循环里提前 `return` | 把一张对照表写成代码的最朴素形态 |
| `pack()` | `smart.py` | **贪心算法**（最简单的背包） | 十行解决"今天的钱装得下哪几份"，是算法不是代码 |
| `pearson()` | `ledger.py` | 相关系数：公式 → 循环 | 一个真实统计量，十行；原来 settle 和 scorecard 各抄了一份 |

**第二档：能自己造输入试**

| 片段 | 在哪 | 学什么 |
| --- | --- | --- |
| `metrics()` | `smart.py:43` | 用字典存结构化结果、`sum` 与生成器表达式 |
| `trust()` / `prescore()` / `score()` | `smart.py` | 把"判断"拆成可测试的小函数 |
| `checks()` | `scan.py:230` | **生成器**（`yield`），以及它和"返回列表"的区别 |
| `read_all()` | `ledger.py` | 正则解析文本 + 时间计算（清单的格式只在这一处解析） |
| `for_storage()` | `ledger.py` | 为什么要挑字段再写进 JSON（datetime 存不下） |

**第三档：工程结构（要连着数据一起看）**

| 片段 | 在哪 | 学什么 |
| --- | --- | --- |
| `get_json()` | `recipe_ids.py:93` | HTTP 请求、**重试**、错误分类与提示（为什么 409 和 403 要分开） |
| `safe_goto()` | `focus_buy.py:145` | 异常处理与退避重试："一次网络抖动不该弄死整轮" |
| `READ_ROWS_JS` | `focus_buy.py:49` | 用 JS 在浏览器里读 DOM，再把结果传回 Python |
| 主循环 | `shell.py main()` | 状态机：`view` / `picks` / `scores` / `scan_results` 各代表什么 |
| `call_retry()` | `verify.py` | "重试期间不刷屏"——为什么失败信息也得挑时机打 |
| `refresh()` | `settle.py` | 把"读一堆 markdown"和"打印给人看"拆开：前者给程序用，后者给人看 |

**为什么这份清单没有变长**：项目收尾时又加了六个脚本
（`smart.py` / `verify.py` / `settle.py` / `budget.py` / `scorecard.py` / `cs2up_login.py`），
但真正值得动手的还是上面这些——**新增的多半是"把已有函数组合一遍"**。
这本身就是一条经验：**看懂少数几个核心函数，比看懂全部文件更有用。**
