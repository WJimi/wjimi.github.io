# 问题驱动知识系统

> **不是先学知识，再寻找用途。**
> 
> **而是从真实目标出发，提出问题，在解决问题的过程中构建知识。**

---

# 1. 核心思想

本系统用于长期学习计算机、IT、网络安全及相关领域。

不把学习理解为：

```text
课程 → 知识点 → 背诵 → 考试
```

而理解为：

```text
目标
 ↓
问题
 ↓
探索
 ↓
发现知识
 ↓
解决问题
 ↓
产生新问题
 ↓
连接已有知识
 ↓
形成知识体系
```

学习不是沿着一条固定道路前进，而是在不断构建一张**问题驱动的知识图谱**。

---

# 2. 第一性原理

遇到任何新技术、新概念、新工具，优先追问：

```text
它解决什么问题？
为什么需要它？
它的基本机制是什么？
它输入什么？
它输出什么？
它和已有的什么东西有关？
如果没有它，会发生什么？
```

不要首先问：

```text
这个东西怎么背？
这个工具有哪些参数？
别人一般怎么学？
```

---

# 3. 学习的最小单位：问题

本系统的基本单位不是“知识点”，而是**待解决的问题**。

例如不要从：

```text
HTTP
```

开始学习。

而从：

```text
为什么浏览器能够访问网站？
```

开始。

解决过程中自然出现：

```text
DNS
IP
TCP
HTTP
Request
Response
Cookie
Session
API
```

术语因此成为**问题解决过程中对某种机制的命名**。

原则：

> **先理解问题，再理解术语；先理解机制，再记住名称。**

---

# 4. 学习路线不是线，而是图

不要设计一条严格线性的：

```text
A → B → C → D → E
```

而采用：

```text
        B
       ↗
A → C → D
       ↘
        E
```

允许：

- 跳跃
    
- 回头
    
- 分支
    
- 汇合
    
- 插入新目标
    
- 暂停某个问题
    
- 返回以前的知识
    

**回到旧知识不是退步，而是新问题暴露了旧知识的缺口。**

---

# 5. 板块只负责提供骨架

可以存在：

```text
Python
Linux
计算机网络
HTTP
Web
数据库
自动化
Web安全
逆向
Docker
CTF
```

但板块不是课程表。

板块的作用是：

> **帮助问题定位和建立知识之间的关系。**

问题才决定实际学习顺序。

---

# 6. 目标可以随时插入

长期学习过程中一定会不断出现新目标。

例如：

```text
Web安全
```

突然加入：

```text
我要参加 CTF Web
```

不需要重新规划整条路线。

直接：

```text
新目标
 ↓
拆成问题
 ↓
寻找已有知识
 ↓
发现知识缺口
 ↓
补最小缺口
 ↓
继续解决目标
```

例如：

```text
CTF Web
 ↓
PHP反序列化
 ↓
发现不会PHP对象
 ↓
学习PHP对象
 ↓
发现不会Cookie / Session
 ↓
回到HTTP
 ↓
解决缺口
 ↓
返回CTF
```

**现实目标拥有修改学习路线的权力。**

---

# 7. 每个新问题进入系统前，问四件事

## ① 为什么现在出现？

它来自：

- 当前目标？
    
- 项目？
    
- 实际工作？
    
- CTF？
    
- 好奇心？
    
- 前置知识缺口？
    

## ② 它依赖什么？

寻找最小前置知识。

不要为了学一个问题，把整个领域从头学完。

## ③ 它连接什么？

寻找它与已有知识的关系。

## ④ 它现在必须解决吗？

如果不影响当前目标：

```text
记录
 ↓
标记为待探索
 ↓
继续当前任务
```

**不是所有问题都必须立即解决。**

---

# 8. 问题状态

每个问题至少属于以下一种状态：

```text
🔴 当前问题
正在解决。

🟡 前置问题
不解决它，当前问题无法继续。

🟢 已解决
已经能够理解并实际使用。

⚪ 待探索
有价值，但当前不是必要条件。

⏸ 暂停
暂时停止，未来恢复。

🔵 新问题
由当前问题解决过程中自然产生。
```

---

# 9. 当前目标 > 当前问题 > 知识

任何时候只维持一个主要焦点：

```text
🎯 当前目标
        ↓
🔴 当前问题
        ↓
🟡 必要前置问题
        ↓
🟢 已掌握知识
        ↓
🔵 新问题
```

避免同时打开几十个学习方向。

允许知识树很大，但**当前注意力必须很小**。

---

# 10. 知识笔记的原则

知识笔记不是教材。

不要追求：

```text
完整
漂亮
百科全书
```

而应该记录：

```text
我为什么知道它？
它解决什么问题？
它到底是什么？
它如何工作？
我在哪里用到了它？
它和什么东西有关？
```

例如：

```markdown
# HTTP

## 来源
解决 [[为什么浏览器能够访问网站？]] 时产生。

## 它解决的问题
……

## 当前理解
……

## 相关问题
- [[GET和POST为什么不同？]]
- [[HTTP请求由什么组成？]]
- [[Cookie是什么？]]

## 实践
……
```

---

# 11. 项目是知识系统的发动机

学习不要只靠人为安排。

使用真实项目不断制造问题。

例如：

```text
APP自动化
    ↓
Python
    ↓
HTTP
    ↓
API
    ↓
JSON
    ↓
Cookie / Token
    ↓
Linux
    ↓
日志
    ↓
自动化系统
```

另一个项目：

```text
CTF Web
    ↓
HTTP
    ↓
PHP
    ↓
SQL
    ↓
XSS
    ↓
反序列化
    ↓
RCE
```

不同项目会经过同一批基础知识。

这些重复出现的节点，就是**真正重要的基础设施**。

---

# 12. 项目优先于假想学习

如果：

```text
看教程
```

和：

```text
解决真实问题
```

发生冲突，优先解决真实问题。

因为真实问题会告诉你：

```text
我真正缺什么？
```

而不是：

```text
别人认为我应该学什么？
```

---

# 13. 学习不是“学完”，而是“能够使用”

一个知识什么时候算掌握？

不是：

> 我看过。

而是至少能够：

```text
解释
 +
识别
 +
使用
 +
排错
```

进一步：

```text
理解机制
 ↓
能够迁移
 ↓
遇到新问题仍能推导
```

最高层级不是记住答案，而是能够**重新推导答案**。

---

# 14. AI在系统中的角色

AI不是：

```text
答案机器
```

而是：

```text
问题拆解器
知识地图维护者
前置依赖发现器
解释器
提问者
代码辅助者
复盘助手
```

正确使用方式：

```text
我遇到问题
 ↓
自己先思考
 ↓
告诉AI当前理解
 ↓
让AI指出缺口
 ↓
继续追问
 ↓
自己重新解释
 ↓
记录到Obsidian
```

不要把：

```text
AI告诉我的答案
```

直接等同于：

```text
我已经掌握的知识
```

---

# 15. AI提出问题时的原则

问题必须：

- 从当前认知出发
    
- 不要求大量未知术语作为前置条件
    
- 能通过当前问题逐步产生新术语
    
- 尽量连接已有知识
    
- 难度逐渐增加
    
- 必要时允许跨板块
    
- 不强迫严格线性学习
    

问题应该让人产生：

> “我不知道，但我想知道为什么。”

而不是：

> “这一堆名词我一个都没见过。”

---

# 16. 第一性原理式提问

遇到复杂概念，不直接接受抽象定义。

不断向下追问：

```text
它是什么？
 ↓
它解决什么问题？
 ↓
为什么需要？
 ↓
它由什么组成？
 ↓
各部分如何协作？
 ↓
输入是什么？
 ↓
输出是什么？
 ↓
中间发生什么？
 ↓
如果改变输入会怎样？
 ↓
如果去掉某部分会怎样？
```

直到能够用更基础的机制解释它。

---

# 17. 从“操纵”逐渐走向“理解”

计算机学习可以不断深入：

```text
使用程序
 ↓
自动操作程序
 ↓
观察程序
 ↓
分析程序
 ↓
修改程序行为
 ↓
理解程序内部机制
```

例如：

```text
网页
 ↓
浏览器操作
 ↓
HTTP请求
 ↓
API
 ↓
JavaScript
 ↓
后端
 ↓
数据库
 ↓
程序运行
 ↓
程序分析
 ↓
安全边界
```

最终目标不是掌握某个工具，而是建立：

> **观察 → 理解 → 控制 → 推导**

的能力。

---

# 18. 防止知识图谱失控

知识图谱可以无限增长，但学习资源和注意力有限。

因此始终区分：

```text
重要 ≠ 现在必须学
```

新问题优先级可以简单判断：

```text
当前目标是否需要？
        ↓
      是 → 立即解决
      否
        ↓
是否是重要基础？
        ↓
      是 → 安排
      否
        ↓
是否有长期价值？
        ↓
      是 → 待探索
      否 → 暂不处理
```

---

# 19. 防止“工具崇拜”

不要因为：

```text
Appium
Burp
Playwright
Docker
Ghidra
Frida
Codex
```

而学习工具本身。

始终追问：

> **这个工具让我能够观察或控制什么？**

工具会变化。

底层问题不会轻易变化：

```text
输入
 ↓
处理
 ↓
输出

数据
 ↓
程序
 ↓
系统

用户
 ↓
程序
 ↓
权限
 ↓
资源
```

---

# 20. 知识连接原则

任何重要知识至少尝试连接：

```text
它的前置知识
+
它解决的问题
+
它产生的新问题
+
它可以应用的项目
```

例如：

```text
HTTP
├── 前置：网络
├── 解决：程序之间的Web通信
├── 应用：API / 自动化
├── 安全：请求篡改 / 身份认证
└── 新问题：Cookie / Session / Token
```

知识节点越能连接不同领域，长期价值通常越高。

---

# 21. 学习状态不是“完成/未完成”

一个问题可以处于：

```text
陌生
 ↓
知道名字
 ↓
能解释
 ↓
能使用
 ↓
能排错
 ↓
能迁移
 ↓
能教别人
 ↓
能从原理推导
```

不要因为“学过”就认为已经掌握。

---

# 22. 每次学习结束只做一次闭环

不需要写长总结。

只回答：

```text
今天解决了什么问题？

我现在真正理解了什么？

产生了什么新问题？

下一步最重要的问题是什么？
```

然后停止。

# 24. 最终原则

### 原则一

> **问题驱动知识，而不是知识驱动问题。**

### 原则二

> **目标可以改变路线，路线不能限制目标。**

### 原则三

> **允许非线性，但必须保持连接。**

### 原则四

> **术语是对机制的命名，不是学习的起点。**

### 原则五

> **真实项目负责制造问题。**

### 原则六

> **只补当前真正需要的最小知识缺口。**

### 原则七

> **不会因为回头补基础而认为自己退步。**

### 原则八

> **不要追求“学完”，追求“能够解释、使用、排错、迁移”。**

### 原则九

> **AI负责辅助构建问题网络，人负责思考、判断和实践。**

### 原则十

> **永远从“它为什么存在”开始，而不是从“它怎么背”开始。**

# 26. 一条最重要的使用规则

以后打开 Obsidian，不要问：

> **“今天应该学什么？”**

而问：

> **“我现在要解决什么问题？”**

如果没有问题：

> 找一个真实目标。

如果目标太大：

> 把它拆成问题。

如果问题太难：

> 找前置缺口。

如果遇到新知识：

> 把它连接回问题。

如果产生新问题：

> 加入图谱。

如果发现暂时没必要：

> 放入待探索。

然后继续。

---

# 27. 系统最终追求的能力

不是：

```text
记住越来越多的知识
```

而是：

```text
遇到未知
   ↓
不慌
   ↓
拆解问题
   ↓
找到基本机制
   ↓
建立连接
   ↓
实验验证
   ↓
解决问题
   ↓
继续向未知推进
```

**真正的终点不是“知道很多”。**

而是：

> **面对一个完全陌生的计算机问题，也知道应该从哪里开始。**
