# 第十届强网杯线上赛 Web 题《ezcms》分析

> 面向新手的题目拆解 + 学习指南
>
> 靶场：`nc 39.107.224.246 26629`（实际是 HTTP 服务，用 `curl http://39.107.224.246:26629/` 更方便）
>
> 前提说明：比赛已经结束，目标为已授权靶场。本文**不以拿 flag 为目标**，而是把这道题当成一个学习样本。作者没有在本轮分析中拿到 flag；下面所有“结论”都来自黑盒观察，**未验证的部分会明确标注“推测”**。请勿把本文当作官方 WP。

## 0. 先给结论

### 这题好不好？

**作为教学样本：质量不错。**

它不是一个“单点漏洞、一条 payload 打完收工”的题，而是一个缩小版的真实 CMS：

- 有注册、登录、退出、发文、文章详情、搜索、团队页、公开 API；
- 有独立的后台登录、后台页面和登录锁定；
- 有一个全局输入过滤器（WAF），会拦截常见 SQL 注入关键字和特殊字符；
- 使用 Java / Spring Boot / Tomcat / Thymeleaf 这一套真实技术栈；
- 页面和接口不多，信息量可控，适合讲“怎么从零开始看一个 Web 应用”。

### 值不值得新手钻研？

**值得，但不建议作为“第一道独立题”。**

更准确的定位是：

- 如果你已经学过 HTTP、表单、Cookie/Session、SQL 基础，想第一次认真做一道 Java Web 题：**很适合**。
- 如果你完全没接触过 Web，连“请求/响应/状态码”都还不熟：**会非常挫败**，建议先做完 PortSwigger Web Security Academy 的基础章节，或者跟着 WP 走一遍。
- 如果你只想要一个“背 payload 就能过”的题：**不适合**，这题的过滤器会让常见 payload 全部报错。

### 主观评分（仅供参考）

| 维度 | 分数 | 说明 |
|---|---|---|
| 题目设计 | 8/10 | 有真实 CMS 的味道，层次清楚，没有为了难而难 |
| 新手友好度 | 5/10 | 入口不明显，WAF 会打击信心，后台是黑盒 |
| 学习价值 | 9/10 | 能同时学到 HTTP、会话、认证、参数化、WAF、Spring 指纹 |
| 推荐方式 | —— | **配合 WP / 导师 / 队友一起做**，不要一个人硬啃 |

## 1. 零基础也能看懂：这道题到底在考什么

这一节假设你**完全没做过 CTF**，也没系统学过 Web 安全。我们不讲 payload，先建立直觉。

### 1.1 把网站想成一家店

你打开浏览器访问一个网站，本质上是：

1. 你（浏览器）写一张“点单纸”，送到店里（服务器）；
2. 店里的厨师（后端程序）看单子，去仓库（数据库）取东西；
3. 厨师把做好的菜（HTML 页面）端回来；
4. 浏览器把菜摆盘（渲染页面）给你看。

在本题里：

- “菜单”是首页、搜索、团队页、登录、注册、发文；
- “仓库”是数据库，存用户和文章；
- “员工通道”是 `/admin` 后台，需要额外密码；
- “门口保安”是一个全局过滤器（WAF），会检查你带进来的字符。

题目让你做的事，本质上就是：

> 在不知道厨房内部结构的情况下，通过不断点单、观察上菜方式，找出“保安没看住的地方”或者“员工通道的钥匙”，最终拿到放在后厨的 flag。

### 1.2 一次请求的一生

你在浏览器地址栏输入：

```text
http://39.107.224.246:26629/search?q=hello
```

浏览器实际发出去的东西大概长这样：

```http
GET /search?q=hello HTTP/1.1
Host: 39.107.224.246:26629
User-Agent: ...
Accept: text/html
Cookie: JSESSIONID=...
```

服务器回给你：

```http
HTTP/1.1 200
Content-Type: text/html;charset=UTF-8

<!DOCTYPE html>
<html>...
```

你要学会读三样东西：

1. **请求行**：方法（GET/POST）、路径、参数；
2. **请求头**：Cookie、Content-Type、Referer 等；
3. **响应**：状态码、响应头（尤其是 `Set-Cookie`、`Location`）、响应体。

### 1.3 Cookie 和 Session：网站怎么记住“你是谁”

HTTP 本身是“失忆”的：每个请求都是独立的，服务器不会天然记得你上一秒来过。

所以网站用了两个东西：

- **Cookie**：浏览器保存的一小段字符串，每次请求自动带上；
- **Session**：服务器端保存的“小本子”，Cookie 里通常只放一个编号（`JSESSIONID`）。

本题的登录流程就是一个标准例子：

```http
POST /login
Content-Type: application/x-www-form-urlencoded

username=tester02&password=Passw0rd123
```

登录成功后服务器回：

```http
HTTP/1.1 302
Set-Cookie: JSESSIONID=xxxxx; Path=/; HttpOnly
Location: /;jsessionid=xxxxx
```

之后浏览器再访问任何页面，都会自动带上：

```http
Cookie: JSESSIONID=xxxxx
```

服务器拿着这个编号去“小本子”里查：哦，这是 tester02，已登录。

**新手要养成的习惯：**

- 不要只看页面长什么样，要看“请求和响应”；
- 登录前后对比 Cookie；
- 退出登录后看 Cookie 是否失效；
- 看到 `302 + Location`，要知道这是“服务器让你去另一个地址”。

### 1.4 前台、后台、WAF：本题的三个世界

本题可以粗分成三块：

| 区域 | 例子 | 说明 |
|---|---|---|
| 前台公开区 | `/`、`/search`、`/team`、`/article/1` | 不登录也能看 |
| 前台登录区 | `/login`、`/register`、`/compose` | 注册/登录后可以发文 |
| 后台区 | `/admin/login`、`/admin/dashboard`、`/admin/media` | 独立登录，普通用户进不去 |
| 保安 | 全局参数过滤器 | 拦截 `; < > ~ OR AND ...` 等字符 |

这题的关键直觉是：

> **前台能做的事很有限，真正有价值的东西大概率在后台。**
>
> 但后台不是“绕过登录框”这么简单：它有独立的账号体系、登录失败锁定，还有一层全局过滤器。

### 1.5 题目可能的目标（推测）

根据页面文案和后台结构，比较合理的猜测是：

- flag 在后台页面（如 dashboard）或后台的媒体库/文件读取功能里；
- 想拿到它，需要一条“从普通用户到后台”的利用链，而不是单个 payload；
- 也可能存在一个我们没测到的、未被参数化的 SQL 注入点，需要用 WAF 绕过技巧打进去。

**再次强调：这些是推测，不是已确认的答案。**

## 2. 新手需要的最小知识清单

下面这些是“做这道题之前最好会”的内容。不会也没关系，可以边做边补。

### 2.1 HTTP 基础

必须知道：

- `GET` 和 `POST` 的区别；
- URL、查询字符串（`?q=xxx`）、表单体（`username=xxx&password=yyy`）；
- 常见请求头：`Host`、`Cookie`、`Content-Type`、`User-Agent`、`Referer`；
- 常见响应头：`Set-Cookie`、`Location`、`Content-Type`、`Allow`；
- 状态码：
  - `200` 成功；
  - `302` 重定向（本题大量用于“未登录 → 去登录页”）；
  - `400` 请求格式不对；
  - `401/403` 未认证/无权限；
  - `404` 路径不存在；
  - `405` 路径存在，但方法不对（**本题很重要的线索**）；
  - `500` 服务器内部错误。

**新手练习：**

```bash
curl -i http://39.107.224.246:26629/
curl -i http://39.107.224.246:26629/api/health
curl -i -X POST http://39.107.224.246:26629/login \
  -d 'username=test&password=test'
```

重点看响应头，不要只看响应体。

### 2.2 浏览器开发者工具（F12）

打开 Network（网络）面板，勾选 “Preserve log”，然后：

1. 访问首页；
2. 注册一个账号；
3. 登录；
4. 发一篇文章；
5. 搜索；
6. 点进文章详情。

每一步都观察：

- 发了哪些请求？
- 方法是 GET 还是 POST？
- 参数名是什么？
- 响应是 200、302 还是 400？
- 有没有 `Set-Cookie`？
- 重定向到了哪里？

**这一步比背一百个 payload 更有价值。** 本题的大部分入口，其实在正常使用流程里就能看到。

### 2.3 curl：命令行里的浏览器

新手最常用的几个参数：

```bash
# 看响应头和响应体
curl -i URL

# 只显示状态码和重定向地址
curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' URL

# 带 Cookie
curl -b 'JSESSIONID=xxxx' URL

# 保存 Cookie
curl -c cookies.txt -X POST URL -d 'username=a&password=b'

# 表单 POST
curl -X POST URL -d 'a=1&b=2'

# 对参数做 URL 编码（避免空格/特殊字符把请求搞坏）
curl -G URL --data-urlencode 'q=hello world'
```

本题里，`curl` 比 `nc` 好用得多。`nc host port` 只是“建立 TCP 连接”，你还得自己手写 HTTP 报文；`curl` 帮你把 HTTP 细节处理好了。

如果你想体验一下“手写 HTTP”，可以：

```bash
printf 'GET / HTTP/1.1\r\nHost: 39.107.224.246:26629\r\nConnection: close\r\n\r\n' | nc 39.107.224.246 26629
```

但日常分析请优先用浏览器 + curl。

### 2.4 表单、参数与数据流

看到一个输入框，先问自己四个问题：

1. 这个输入框的 `name` 是什么？
2. 提交时用的是 GET 还是 POST？
3. 这个参数最终会进入哪里？（数据库？模板？日志？文件路径？）
4. 服务器返回什么，能否证明我的输入被“原样”处理了？

本题的发文表单长这样：

```html
<form action="/compose" method="post">
  <input name="title">
  <input name="summary">
  <input name="category">
  <textarea name="body"></textarea>
</form>
```

提交后，文章会出现在 `/article/{id}`、首页和搜索结果里。

**新手要建立的思维：**

> 输入 → 参数 → 后端处理 → 存储/查询 → 输出。
>
> 漏洞通常出现在“某一环没有按预期处理输入”的地方。

### 2.5 SQL 与参数化查询（非常重要）

SQL 是数据库的查询语言。一个典型的查询是：

```sql
SELECT id, title, author, category
FROM articles
WHERE title LIKE '%hello%'
ORDER BY id DESC;
```

本题的搜索行为很像是：

```sql
WHERE title LIKE '%<你输入的 q>%'
```

这里有两个新手必须知道的点：

1. `%` 是 SQL `LIKE` 的通配符，表示“任意多个字符”；
2. `_` 是“任意一个字符”。

所以：

- 搜 `%` 会匹配所有标题；
- 搜 `_` 也会匹配所有非空标题；
- 搜 `pl_in` 能匹配 `plain`。

**这不等于 SQL 注入。** 这只是 `LIKE` 的正常语法。

真正的 SQL 注入，是让用户输入“跳出字符串”，变成 SQL 代码。例如，如果后端是这样拼 SQL 的：

```java
String sql = "SELECT * FROM articles WHERE title LIKE '%" + q + "%'";
```

那么输入：

```text
' OR '1'='1
```

就可能变成：

```sql
SELECT * FROM articles WHERE title LIKE '%' OR '1'='1%'
```

从而绕过条件。

**防御的正确做法是参数化查询（PreparedStatement）：**

```java
String sql = "SELECT * FROM articles WHERE title LIKE ?";
ps.setString(1, "%" + q + "%");
```

参数化之后，`'` 只是普通字符，不会变成 SQL 语法。

本题的黑盒测试结果是：

- 搜 `plain'` 返回 0 条，而不是报 SQL 语法错误；
- 发文标题写 `x'+SLEEP(3)+'`，被原样保存，响应也没有延迟；
- 登录/注册用户名里带引号，可以正常注册和登录。

这些现象都说明：**我们测到的这些入口大概率是参数化的**。所以“看到搜索框就上 `' OR 1=1`”在这题里行不通。

### 2.6 过滤器 / WAF 是什么

WAF（Web Application Firewall）可以理解成“门口的保安”：

- 它检查你提交的参数；
- 发现可疑字符或关键字，就直接拒绝；
- 本题的拒绝方式是返回一个固定错误：

```text
语句包含非法字符 (illegal character in statement)
```

我们实测到的拦截规则（黑盒观察，可能不完整）：

| 类型 | 被拦截 | 未被拦截（示例） |
|---|---|---|
| 字符 | `;` `<` `>` `~` `\|\|` | `'` `"` `=` `+` `-` `*` `/` `(` `)` `%` `&` `#` `$` |
| 关键字 | `OR` `AND` `UNION` `CASE` `LIKE` `IN` `CONCAT` `ASCII` `SUBSTR`（大小写不敏感） | `SELECT` `SLEEP` `XOR` `IF` `ORDER` `BY` `GROUP` `FROM` `WHERE` |

**新手最容易犯的错：**

> 把“过滤器报错”当成“发现漏洞”。

过滤器报错只能说明“这里有输入检查”，不能说明“这里能注入”。真正要证明的是：

1. 输入是否进入了 SQL / 模板 / 命令 / 文件路径；
2. 进入时是否被正确参数化或转义；
3. 过滤器和实际执行点是否一致。

本题里，过滤器很显眼，但我们测到的执行点大多是参数化的。这是一个很好的“反直觉”教学点：**有 WAF ≠ 有注入；能被 WAF 拦截 ≠ 能绕过 WAF 就有洞。**

### 2.7 认证、会话与访问控制

新手要分清三个概念：

| 概念 | 回答的问题 | 本题表现 |
|---|---|---|
| 认证（Authentication） | 你是谁？ | `/login`、`/admin/login` |
| 会话（Session） | 服务器怎么记住你？ | `JSESSIONID` Cookie |
| 授权（Authorization） | 你能不能做这件事？ | 普通用户进不了 `/admin/**` |

本题的访问控制现象：

- 未登录访问 `/compose` → `302` 到 `/login`；
- 未登录访问 `/admin` → `302` 到 `/admin/login`；
- 普通用户登录后访问 `/admin/dashboard` → 仍然 `302` 到 `/admin/login`。

后台还有**登录失败锁定**：

- 同一个账号连续失败若干次后，会提示“该账号因多次登录失败已被临时锁定，请 N 秒后再试”；
- 用户名大小写、前后空格会被归一化（`Admin`、`admin `、` admin` 都会被识别为同一个账号）；
- 用 `X-Forwarded-For`、`X-Real-IP` 等请求头换 IP，**没有**绕过锁定；
- 所以“暴力破解后台密码”在这题里不是一条好路。

**新手应该学到的：** 遇到登录框，先判断有没有验证码、锁定、限流、MFA；没有这些再考虑爆破，而且要在授权范围内。

### 2.8 Java / Spring Boot 指纹

本题是 Java 技术栈。新手不一定要会写 Spring Boot，但最好能认出它：

| 现象 | 说明 |
|---|---|
| `JSESSIONID` Cookie | Java Servlet / Tomcat 常见会话 Cookie |
| 登录后 URL 出现 `;jsessionid=...` | Tomcat 的 URL 重写机制（浏览器禁用 Cookie 时的兜底） |
| 404/400 返回 `{"timestamp":...,"status":...,"error":...,"path":...}` | Spring Boot 默认错误 JSON 风格 |
| 错误页是 Thymeleaf 模板渲染的 HTML | Java 模板引擎 |
| `/api/health` 返回 JSON | 典型的 Spring Boot 健康检查风格 |
| `Vary: Origin` | 有 CORS 配置 |
| `Content-Disposition: inline;filename=f.txt` | Spring MVC 的 RFD（反射文件下载）防护头，冷知识，不影响主线 |

本题没有发现：

- `/actuator/*`（Spring Boot Actuator）→ 全部 404；
- `/swagger-ui`、`/v3/api-docs` → 404；
- `/h2-console`、`/druid` → 404；
- 暴露的源码、备份、`.git`、`pom.xml` → 404。

这些“常见入口都没有”本身也是信息：说明出题人收得比较干净，不能指望捡现成的。

## 3. 本题的“地图”（精简版）

这一节只保留新手需要知道的骨架，不做深层信息收集。

### 3.1 公开页面与接口

| 路径 | 方法 | 是否需要登录 | 说明 |
|---|---|---|---|
| `/` | GET | 否 | 首页，展示所有文章 |
| `/search?q=` | GET | 否 | 按标题搜索 |
| `/team` | GET | 否 | 团队页，列出 5 位成员 |
| `/article/{id}` | GET | 否 | 文章详情，正文按纯文本转义显示 |
| `/api/health` | GET | 否 | `{"status":"ok","service":"easycms"}` |
| `/api/articles` | GET | 否 | 返回文章列表 `{id,title,author,category}` |
| `/register` | GET/POST | 否 | 注册 |
| `/login` | GET/POST | 否 | 登录 |
| `/logout` | GET | 是 | 退出 |
| `/compose` | GET/POST | 是 | 发文 |
| `/admin/login` | GET/POST | 否 | 后台登录 |
| `/admin/dashboard` | GET | 后台登录 | 后台首页（未登录 302） |
| `/admin/media` | GET | 后台登录 | 后台媒体库（未登录 302） |
| `/admin/logout` | GET | 后台登录 | 后台退出 |

### 3.2 几个关键现象

1. **搜索是 `LIKE` 语义**
   - `q=%` 返回全部；
   - `q=_` 返回全部；
   - `q=pl_in` 能匹配 `plain`；
   - 但 `q=plain'` 不会报 SQL 错，说明大概率参数化。

2. **发文内容是转义的**
   - 正文里的 `<b>`、`<script>` 会被过滤器拦截；
   - 即使通过其他方式写入，页面也是按纯文本显示，不会当 HTML 执行；
   - 文章正文区域使用 `white-space: pre-wrap`，只是保留换行，不是 Markdown 渲染。

3. **后台是独立认证**
   - 前台注册一个叫 `admin` 的用户，可以登录前台；
   - 但**不能**登录后台；
   - 后台的 `admin` 账号和前台用户表大概率是分开的（或至少有角色区分）。

4. **后台路径的 302 / 405 区别**
   - `GET /admin/dashboard` → `302 /admin/login`（页面存在，但未登录）；
   - `POST /admin/dashboard` → `405 Allow: GET`（路径存在，但没有 POST 处理）；
   - `GET /admin/zzzz` → `302 /admin/login`（未知路径也被统一重定向，隐藏后台结构）；
   - 这个区别是“枚举后台有哪些页面”的重要线索，新手可以借此理解 `405` 和 `302` 的含义。

5. **登录锁定**
   - 同一账号连续失败 5 次左右 → 锁定约 600 秒；
   - 换 IP 头无效；
   - 所以不要在这题上无脑爆破。

### 3.3 我们验证/排除了什么（黑盒层面）

> 这一节是“方法示范”，不是“答案”。黑盒结论都可能因为容器重置或版本差异而变化。

**比较确定的现象：**

- 前台注册/登录/发文/搜索都可用；
- 搜索按标题匹配，`%`/`_` 是通配符；
- 发文正文按纯文本转义；
- 后台有独立登录和锁定；
- 全局过滤器会拦截常见 SQLi 关键字/字符；
- 我们测到的登录、注册、发文、搜索入口，**没有观察到 SQL 注入**（引号被当普通字符、`SLEEP` 无延迟、内容原样存储）；
- 没有 Actuator / Swagger / H2 / Druid 等常见暴露面；
- 没有发现可直接读取的源码、备份、`.git`；
- 静态资源的编码斜杠穿越（`%2f`）被 Tomcat 直接 400 拒绝；
- 没有发现通过 Cookie、代理头、路径归一化绕过后台认证的简单方法；
- 没有发现明显的存储型 XSS（输出转义 + WAF 拦 `<`/`>`），也没发现 admin bot 的迹象。

**仍未知 / 推测：**

- 后台 `dashboard` / `media` 页面里到底有什么；
- 是否存在一个我们没测到的、未参数化的 SQL 注入点（例如后台的排序/筛选参数）；
- 后台 `media` 是否支持上传/读取文件，是否存在路径穿越；
- 是否存在弱口令/默认口令 + 锁定绕过；
- 是否存在特定 Spring/Tomcat/Thymeleaf 版本的 CVE；
- flag 的具体位置（后台页面、文件系统、环境变量等）。

## 4. 本题难点在哪

### 难点 1：黑盒，信息少

题目只给了一个地址，没有源码、没有附件、没有提示。你必须从页面、链接、表单、状态码、错误信息里自己拼出应用结构。

对新手来说，这比“给源码找漏洞”难得多，因为：

- 你不知道有哪些路由；
- 你不知道后端用了什么框架；
- 你不知道哪些输入进了数据库、哪些只是展示；
- 你甚至不知道 flag 在哪。

### 难点 2：前台和后台是两套认证

前台注册的账号进不了后台。后台还有登录锁定。这意味着：

- 不能靠“注册一个 admin 用户名”提权；
- 不能靠无脑爆破；
- 必须找到“从普通用户到后台”的缺口，或者找到后台凭据的泄露点。

### 难点 3：全局 WAF 会误导你

本题的过滤器非常显眼：你只要输入 `;`、`<`、`OR`，就会看到固定错误。新手很容易：

- 以为“报错 = 有注入”；
- 以为“绕过 WAF = 拿 flag”；
- 花大量时间研究过滤器，却忽略了真正的业务逻辑。

正确的思路是：**先确认数据流，再谈绕过。** 如果执行点是参数化的，绕过 WAF 也没有意义。

### 难点 4：参数化查询让“经典 SQLi”失效

搜索框看起来像 SQL 注入的完美目标（`LIKE '%q%'`），但实际测试表明它大概率是参数化的。这是本题最重要的“反套路”：

> 一个输入框长得像注入点，不代表它真的是注入点。

新手需要学会用**证据**判断，而不是靠“感觉像”：

- 输入引号，看是否报 SQL 语法错误；
- 输入 `SLEEP()`，看响应是否延迟；
- 输入特殊字符，看是否原样存储/显示；
- 对比“过滤器报错”和“数据库报错”的区别。

### 难点 5：需要链路思维，而不是单点思维

如果 flag 在后台，那么你需要的是：

```text
信息收集 → 发现入口 → 获得普通用户 → 找到提权/凭据泄露 → 进入后台 → 找到 flag
```

任何一步缺失，都拿不到 flag。这对新手的“耐心”和“记录习惯”要求很高。

### 难点 6：需要一点 Java / Spring 常识

如果你只学过 PHP 或 Python Web，看到这些会懵：

- `JSESSIONID` 是什么？
- 为什么登录后 URL 里多了 `;jsessionid=`？
- 为什么 404 返回的是 JSON 而不是 HTML？
- `302` 和 `405` 有什么区别？
- 什么是 Actuator / Thymeleaf / Spring Security？

这些不是“必须会写”，但“必须能认”。认不出来，就会把正常现象当成漏洞。

### 难点 7：比赛时间压力

线上赛通常时间紧、题目多。这题的信息收集和验证成本不低，容易让人在中途放弃。作为学习样本，建议**赛后慢慢做**，不要用比赛心态。

- 过滤器覆盖范围（query/form/JSON/header/cookie/path）；
- 参数污染、编码、大小写、注释等绕过思路（概念层面）；

- Spring MVC 的 Controller / 表单绑定；

## 6. 如果让你从零开始做这题：推荐步骤

> 这一节是“学习流程”，不是“通关秘籍”。每一步都建议你在浏览器和 curl 里亲手做一遍。

### 第 1 步：只读浏览，不碰任何 payload

- 打开 `/`、`/team`、`/login`、`/register`；
- 看页面上的每一个链接；
- 用 F12 记录每个页面的请求；
- 画出站点地图（哪怕只有一页纸）。

**目标：** 知道这个站有哪些页面，哪些需要登录。

### 第 2 步：注册一个账号，完整走一遍流程

- 注册 → 登录；
- 观察 `Set-Cookie` 和 `302`；
- 访问 `/compose`，发一篇文章；
- 看文章出现在哪里：首页、`/article/{id}`、`/api/articles`、搜索结果。

**目标：** 理解“登录态”和“数据流”。

### 第 3 步：玩搜索，理解 LIKE

- 搜 `hello`；
- 搜 `%`；
- 搜 `_`；
- 搜 `pl_in`；
- 搜 `plain'`；
- 搜 `plain' #`；
- 搜 `OR`、`AND`、`;`、`<`。

**目标：** 区分“LIKE 通配符”“参数化”“WAF 拦截”三种现象。

### 第 4 步：故意制造错误，读状态码

- `/article/abc` → 400；
- `POST /search` → 405；
- `/nope` → 404；
- `/admin/dashboard` 未登录 → 302；
- `POST /admin/dashboard` → 405；
- `/admin/zzzz` → 302。

**目标：** 学会用状态码判断“路径是否存在”“方法是否支持”“是否需要登录”。

### 第 5 步：找后台，但不要爆破

- 从页面链接、HTML 注释、CSS 类名、常见命名里找后台入口；
- 访问 `/admin`、`/admin/login`；
- 观察后台登录的错误提示；
- 试 1～2 次错误密码，看是否有锁定提示；
- **不要**连续爆破，既没效率，也不礼貌。

**目标：** 理解后台的认证边界和锁定机制。

### 第 6 步：系统地记录 WAF 行为

- 做一个字符表：`; < > ~ | & = ' " ( ) + - * / # $ %`；
- 每个字符单独测试；
- 记录“被拦截 / 未拦截”；
- 再做关键字表：`OR AND UNION CASE LIKE IN CONCAT ASCII SUBSTR SELECT SLEEP XOR`；
- 记录结果。

**目标：** 学会“用实验代替猜测”，并理解黑名单过滤的局限。

### 第 7 步：验证“是不是注入”，而不是“像不像注入”

对每个可疑输入，至少做三种验证：

1. **语法验证**：输入 `'`，看是否报 SQL 语法错误；
2. **时间验证**：输入 `SLEEP(3)` 或 `BENCHMARK`，看是否延迟；
3. **内容验证**：输入特殊字符串，看是否原样存储/显示。

如果三者都不支持“注入”，就暂时放下，不要恋战。

### 第 8 步：如果卡住，换思路

- 回到业务逻辑：注册、登录、发文、搜索、后台；
- 看有没有“权限判断”和“数据归属”的漏洞；
- 看有没有“前端隐藏字段”“多余参数”“接口返回多余字段”；
- 看有没有“错误信息泄露”；
- 看有没有“默认口令/弱口令/凭据泄露”；
- 如果实在没有思路，去看官方 WP 或和队友讨论。

### 第 9 步：复盘

做完或看完 WP 后，回答这些问题：

- 这题真正的漏洞点在哪？
- 我一开始的假设错在哪？
- 哪些现象是“过滤器”，哪些是“漏洞”？
- 如果让我防这个漏洞，应该怎么改？
- 我下一次遇到类似的 Java CMS，应该先看什么？

## 7. 新手常见误区

1. **看到登录框就 `' OR 1=1`**
   - 本题会直接返回“语句包含非法字符”，因为 `OR` 被过滤器拦了。
   - 即使绕过过滤器，如果后端是参数化的，也不会成功。

2. **看到 `%` 能搜出全部，就以为 SQL 注入**
   - 这是 `LIKE` 的通配符，不是注入。
   - 判断注入要看“引号是否改变 SQL 结构”，而不是“通配符是否生效”。

3. **把 302 当成 404**
   - 302 往往表示“路径存在，但你需要先登录/去别处”。
   - 本题大量使用 302 到 `/admin/login`。

4. **把 405 当成没权限**
   - 405 表示“路径存在，但 HTTP 方法不对”。
   - 它反而是“这个路径有处理器”的证据。

5. **忽略 Cookie 和重定向**
   - 很多新手只看响应体，不看 `Set-Cookie` 和 `Location`。
   - 本题的登录态完全靠 `JSESSIONID`。

6. **无脑目录爆破**
   - 本题页面链接已经给了大部分入口；
   - 后台路径统一 302，爆破收益低；
   - 还可能触发防护/影响别人。

7. **把 WAF 报错当成漏洞**
   - WAF 报错只说明“有过滤”，不说明“有注入”。

8. **不做记录**
   - 做到后面忘了前面试过什么；
   - 建议用表格记录：URL、方法、参数、状态码、结论。

9. **在非授权目标上测试**
   - 只在比赛/靶场/书面授权范围内测试；
   - 不做破坏性操作。

## 8. 题目评价：优点、缺点、适合谁

### 优点

- **真实感强**：注册、登录、发文、搜索、后台、WAF、锁定，像一个真实的小型 CMS。
- **技术栈主流**：Java + Spring Boot + Tomcat + Thymeleaf，学了不亏。
- **层次清楚**：前台 → 登录 → 后台 → 文件/数据，适合讲“利用链”。
- **有反套路设计**：搜索框像注入点，但实际参数化；WAF 很显眼，但不一定是洞。
- **没有依赖冷门 CVE**（至少从黑盒看）：更考验基础和方法，而不是背漏洞编号。

### 缺点

- **对完全新手不友好**：入口不明显，信息少，容易迷路。
- **WAF 会打击信心**：常见 payload 全部报错，容易误判。
- **后台是黑盒**：在没拿到凭据前，能测试的东西有限。
- **难度和题名“ez”不太匹配**：对新手来说不算 easy。
- **黑盒结论不稳定**：容器可能重置，观察结果可能变化。

### 适合谁

- 学过 HTTP、表单、Cookie/Session、SQL 基础；
- 想第一次认真做一道 Java Web 题；
- 愿意做记录、画图、写验证脚本；
- 有 WP/导师/队友可以讨论。

### 不适合谁

- 完全没写过请求、没听过 Cookie/Session；
- 只会上工具、不愿意读响应；
- 想靠爆破/无脑 payload 过关；
- 没有授权就想“实战”的人。

### 建议的学习顺序

1. PortSwigger Web Security Academy 的基础章节（HTTP、认证、SQLi、访问控制）；
2. OWASP Juice Shop 或 WebGoat（本地靶场）；
3. 本题（配合 WP 或导师）；
4. 自己复现一个最小的 Spring Boot CMS，亲手写一个参数化查询和一个 WAF，理解防御；
5. 再回头看本题的 WP，对照自己的记录。

## 9. 术语小抄

| 术语 | 一句话解释 |
|---|---|
| HTTP | 浏览器和服务器说话的协议 |
| 请求 / 响应 | 你发过去的单子 / 服务器端回来的菜 |
| GET / POST | 两种最常见的“点单方式” |
| 状态码 | 服务器对这次请求的“结果编号” |
| 302 | 重定向，去另一个地址 |
| 405 | 路径存在，但方法不对 |
| Cookie | 浏览器保存的一小段字符串 |
| Session | 服务器端的“小本子”，用 Session ID 关联 |
| JSESSIONID | Java/Tomcat 常见的 Session Cookie 名 |
| WAF | 检查请求的“门口保安” |
| SQL | 数据库查询语言 |
| SQL 注入 | 让用户输入变成 SQL 代码 |
| 参数化查询 | 把用户输入当“数据”，而不是“代码” |
| LIKE | SQL 的模糊匹配 |
| `%` / `_` | LIKE 的通配符 |
| Spring Boot | Java 的快速开发框架 |
| Tomcat | Java Web 服务器 |
| Thymeleaf | Java 模板引擎 |
| Actuator | Spring Boot 的运维端点（本题没有） |
| 越权 | 做了自己权限之外的事 |
| 爆破 | 批量猜密码（本题有锁定，不推荐） |
