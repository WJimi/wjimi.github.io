复盘分两种：**赛后复盘（选手自己）**和**面向新手的复盘（把题变成训练材料）**。容器题的特殊性只影响“现场怎么保存”，不影响复盘的方法论。下面按可执行的流程讲。

---

## 一、先纠正一个常见误区

复盘不是“把 WP 再写一遍”。WP 只是副产品。真正要产出的是三样东西：

1. **决策日志**：你当时看到什么信号、做了什么假设、走了哪条路、哪里走错、什么时候该停。
2. **可复现资产**：源码、DB dump、请求包、脚本、环境快照、版本信息——保证环境没了也能重建。
3. **可迁移的知识卡/检查表**：下次看到同类信号，能在 5 分钟内触发正确动作，而不是“想起这道题”。

没有这三样，WP 收藏再多，下次遇到变种还是不会。

## 二、通用复盘流程（24h / 72h / 7 天）

### 24 小时内：只做“原始记录”，不急着解释

趁记忆和现场还在，先固化证据：

- 浏览器历史、Burp/mitmproxy 项目、curl 命令历史、shell history；
- 所有 payload 和响应原文（成功/失败都要）；
- 截图：源码、进程、端口、权限、DB 内容；
- 环境信息：PHP/Perl/MariaDB 版本、容器镜像、启动脚本、目录结构；
- flag 和读取路径。

这一步的关键是**不要美化**：把“当时其实没看懂”的地方也记下来。

### 72 小时内：还原时间线 + 决策树

按 10~20 分钟一个节点写表：

| 时间 | 观察到的信号 | 当时假设 | 动作 | 结果 | 现在回看 |
|---|---|---|---|---|---|
| 10:20 | feed 参数引号被参数化 | 注入点在别处 | 继续 fuzz 参数 | 无果 | 应转向 bulk/路由层 |
| ... | ... | ... | ... | ... | ... |

然后画两条线：

- **成功链**：哪几个步骤是必需的，顺序能不能换；
- **死路清单**：为什么走进死路、什么信号本应让你及时掉头。

死路往往比成功链更值钱，因为它对应你下次该提前识别的信号。

### 7 天内：最小复现 + 变式验证

把整条链拆成“单点最小复现单元”，每个单元单独跑通：

- 只保留触发某个漏洞的最小请求；
- 单独确认 SQLi 能 UNION；
- 单独确认 hook 能建号；
- 单独确认 hpxd 能执行一条 `id`。

然后做**变式**：

- 把漏洞补上，再尝试用别的路径打；
- 换一种 payload 编码；
- 改掉一个前提（比如关闭嵌套 bulk），看链条断在哪；
- 用不同工具重放（Python、curl、Burp）。

能拆能合、能改能防，才算真的吃透。

## 三、容器题（需要环境）的复盘难点

容器题有三态：**赛时 live → 赛后 frozen → 最终回收**。难点是：

- 环境随时可能消失，动态 flag 不可复用；
- 你的利用会改变 DB/文件状态，“你离开时的环境”不等于“你刚进来时的环境”；
- 内网服务、localhost 端口、root-only 文件，外部看不见；
- 源码可能只在容器里，甚至被删。

### 对策 1：一进场就“固化现场”

拿到任何立足点（哪怕只是 SQLi 或 www-data shell）就立刻做快照：

```text
源码/配置：tar 打包 /var/www、/etc/site、/opt/scripts（能读的）
数据库：mysqldump --all-databases（能连的话）
进程/网络：ps aux、ss -lntup、/proc/net/tcp
权限：/etc/passwd、/etc/group、find / -perm -4000、getcap -r /
本地服务：逐个访问 127.0.0.1:<port>，保存响应和源码泄露
请求证据：Burp 项目或 mitmproxy flow，带时间戳
凭据/会话：cookie、token、账号口令
```

把这些拷回本地，放到一个带日期的目录里。

### 对策 2：脚本一律参数化

地址、flag、账号、token、staff 登录名全部做成变量；不要把一次性状态写死。这样环境重建后脚本还能跑，也方便别人复现。

### 对策 3：环境没了就本地重建

容器题最好的复盘资产就是**自包含 WP + 最小 compose**。例如本题可以重建：

```text
php:8.3-apache + mariadb:10.11
挂载 WP 里内嵌的 8 个 PHP 文件
初始化 SQL：entries / entry_comments / entry_tags / staff_accounts /
          site_config / site_changesets / staff_sessions
hpxd：用同一个 Perl 脚本，root 运行，stub 掉 /root/.vault_key 和 vaultdb，
      或者在本地 compose 里真建 vaultdb + master_auth
```

重建时把版本钉死，记录 PHP/MariaDB/Perl 模块版本，否则行为会漂移。

### 对策 4：把“请求包”当一等证据

容器题的复盘时间线几乎都能从抓包时间戳还原：

- 每个请求标注目的和结论；
- 失败的请求也保留；
- 关键 payload 用“注释版”保存（哪一段是闭合、哪一段是 UNION、哪一段是注释）。

### 对策 5：区分“题目的必然”和“环境的偶然”

复盘时明确哪些是题目设计（bulk 下标错位、hook 提权），哪些是本次环境特有（随机 staff 登录名、动态 flag、端口号、实例地址）。写 WP 时前者写成通用原理，后者写成占位符。

## 四、面向“WP 最后一节新手向”的复盘法

新手最难的不是“没看懂”，而是**看懂了但不会自己做**。所以新手复盘要分层，每层有验收标准。

### L0：跑通（照做）

- 按 WP 分阶段复现：SQLi → 建号 → webshell → root。
- 每阶段单独保存请求和响应。
- 验收：不看 WP 能凭自己的脚本跑出同样结果。

### L1：讲清（费曼）

- 合上 WP，用自己的话讲清楚：为什么下标会错位？为什么 `omit` 能绕过清洗？为什么 `PUBLISH_AS` 能提权？为什么 www-data 不够？
- 讲不出来的地方，就是没掌握的地方，回到源码补。
- 验收：能画出一张“参数从 HTTP 到 SQL/命令”的流程图。

### L2：改坏再修（断点思维）

- 在本地重建环境里，故意改坏一个前提再跑：
  - 把 `omit` 加回 `id_list` 清洗 → SQLi 断了，为什么？
  - 去掉嵌套 bulk → 还能不能触发 hook？
  - 把 `PUBLISH_AS` 改成每次请求都清 → 链条断在哪？
- 验收：能解释每个断点，并能提出替代路径。

### L3：变式（迁移）

- 改代码：把 `owner_not_in` 修好，换成 `tag` 注入，再打；
- 改防御：加 WAF/过滤，尝试编码绕过；
- 换语言/框架：用另一种写法复现同类“批量接口内外校验不一致”。
- 验收：面对“长得不像但结构相似”的题，能识别出同类信号。

### L4：形成检查表

把题目抽象成**触发式检查表**，而不是故事：

```text
看到批量/嵌套接口
  → 检查内外层动词、参数、权限是否一致
  → 检查错误项是否参与下标/数组对齐
看到"参数化查询"但仍有拼接
  → grep 所有 SQL 字符串拼接，重点看 IN/NOT IN、ORDER BY、LIMIT
看到读接口触发写操作
  → 找 hook/snapshot/cache 副作用
拿到低权限 shell
  → ps/ss /proc /sudo -l / find -perm -4000 / localhost 服务 / 源码泄露
```

验收：下次遇到新题，这张表能在 10 分钟内跑完一遍。

### 新手最常犯的 5 个错误

1. 只收藏 WP，不敲；
2. 只背 payload，不理解闭合和列对齐；
3. 跳过失败记录，导致同样的死路反复走；
4. 一次就想复现整条链，卡住就放弃；
5. 环境一没就放弃，觉得“没法复盘”。

对应解法：**分阶段、留失败、先单点后链、环境自建**。

### 一个可执行的 7 天新手复盘计划

| 天 | 30~60 分钟任务 | 产出 |
|---|---|---|
| D1 | 按 WP 跑通 SQLi 单点 | 最小请求 + 响应 |
| D2 | 本地重建 PHP+MariaDB 环境 | compose + 初始化 SQL |
| D3 | 复现 hook 提权，画时序图 | 时序图 + 断点说明 |
| D4 | 复现 skin editor + hpxd 提权 | 两个脚本 + 权限边界图 |
| D5 | 改坏 3 个前提，记录断点 | 断点日志 |
| D6 | 不看 WP 从头再做一遍 | 个人版 WP |
| D7 | 写成检查表 + 知识卡 | 可复用资产 |

## 五、可直接套用的复盘模板

### 1）时间线 / 决策表

```text
| 时间 | 信号 | 假设 | 动作 | 结果 | 回看结论 |
```

### 2）死路清单

```text
| 死路 | 当时为什么走进去 | 本应出现的掉头信号 | 下次何时停 |
```

### 3）知识卡（一张卡只写一个点）

```text
信号：批量接口内外动词/权限不一致
原理：外层校验不等于内层校验；错误项可能破坏数组下标
最小动作：构造 [坏路由, 注入op, 目标处理器] 看参数落到谁手里
边界：内层是否重新校验；错误项是否占位
反例/防御：执行前重新 route_bind + op_check
```

### 4）环境固化清单

```text
[ ] 源码/配置 tar
[ ] DB schema + dump
[ ] 版本（PHP/MariaDB/Perl/内核）
[ ] 进程、端口、socket
[ ] 用户、权限、SUID、capabilities
[ ] localhost 服务与源码泄露
[ ] Burp/mitmproxy 项目与 curl 日志
[ ] 凭据、cookie、token
[ ] flag 及读取位置
```

### 5）目录结构

```text
ctf/2026/cwp/
├── writeup.md          # 自包含题解
├── timeline.md         # 时间线/决策表
├── dead-ends.md        # 死路清单
├── cards/              # 知识卡
├── env/                # compose + init.sql + 版本信息
├── payloads/           # 原始请求/脚本
├── logs/               # 抓包、命令历史、截图
└── notes/              # 卡点日志
```

## 六、拿本题举例：四层“当时该想到什么”

| 层次 | 当时现象 | 正确信号 | 下次动作 |
|---|---|---|---|
| 1 | feed 参数引号被参数化 | 有参数化，但代码里可能还有拼接分支 | grep 所有 SQL 字符串拼接，重点 `IN/NOT IN` |
| 2 | 有 bulk.php，但外层只允许写动词 | 内外层校验可能不一致 | 检查嵌套/混淆调用，错误项是否影响下标 |
| 3 | SQLi 能读库，但拿不到权限 | 读接口可能触发写/hook | 找 snapshot/cache/hook 副作用 |
| 4 | www-data 读不到 /root | 本地还有 root 服务 | ps/ss/localhost 端口/源码泄露/权限枚举 |

这四行就是本题最有价值的复盘产出——它比“payload 长什么样”更能迁移到下一题。

## 七、团队复盘（如果是队伍）

- **不追责**：只讨论“信号—假设—动作”，不讨论“谁菜”。
- 对齐时间线：每个人写自己的 5 分钟粒度时间线，合并后找分叉点。
- 做 5 Whys：连续问五个“为什么没更早发现”，落到流程/工具/知识，而不是“再努力点”。
- 每人只定一个改进动作（例如“下次先列接口清单再 fuzz”“看到批量接口先查内外校验”），下次比赛验证。
