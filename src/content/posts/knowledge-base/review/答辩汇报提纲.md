# ·答辩汇报提纲

这份材料用于 10 分钟左右的课程设计答辩。每个问题先准备“一句话版本”，
老师继续追问时再展开。答辩时先把机制和证据讲清楚，不必一次把所有细节说完。

---

## 一、开场 60 秒

可以按下面四句介绍：

> 1. 我做的是《字符串多模式匹配综合实验平台》。输入一个关键词库和一段文本，
>    找出文本中全部关键词出现的位置，并展示算法是怎么一步一步得到结果的。
>
> 2. 项目以字典树为主结构，在字典树上构建 AC 自动机的失配指针；
>    同时实现朴素匹配和 KMP 作为对照。
>
> 3. 控制台只负责加载词库、导入文本和生成网页。算法全部由 C++ 完成，
>    网页负责把字典树、匹配过程、命中结果和性能数据画出来。
>
> 4. 当前默认词库 12 个词、综合文本 126 字符时命中 47 处；3000 组随机对拍中，
>    三种算法的结果逐条一致。

如果老师关注性能，再补一句：

> 在本次两组实验中，词库从 10 个词增加到 1000 个词，
> 朴素匹配从约 0.030 ms 增加到 2.966 ms，AC 自动机从约 0.015 ms 到 0.020 ms，
> 最后朴素匹配约为 AC 的 151 倍。具体数字以现场生成的性能页为准。

## 二、项目结构

系统分成三层：

| 层     | 做什么                                 | 主要文件                                 |
| ------ | -------------------------------------- | ---------------------------------------- |
| 数据层 | 读词库、处理 UTF-8、去重、保存文本     | `wordbank.*`、`utf8.*`、`data/`          |
| 算法层 | 朴素匹配、KMP、字典树、AC 自动机、对拍 | `matcher.*`、`trie.*`、`ac.*`、`bench.*` |
| 表现层 | 控制台调度、生成自包含网页             | `main.cpp`、`visualize.*`                |

一句话：

> 算法层只产生“命中了什么、过程中走了哪一步”，显示层只负责把数据画出来。
> 两边通过 `model.h` 里的公共结构传递数据，所以换可视化方式不需要改算法。

### 2.1 可视化是怎么实现的？`visualize.cpp` 为什么这么长？

老师可能的问法：

> 可视化是怎么实现的？`visualize.cpp` 代码这么长，是往 HTML 里插入变量吗？这个文件你吃透了吗？

一句话回答：

> 不是 C++ 在运行时控制浏览器，而是 C++ 先把字典树、命中结果和过程记录序列化成
> JavaScript 数据对象，再和 HTML/CSS/JS 模板一起写进一个自包含文件。浏览器打开后，
> 才由页面里的 JS 完成播放、单步和绘制。

完整数据流：

```text
Trie / matcher / ac / bench
        ↓
公共结构 VizData（model.h）
        ↓
C++ 序列化成 const DATA = { ... }
        ↓
嵌入 HTML/CSS/JS 原始字符串
        ↓
写出 output/report.html
        ↓
浏览器执行 JS，完成绘制和交互
```

关键代码位置：

| 位置                                                         | 作用                                                      |
| ------------------------------------------------------------ | --------------------------------------------------------- |
| `visualize.cpp` 的 `emitSvg()`                               | 递归计算树节点坐标，写出 SVG 的边、节点、词尾和 fail 编号 |
| `emitNodes()`、`emitAcSteps()`、`emitAlignSteps()`、`emitHits()` | 把 C++ 过程记录变成 JS 可以直接读的数组                   |
| `emitNextSteps()`、`emitFailSteps()`、`emitNextArrays()`     | 输出两种构造过程的数据                                    |
| `emitBench()`、`emitScale()`                                 | 输出性能实验数据                                          |
| `kHtmlHead`                                                  | HTML 头部、CSS 和页面结构                                 |
| `kHtmlTail`                                                  | 浏览器端 JS：切换算法、播放、单步、画树、画文本、画命中   |
| `Visualizer::exportHtml()`                                   | 最终把模板、`const DATA` 和所有数据写成一个文件           |

为什么文件长：

- `visualize.cpp` 当前约 **1429 行**；
- 其中约 **1081 行**位于两个 `R"HTML(... )HTML"` 原始字符串里，是 CSS/HTML/JS 模板；
- 纯 C++ 的序列化、树布局和文件写出逻辑约 **348 行**；
- 文件长不代表算法难，主要是因为把整套前端样式和交互都内嵌进一个自包含文件，
  避免依赖服务器、框架和网络。

可以直接这样说明自己的掌握程度：

> 我能从 `VizData` 的入口讲到 HTML 的出口。真正需要掌握的不是背下每一条 CSS，
> 而是三件事：第一，C++ 和页面之间传递哪些字段；第二，`step` 如何驱动页面状态；
> 第三，树、文本、next 和性能表分别由哪组函数渲染。页面出现问题时，我能判断
> 是数据记录错了、序列化转义错了，还是浏览器渲染错了。

两个容易答错的细节：

- `emitSvg()` 负责树形结构；页面上的失配箭头不是一棵静态 SVG 全部画满，
  而是由 JS 在每一步根据 `chain` 动态重画当前真正走过的箭头；
- 文本进入 HTML 和进入 JS 字符串使用不同转义函数。`escHtml()` 处理标签，
  `escJs()` 防止 `</script>` 和实体解码造成字符位置错位。

### 2.3 标准库使用边界

老师的问法：

> 哪些是直接引用了标准库的东西？讲解一下。

| 标准库组件                                 | 主要用途                             | 项目位置                                    |
| ------------------------------------------ | ------------------------------------ | ------------------------------------------- |
| `std::string`                              | 保存关键词、文本、路径、页面字符串   | 全项目                                      |
| `std::vector`                              | 节点池、命中结果、过程步骤、性能结果 | `trie.*`、`model.h`、`bench.*`              |
| `std::map<int,int>`                        | 每个 Trie 节点的稀疏孩子表           | `trie.h`                                    |
| `std::unordered_set<std::string>`          | 词库去重                             | `wordbank.cpp`                              |
| `std::queue<int>`                          | AC 失配指针的 BFS                    | `ac.cpp`                                    |
| `std::sort`、`std::unique`                 | 命中结果统一排序、去重               | `matcher.cpp`                               |
| `std::find`、`std::max`、`std::min`        | 查找、树布局边界、采样长度           | 多个模块                                    |
| `std::ifstream`、`std::ofstream`           | 读数据文件、写 HTML                  | `wordbank.cpp`、`main.cpp`、`visualize.cpp` |
| `std::ostringstream`                       | 拼接字符串和数字                     | `main.cpp`、`visualize.cpp`                 |
| `std::chrono::steady_clock`                | 性能实验计时                         | `bench.cpp`                                 |
| `std::rand`、`std::srand`                  | 可复现随机测试                       | `bench.cpp`                                 |
| `std::stoi`、`std::atoi`、`std::to_string` | 字符串与整数转换                     | `main.cpp`                                  |

`std::` 是 C++ 标准库的命名空间。例如 `std::vector` 表示“标准库里的 `vector`”，
不是本项目自己写的类。项目没有写入 `using namespace std;`，所以标准库名字前保留
`std::`，避免和项目里的 `Trie`、`MatchResult` 等名称冲突。

需要特别区分：

- `std::map` 是有序关联容器，常见实现使用平衡树；
- `std::unordered_set` 是哈希容器，平均 O(1) 查找，但无序；
- `<windows.h>`、`<direct.h>`、`<io.h>`、`<dirent.h>`、`<sys/stat.h>`、
  `<unistd.h>` 属于操作系统/平台 API，**不是 C++ 标准库**；
- 项目没有第三方 C++ 库，核心算法全部由项目代码实现。

## 三、涉及的数据结构

被问到“用了哪些数据结构”时，按“结构 → 解决什么问题”回答：

| 数据结构               | 项目中的用途                     | 为什么用它                                                   |
| ---------------------- | -------------------------------- | ------------------------------------------------------------ |
| 字典树 Trie            | 保存全部关键词，共享公共前缀     | 几千个词可以合并成一棵树，不必存几千条独立串                 |
| 数组池 + 整数下标      | 字典树节点存储                   | 节点集中在 `vector` 中，节点之间用下标关联，避免 `new/delete` 和野指针 |
| 有序映射 `std::map`    | 每个节点的孩子表                 | 每个节点的分支通常很少，比固定开 256 个格子省空间，还能按字符有序遍历 |
| 队列                   | 按层构建 AC 失配指针             | 算子节点要用父节点的结果，先进先出正好保证父层先处理完       |
| 哈希表 `unordered_set` | 词库去重                         | 平均 O(1) 判断重复，避免逐条两两比较                         |
| 动态数组 `vector`      | 节点池、命中结果、过程记录       | 规模事先未知，可以自动扩容                                   |
| 排序与去重             | 统一三种算法的命中结果           | 输出顺序一致，才能逐条对拍                                   |
| 输出链 `outLink`       | 从一个词尾直接跳到下一个词尾祖先 | 让 AC 匹配阶段达到 O(n+z)，不必每步爬完整条失配链            |

对应的标准回答：

> 主结构是字典树，节点用数组池保存，孩子表用有序映射。
> 建失配指针用队列做按层遍历，词库去重用哈希表，过程记录和命中结果用动态数组。
> 三种算法的结果统一排序去重后逐条对拍。

### 3.1 字典树的结构：逻辑上是什么，最底层是什么？

老师可能的问法：

> 字典树的结构是什么？细化到最基本的数据结构又是什么？

标准回答：

> 逻辑上，字典树是一棵有根前缀树；物理上，它不是指针树，而是
> `vector<TrieNode>` 数组池加上每个节点的 `map<int,int>` 稀疏邻接表。
> 每个字符通过“字符编号 → 子节点下标”挂在当前节点下面。

节点结构在 `src/trie.h`：

```cpp
struct TrieNode {
    std::map<int, int> child;  // 字符编号 -> 子节点下标
    int fail;                  // AC 失配指针
    int outLink;               // 最近词尾祖先
    int wordId;                // 词尾标记
    int parent;                // 父节点下标
    int depth;                 // 深度
    int ch;                    // 到达本节点的字符
};
```

数组池在 `Trie` 类：

```cpp
std::vector<TrieNode> pool;   // pool[0] 固定为根节点
```

插入时在 `Trie::insert()` 中：

1. 先把关键词解码成字符编号；
2. 从 `pool[0]` 根节点出发；
3. 用 `child.find(cp)` 查当前字符的孩子；
4. 没有孩子就 `pool.push_back()` 新建节点；
5. 用 `child[cp] = 新节点下标` 建立边；
6. 最后一个节点写 `wordId`。

所以“最基本的数据结构”可以分三层回答：

1. **逻辑层**：树，每个节点代表从根到它的前缀；
2. **存储层**：动态数组 + 有序映射，分别来自 `std::vector` 和 `std::map`；
3. **引用层**：节点之间用整数下标，不用 `TrieNode*` 指针。

`std::map` 的底层实现通常是有序平衡树，但 C++ 标准只规定它是
有序关联容器，不强制某一种具体实现；答辩时不要说成“标准保证一定是红黑树”。

为什么适合这个项目：

- 公共前缀只存一份；
- 每个节点的分支通常很少，`map` 比固定大数组省空间；
- 整数下标稳定，不会出现野指针；
- `fail`、`outLink`、`wordId` 可以直接挂在节点上，后续算法不需要再建映射。

### 3.2 `unordered_set`、数组池和“排序去重”的准确关系

老师的问法里可能把“排序去重”和 `unordered_set` 混在一起，先纠正：

> 词库去重用的是 `unordered_set`；三种算法的命中结果排序去重用的是
> `std::sort + std::unique`。两者用途不同。

#### `unordered_set` 在哪里

位置：`src/wordbank.cpp`，`WordBank::load()`。

```cpp
std::unordered_set<std::string> seen;
if (seen.find(line) != seen.end()) { ++dup; continue; }
seen.insert(line);
words.push_back(line);
```

它是最基础的数据结构：

- 哈希表；
- 存储已经见过的字符串；
- 平均 O(1) 查找和插入；
- 无序，所以不负责保持原文件顺序；
- 真正的词库顺序保存在旁边的 `std::vector<std::string> words`。

如果逐条与 `words` 比较，去重是 O(n²)；哈希表把平均代价降到接近 O(n)。

#### 命中结果为什么不是用它

位置：`src/matcher.cpp` 的 `normalizeMatches()`。

```cpp
std::sort(hits.begin(), hits.end(), ...);
hits.erase(std::unique(hits.begin(), hits.end(), ...), hits.end());
```

因为三种算法的命中结果必须按统一顺序逐条比较。这里需要“先有序，再去相邻重复”，
所以用 `sort + unique`，而不是哈希表。

#### 数组池在哪里

| 位置                                          | 内容                                             |
| --------------------------------------------- | ------------------------------------------------ |
| `src/trie.h` 的 `Trie` 私有成员               | `std::vector<TrieNode> pool`                     |
| `src/trie.cpp` 的 `Trie::Trie()`              | `pool.push_back(TrieNode())` 创建根节点          |
| `src/trie.cpp` 的 `Trie::insert()`            | 新节点追加到 `pool`，父节点的 `child` 保存新下标 |
| `src/trie.cpp` 的 `Trie::node()`、`childAt()` | 通过节点编号访问池中数据                         |

数组池的本质：

> 把很多节点放进一个连续动态数组，节点之间不保存内存地址，只保存数组下标。

这样做的直接收益：

- 不需要 `new/delete`；
- 不会出现悬空指针；
- 调试时可以直接查看 `pool[17]`；
- `vector` 扩容不会改变节点编号，只可能让节点在内存中的地址变化。

这里要能答出一个陷阱：

> `pool.push_back()` 之后不能继续使用之前保存的节点引用或指针，
> 因为 `vector` 可能重新分配内存；项目里每次都重新用 `pool[下标]` 访问。

### 4.1 朴素匹配：最直接，也最适合当标准答案

文件：`src/matcher.cpp`，函数：`naiveSearch()`

```cpp
std::vector<MatchResult> naiveSearch(const std::string& text,
                                     const std::vector<std::string>& words,
                                     long* comparisons,
                                     std::vector<AlignStep>* trace,
                                     const RecordMask* mask) {
    std::vector<MatchResult> hits;              // 收集所有命中的关键词位置
    long cmp = 0;                               // 统计字符比较次数，供性能实验使用
    std::vector<int> t = utf8Decode(text);      // 文本按“字符”处理，不按字节处理

    for (std::size_t w = 0; w < words.size(); ++w) {
        std::vector<int> p = utf8Decode(words[w]); // 当前关键词也按字符处理
        if (p.empty() || p.size() > t.size()) continue; // 空词或过长词不可能命中

        for (std::size_t i = 0; i + p.size() <= t.size(); ++i) {
            std::size_t j = 0;                  // 每个文本起点都从模式串第 0 格开始
            while (j < p.size()) {
                ++cmp;                          // 真正比较一次字符
                bool eq = (t[i + j] == p[j]);   // 文本第 i+j 格对模式第 j 格
                record(trace, (int)w, (int)i, (int)j, eq, eq ? 0 : 1,
                       mask, (int)(i + j));      // 只在需要可视化时记录这一步
                if (!eq) break;                 // 有一位不同，整个起点失败
                ++j;                            // 这一位相同，继续比下一位
            }
            if (j == p.size()) {                // 模式串所有字符都比完了
                markHit(trace);                 // 告诉可视化“上一条记录是命中”
                MatchResult r;
                r.wordId = (int)w;              // 命中的关键词编号
                r.start  = (int)i;              // 命中起点就是当前对齐位置
                r.length = (int)p.size();        // 命中长度就是关键词长度
                hits.push_back(r);               // 保存这条命中
            }
        }
    }

    if (comparisons) *comparisons = cmp;         // 调用者需要时才回传比较次数
    normalizeMatches(hits);                      // 统一排序、去重，便于与 KMP/AC 对拍
    return hits;                                 // 返回全部命中
}
```

逐段解释：

| 代码                                | 作用                                                    |
| ----------------------------------- | ------------------------------------------------------- |
| `hits`、`cmp`                       | `hits` 保存结果，`cmp` 统计字符比较次数                 |
| `utf8Decode(text)`                  | 把 UTF-8 字节流变成字符编号数组，避免一个汉字占三个位置 |
| 外层 `for (w...)`                   | 每个关键词独立处理一次                                  |
| `p.empty()` / `p.size() > t.size()` | 空词或比文本长的词不可能命中，直接跳过                  |
| `for (i...)`                        | 枚举模式串在文本中的每一个可能起点                      |
| `j = 0`                             | 每次从模式串第 0 格重新比较                             |
| `++cmp`                             | 一次字符比较记一次操作                                  |
| `t[i+j] == p[j]`                    | 比较文本第 `i+j` 格和模式第 `j` 格                      |
| `record(...)`                       | 只记录可视化步骤；`trace == 0` 时不产生记录开销         |
| `if (!eq) break`                    | 当前起点失败，整体右移一格                              |
| `j == p.size()`                     | 模式全部比完，说明命中                                  |
| `start = i`、`length = p.size()`    | 记录命中起点与长度                                      |
| `normalizeMatches(hits)`            | 统一结果顺序并去重，便于对拍                            |

为什么它慢：

> 每个关键词都重新扫描全文，失配后只右移一格，刚刚比较过的内容下一次还要重比。

复杂度：设关键词数为 `N`，文本长度为 `n`，单词长度为 `m`，最坏为
`O(N·n·m)`。但它的逻辑最容易验证，所以被用作随机对拍的标准答案。

### 4.2 字典树：数组池 + 稀疏孩子表

文件：`src/trie.h`、`src/trie.cpp`

节点结构：

```cpp
struct TrieNode {
    std::map<int, int> child;  // 稀疏孩子表：字符编号 -> 子节点下标
    int fail;                  // AC 失配指针；建 Trie 时先保持 -1
    int outLink;               // 最近词尾后缀节点；用于快速枚举命中
    int wordId;                // 词尾标记：>=0 是关键词编号，-1 不是词尾
    int parent;                // 父节点下标，根节点为 -1
    int depth;                 // 深度；按字符计算，也等于当前前缀长度
    int ch;                    // 从父节点走到本节点经过的字符编号
};
```

数组池：

```cpp
class Trie {
private:
    std::vector<TrieNode> pool;   // pool[0] 固定是根
};
```

#### `Trie::insert()`

```cpp
int Trie::insert(const std::string& word, int wordId) {
    std::vector<int> chars = utf8Decode(word); // 把 UTF-8 字节转成字符编号
    int cur = 0;                                // 0 号节点固定是根

    for (std::size_t i = 0; i < chars.size(); ++i) {
        int cp = chars[i];                      // 当前要走的字符
        if (pool[cur].child.find(cp) == pool[cur].child.end()) {
            TrieNode n;                         // 没有这条边，就新建节点
            n.parent = cur;                     // 新节点挂在 cur 下面
            n.depth  = pool[cur].depth + 1;     // 深度比父节点多一层
            n.ch     = cp;                      // 记录到达本节点的字符
            pool.push_back(n);                  // 放进数组池
            pool[cur].child[cp] = (int)pool.size() - 1; // 父节点保存新节点下标
        }
        cur = pool[cur].child[cp];              // 沿着现有边或刚建的边继续向下
    }

    pool[cur].wordId = wordId;                  // 在终点盖章：这里是一个完整词
    return cur;                                 // 返回词尾节点下标
}
```

逐段解释：

- `utf8Decode(word)`：把一个字符串变成字符编号数组；
- `cur = 0`：从根节点出发；
- `child.find(cp)`：当前节点有没有字符 `cp` 的孩子；
- `TrieNode n`：创建一个新节点；
- `parent/depth/ch`：记录它是谁的子节点、深度和经过的字符；
- `pool.push_back(n)`：把新节点放进数组池；
- `child[cp] = pool.size()-1`：父节点保存新节点下标；
- `cur = child[cp]`：继续向下走；
- `wordId = wordId`：走完整词后，在终点盖章。

一个必须说明的细节：

> `push_back()` 可能让 `vector` 重新分配内存，所以不能提前保存
> `TrieNode&` 或指针后再使用；必须重新通过 `pool[cur]` 访问。

#### `Trie::find()` 和 `Trie::remove()`

```cpp
int Trie::find(const std::string& word) const {
    std::vector<int> chars = utf8Decode(word);
    int cur = 0;                                // 从根开始查
    for (std::size_t i = 0; i < chars.size(); ++i) {
        std::map<int, int>::const_iterator it = pool[cur].child.find(chars[i]); // 找这条边
        if (it == pool[cur].child.end()) return -1; // 中途没有孩子，词不存在
        cur = it->second;                       // 沿孩子下标继续走
    }
    return (pool[cur].wordId >= 0) ? cur : -1;  // 路径存在但没盖章，也不是词
}

bool Trie::remove(const std::string& word) {
    int id = find(word);                        // 先确认词存在
    if (id < 0) return false;                   // 不存在，删除失败
    pool[id].wordId = -1;                       // 只擦词尾标记，不释放节点
    return true;
}
```

删除只清 `wordId`，不释放节点：

> `at` 可能是 `ata` 的前缀。如果删除 `at` 时把节点删掉，后面的 `ata` 也会丢失。

复杂度：每次插入/查找沿 `m` 个字符走，每个节点用 `map` 找孩子，
约为 `O(m·log d)`，`d` 是该节点的分支数；空间是节点数和边数。

### 4.3 KMP 建 next：模式串自己和自己比

文件：`src/matcher.cpp`，函数：`kmpBuildNext()`

```cpp
std::vector<int> kmpBuildNext(const std::vector<int>& p,
                              std::vector<NextStep>* trace) {
    std::vector<int> next(p.size(), 0);         // next[0] 固定为 0
    if (trace) trace->clear();                  // 每次构造都重新收集过程记录

    int k = 0;                                  // 当前最长相等前后缀长度
    for (std::size_t i = 1; i < p.size(); ++i) {
        while (k > 0 && p[i] != p[k]) {          // 当前后缀接不上，沿 next 回退
            if (trace) {                         // 记录“回退前”的状态
                NextStep st;
                st.i = (int)i;
                st.k = k;
                st.equal = false;
                st.written = -1;                 // -1 表示这一步只回退，不写结果
                trace->push_back(st);
            }
            k = next[k - 1];                     // 跳到更短但仍相等的后缀
        }

        int kk = k;                              // 保存比较前的 k，供可视化讲解
        bool eq = (p[i] == p[k]);                // 尝试把当前字符接到前缀后面
        if (eq) ++k;                             // 相同则最长前后缀长度加一
        next[i] = k;                             // 当前格的结果此时才确定

        if (trace) {                             // 记录真正比较和写入 next 的一步
            NextStep st;
            st.i = (int)i;
            st.k = kk;
            st.equal = eq;
            st.written = k;
            trace->push_back(st);
        }
    }
    return next;
}
```

逐段解释：

- `next` 初始全 0，`next[0]` 永远为 0；
- `k` 是当前已经匹配上的前后缀长度；
- `i=1` 从模式第二个字符开始计算；
- `while (k>0 && p[i]!=p[k])`：当前后缀接不上，沿已经算出的 `next` 回退；
- `trace` 在 `k=next[k-1]` 之前记录，保存的是“回退前”的状态；
- `st.written=-1` 表示这一步只是回退，还没有写出 next；
- `eq = p[i]==p[k]`：回退结束后再比较一次；
- `if (eq) ++k`：相等则最长相等前后缀加一；
- `next[i]=k`：当前格的结果定下来；
- 第二个 `NextStep` 记录实际比较和写入结果。

为什么记录要在回退前：

> 如果先执行 `k=next[k-1]` 再记录，原来已经匹配了几格已经丢失，
> 页面就永远只能显示“右移 1 格”，看不出 KMP 的跳跃。

复杂度：`i` 单调前进，`k` 每次回退，累计回退次数不超过前进次数，
所以 next 构造是 `O(m)`。

### 4.4 KMP 匹配：文本指针不回退

文件：`src/matcher.cpp`，函数：`kmpSearch()`

```cpp
std::vector<MatchResult> kmpSearch(const std::string& text,
                                   const std::vector<std::string>& words,
                                   long* comparisons,
                                   std::vector<AlignStep>* trace,
                                   const RecordMask* mask) {
    std::vector<MatchResult> hits;              // 保存所有命中
    long cmp = 0;                               // 统计比较次数
    std::vector<int> t = utf8Decode(text);      // 文本先转成字符编号

    for (std::size_t w = 0; w < words.size(); ++w) {
        std::vector<int> p = utf8Decode(words[w]); // 当前模式串
        if (p.empty() || p.size() > t.size()) continue; // 不可能命中的边界

        std::vector<int> next = kmpBuildNext(p); // 每个词先建自己的 next
        int k = 0;                              // 当前已经匹配的模式长度

        for (std::size_t i = 0; i < t.size(); ++i) {
            while (k > 0 && t[i] != p[k]) {      // 失配，沿 next 回退模式指针
                ++cmp;                           // 这次比较也要计入操作数
                int nv = next[k - 1];            // 能复用的最长相等前后缀
                record(trace, (int)w, (int)i - k, k, false, k - nv,
                       mask, (int)i);            // 记录回退前的对齐和跳跃量
                k = nv;                          // 模式指针回退，文本 i 不动
            }

            ++cmp;                              // 回退结束后的正式比较
            bool eq = (t[i] == p[k]);            // 当前文本字符和模式字符比较
            record(trace, (int)w, (int)i - k, k, eq,
                   eq ? 0 : 1, mask, (int)i);    // 记录普通匹配/失配
            if (!eq) continue;                   // 仍然不等，文本前进一格

            ++k;                                // 这一格匹配，已匹配长度加一
            if (k == (int)p.size()) {            // 模式全部匹配
                markHit(trace);                 // 标记刚记录的步骤为命中
                MatchResult r;
                r.wordId = (int)w;
                r.start  = (int)i - k + 1;
                r.length = (int)p.size();
                hits.push_back(r);
                k = next[k - 1];                 // 允许下一次命中重叠
            }
        }
    }

    if (comparisons) *comparisons = cmp;          // 回传比较次数
    normalizeMatches(hits);                       // 与朴素、AC 统一排序
    return hits;
}
```

逐段解释：

- 外层 `w`：KMP 仍然是单模式算法，每个关键词独立扫描；
- `k`：当前模式串已经匹配的长度；
- `for i`：文本指针只从左到右前进；
- 第一个 `while`：失配时按 `next[k-1]` 回退模式位置；
- `record` 放在 `k=nv` 前：保留回退前的 `k` 和跳跃量 `k-nv`；
- 第二个比较：回退结束或本来就在根位置，再用当前文本字符比较一次；
- `k++`：当前格匹配成功，匹配长度加一；
- `k==p.size()`：模式整体命中；
- `start=i-k+1`：因为 `i` 是命中的最后一个文本位置；
- `k=next[k-1]`：继续寻找可能重叠的下一次命中；
- `normalizeMatches`：统一三种算法的输出顺序。

为什么不是所有场景都比朴素快：

> 当前基准是多关键词、短模式。KMP 仍要每个词扫一遍文本，还要建 next；
> 短模式下预处理和循环开销可能比朴素更大。KMP 的优势在长模式、
> 失配频繁且能大量复用已匹配前缀的场景。

复杂度：单个词预处理 `O(m)`，匹配 `O(n)`；N 个词总计
`O(N·(n+m))`。

### 4.5 AC 建失配指针：队列保证按层

文件：`src/ac.cpp`，函数：`AhoCorasick::buildFail()`

```cpp
void AhoCorasick::buildFail(std::vector<FailStep>* trace) {
    if (trace) trace->clear();                  // 可视化记录重新开始

    trie->setFail(0, 0);                        // 根的 fail 指向自己，方便循环处理
    trie->setOutLink(0, -1);                    // 根不是词尾，没有输出后继
    std::queue<int> q;                          // 队列保证按层构造

    const std::map<int, int>& rootKids = trie->children(0);
    for (std::map<int, int>::const_iterator it = rootKids.begin();
         it != rootKids.end(); ++it) {
        int v = it->second;                     // 根的一个直接孩子
        trie->setFail(v, 0);                    // 第一层：只有一个字符，退路是根
        trie->setOutLink(v, -1);                // 根不是词尾，没有输出链
        q.push(v);                              // 子节点入队，之后处理它的孩子
        if (trace) {
            FailStep fs;
            fs.u = 0;                           // 当前父节点是根
            fs.v = v;                           // 当前确定 fail 的节点
            fs.ch = utf8Encode(trie->node(v).ch); // 这条边上的字符
            fs.walk.push_back(0);               // 第一层只经过根
            fs.failTo = 0;                      // 结果指向根
            fs.queueLeft = (int)q.size() - 1;   // 记录队列剩余量
            trace->push_back(fs);
        }
    }

    while (!q.empty()) {
        int u = q.front();                      // 当前处理的父节点
        q.pop();

        const std::map<int, int>& kids = trie->children(u);
        for (std::map<int, int>::const_iterator it = kids.begin();
             it != kids.end(); ++it) {
            int c = it->first;                  // u -> v 的边字符
            int v = it->second;                 // 正在确定 fail 的孩子

            std::vector<int> walk;              // 记录沿 fail 向上找的路径
            int f = trie->node(u).fail;         // 从父节点的 fail 开始找
            walk.push_back(f);
            while (f > 0 && trie->childAt(f, c) < 0) {
                f = trie->node(f).fail;         // 当前候选没有 c 孩子，继续上跳
                walk.push_back(f);
            }

            int t = trie->childAt(f, c);        // 找到能接收 c 的孩子
            if (t >= 0 && t != v) f = t;        // 不能把节点指回自己
            else                  f = 0;         // 找不到就回到根

            trie->setFail(v, f);                // 正式写入 v 的 fail
            if (trie->node(f).wordId >= 0) {
                trie->setOutLink(v, f);         // f 是词尾，直接作为输出链
            } else {
                trie->setOutLink(v, trie->node(f).outLink); // 继承更短词尾
            }

            if (trace) {
                FailStep fs;
                fs.u = u;                       // 正在处理的父节点
                fs.v = v;                       // 当前孩子
                fs.ch = utf8Encode(c);           // 边字符
                fs.walk = walk;                 // 画浅红路径
                fs.failTo = f;                  // 画最终红色箭头
                fs.queueLeft = (int)q.size();   // 显示队列层序
                trace->push_back(fs);
            }

            q.push(v);                          // 孩子入队，之后再处理它的孩子
        }
    }
}
```

逐段解释：

- 根 `fail=0`：根没有真正的退路，指向自己方便循环；
- 根的直接孩子 `fail=0`：第一层前缀只有一个字符，没有更短真后缀；
- `q`：按层保存待处理节点；
- `u=q.front()/q.pop()`：取出当前父节点；
- `c`：父节点到孩子的边字符；
- `v`：正在确定 fail 的孩子；
- `f=fail[u]`：从父节点的退路开始找；
- `while f>0 && childAt(f,c)<0`：沿 fail 继续往上找；
- `walk`：把这一路上爬过的节点记下来，专供可视化；
- `t=childAt(f,c)`：找到能接收字符 `c` 的后继；
- `t!=v`：避免把节点错指回自己；
- `setFail(v,f)`：正式写入孩子的失配指针；
- `wordId>=0`：`f` 是词尾，直接作为输出链；
- 否则继承 `outLink[f]`：跳过非词尾节点，保存最近词尾后缀；
- `q.push(v)`：孩子入队，之后再处理它的孩子。

为什么必须按层：

> 算 `v` 的 fail 需要先知道父节点 `u` 的 fail。队列让浅层先完成，
> 所以轮到 `v` 时，依赖信息已经存在。

复杂度：每个节点入队/出队一次，每个孩子被处理一次；如果孩子表查找是
`O(log d)`（`map`），预处理约为 `O(节点数·log d)`；固定字符集且使用
O(1) 转移表时可写成 `O(总节点数)`。

#### 怎么读 AC 建失配的颜色

| 颜色/图形 | 含义                                                |
| --------- | --------------------------------------------------- |
| 橙色节点  | 当前从队列取出的父节点 `u`                          |
| 深红节点  | 正在确定 fail 的孩子 `v`                            |
| 浅红节点  | `walk` 中从 `fail[u]` 向上爬过的节点                |
| `→数字`   | 节点已经确定的固定 fail 编号                        |
| 红色箭头  | 本步实际经过的 `walk` 跳转，以及最后的 `v → failTo` |

看到橙色节点时，当前一定是“AC建失配”，不是普通 AC 匹配。

### 4.6 AC 匹配：文本单次扫描 + 输出链

文件：`src/ac.cpp`，函数：`AhoCorasick::match()`

```cpp
std::vector<MatchResult> AhoCorasick::match(const std::string& text,
                                            std::vector<MatchStep>* trace,
                                            long* jumps,
                                            const RecordMask* mask) const {
    std::vector<MatchResult> hits;              // 所有命中结果
    if (trace) trace->clear();                  // 清空上一次的过程记录
    long jumpCount = 0;                         // 统计失配跳转次数

    std::vector<int> chars = utf8Decode(text);  // 文本按字符扫描
    int cur = 0;                                // 当前自动机状态，从根开始

    for (std::size_t i = 0; i < chars.size(); ++i) {
        int cp = chars[i];                      // 当前读入的字符
        int from = cur;                         // 记录转移前状态

        while (cur > 0 && trie->childAt(cur, cp) < 0) {
            cur = trie->node(cur).fail;         // 接不上，沿失败指针回退
            ++jumpCount;                        // 记录一次失配跳转
        }

        int nxt = trie->childAt(cur, cp);       // 回退后看能否接上当前字符
        if (nxt >= 0) cur = nxt;                // 能接上就进入孩子节点

        bool keep = trace && (int)trace->size() < MAX_TRACE_STEPS; // 是否记录本步
        if (keep && mask && !mask->empty() &&
            ((int)i >= (int)mask->size() || !(*mask)[i])) {
            keep = false;                       // 超出选区的位置不记录
        }

        MatchStep st;
        if (keep) {
            st.pos  = (int)i;                   // 文本字符下标
            st.ch   = utf8Encode(cp);            // 当前字符
            st.from = from;                     // 跳转前节点
            st.to   = cur;                      // 跳转后节点
        }

        for (int v = cur; v >= 0; v = trie->node(v).outLink) {
            // 从当前节点沿输出链只访问“词尾后缀”，不是整条 fail 链
            if (trie->node(v).wordId >= 0) {
                MatchResult r;
                r.wordId = trie->node(v).wordId; // 哪个关键词命中
                r.length = trie->node(v).depth;  // 节点深度就是关键词长度
                r.start  = (int)i - r.length + 1;// 用终点反推起点
                hits.push_back(r);               // 保存命中
                if (keep) st.hits.push_back(r.wordId); // 同步给可视化
            }
        }

        if (keep) {
            for (int v = cur; ; v = trie->node(v).fail) {
                // 为了画图额外记录完整 fail 链；这遍只用于过程可视化
                st.chain.push_back(v);
                if (v == 0) break;
                if (trie->node(v).fail < 0) {
                    st.chain.push_back(0);
                    break;
                }
            }
            trace->push_back(st);
        }
    }

    normalizeMatches(hits);                     // 三种算法统一排序、去重
    if (jumps) *jumps = jumpCount;               // 性能实验需要时回传跳转次数
    return hits;                                // 返回所有命中
}
```

逐段解释：

- `cur=0`：从根开始；
- `for i`：文本字符从左到右，`i` 从不减少；
- `while (cur>0 && 没有 cp 孩子)`：当前自动机状态接不下，沿 fail 回退；
- `jumpCount`：统计失配跳转，供性能实验使用；
- `nxt=childAt(cur,cp)`：回退到能接收字符的状态后继续找孩子；
- `keep`：只有生成可视化时才记录，且不超过上限、遵守长文本选区；
- `st.from/st.to`：当前步转移前后状态；
- `for (v=cur; v>=0; v=outLink[v])`：命中枚举只走输出链；
- `wordId>=0`：当前后缀节点是词尾，产生命中；
- `length=depth`：节点深度等于该关键词字符长度；
- `start=i-length+1`：由当前文本终点反推起点；
- 第二个 `for (v=cur; ; v=fail[v])`：为了页面展示，额外记录完整 fail 链；
- `trace->push_back(st)`：把这一步交给网页回放。

#### fail 链和输出链

**fail 链**：

```text
cur → fail[cur] → fail[fail[cur]] → ... → root
```

它包含所有“既当前后缀、又是树中前缀”的节点，是回溯状态用的完整链。

**输出链**：

```text
cur → outLink[cur] → outLink[outLink[cur]] → ...
```

它跳过非词尾节点，只保留 fail 链上的词尾节点，用来枚举命中。

以词库 `data / ata / at / a`、当前节点 `data` 为例：

```text
fail 链：data → ata → a → root
输出链：data → ata → a
```

`at` 不在链上，因为 `data` 的后缀是 `ata / ta / a`，不是 `at`。

“词尾祖先”更准确的说法是：

> fail 链上带有 `wordId` 的后缀节点

不是字典树 `parent` 指针意义上的父节点祖先。

为什么页面记录的是 fail 链：

> C++ 实际计算命中时使用 outLink，保证不会每步爬完整条 fail 链；
> 可视化为了展示“当前状态有哪些后缀候选”，在 trace 非空时额外走一遍 fail 并记录。
> 这段额外遍历不进入纯匹配性能计时。

复杂度：

- 文本扫描：`O(n)`；
- 输出链枚举：与命中数 `z` 成正比；
- 总体：`O(n+z)`；
- 当前孩子表使用 `map`，严格实现口径还要加上每次转移的 `O(log d)` 查找，
  固定小字符集的常规复杂度表述写 `O(n+z)`，答辩时说明实现细节即可。

### 4.7 随机对拍：证明三个实现结果一致

文件：`src/bench.cpp`，函数：`crossCheck()`

核心逻辑：

```cpp
for (int r = 0; r < rounds; ++r) {
    随机生成小词库;
    随机生成小文本;

    auto ref = naiveSearch(text, words);
    auto kmp = kmpSearch(text, words);

    Trie trie;
    // 插入随机词
    AhoCorasick ac(trie);
    ac.buildFail();
    auto acc = ac.match(text);

    if (ref != kmp || ref != acc) return false;
}
return true;
```

逐段解释：

- 随机词只使用少量字母，故意制造公共前后缀；
- `naiveSearch` 结果作为标准答案；
- KMP 和 AC 独立运行；
- `sameHits` 逐条比较 `wordId/start/length`，不比较总数；
- 当前固定 `3000` 组，全部一致；
- 随机种子固定，出问题可以复现。

## 七、常见追问

### Q1：为什么 AC 的复杂度是 O(n+z)，不是 O(n·m)？

> n 是文本长度，z 是命中数。文本从头到尾只走一遍，是 O(n)；
> 命中检查靠输出链直接跳到下一个词尾祖先，代价和命中数成正比，是 O(z)。
> 关键是文本指针不回退。

### Q2：为什么建失配指针必须用队列？

> 算一个节点的失配指针要用到父节点或更浅层节点的结果。
> 队列按层遍历，能保证轮到子节点时，父层已经算完。

### Q3：为什么走了当前节点还要沿失配链检查命中？

> 失配链上的每个节点都代表当前已匹配串的一个真后缀。
> 例如文本走到 `data` 结尾时，`ata` 也恰好结束，只检查当前节点会漏掉它。
> C++ 实际用 `outLink` 直接跳到词尾节点；页面为了教学会额外画出完整 fail 链，
> 但真正的命中枚举计算和性能计时走的是输出链。

### Q4：KMP 在性能表里为什么没有明显快于朴素匹配？

> 这组实验是多关键词匹配，KMP 仍然是“每个词扫一遍文本”，而且每个词都要先建
> next 数组。关键词又很短，预处理和循环开销会占较大比例。
> KMP 的价值主要体现在长模式串、失配频繁且能大量复用已匹配前缀的场景。
> 项目保留它，是为了和 AC 的“一次扫描”形成结构上的对照，不是强行证明它在所有数据上都最快。

### Q5：为什么用网页显示？这还算 C++ 项目吗？

> 网页是 C++ 程序生成的一个静态文件，算法、数据和对拍全部在 C++ 中完成，
> 浏览器只负责绘制和交互。生成的文件不联网，也不需要安装额外环境。

### Q6：中文怎么处理？

> 先把 UTF-8 字节流解码成字符编号，再建树和匹配。一个汉字是一个字符、一个节点。
> 早期按字节处理时，一个汉字占三个下标，树上会出现半个字符，位置也会错位。

### Q7：关键词太长时为什么曾经错位？

> 对齐视图最初只按文本窗口裁剪，模式串没有跟着窗口裁剪。
> 当关键词头部落在窗口左侧时，偏移量算成负数，整条模式串被顶到最左边。
> 修复时分别计算窗口左右边界对应模式串的第几格，只绘制落在窗口内的部分，
> 并让两行格子弹性均分，避免横向溢出。

### Q8：超过 2 万字符为什么只记录命中附近？

> 每一步都要保存状态，长文本会产生大量过程对象，网页体积和浏览器内存都承受不了。
> 2 万字符以内记录全程；超过后只记录命中附近的区域，但命中清单仍能跳到对应位置。
> 这是“完整可视”和“可打开、可操作”之间的取舍。

### Q9：一个人做工作量够吗？

> 项目源代码 3249 行，包含数据读写、UTF-8、字典树、三种匹配算法、
> 两种构造过程可视化、性能实验、自动对拍和课程文档。
> 我把主要时间放在可视化暴露出的边界问题和验证上，不是只写了三个算法函数。

### Q10：最值得讲的调试经历是什么？

> KMP 过程记录时机的问题。算法结果一直正确，但页面看不出 KMP 的特点。
> 最后定位到“记录发生在回退之后”，把记录移到回退之前才解决。
> 另外还有 UTF-8 按字节导致中文错位、长关键词对齐溢出、长文本记录量过大等问题，
> 都能在 git 提交记录里看到逐步修改的过程。

### Q11：项目还有哪些不足？

> 一是字典树很大时构造演示会拥挤，目前用节点数 50 作为可读性提示；
> 二是超过 2 万字符后中间过程不完整；
> 三是词库目前只从文本文件加载，没有做增量更新。
> 这些是明确的后续改进方向，不影响当前版本的演示和正确性验证。

### 二、数据结构

#### Q6　为什么用字典树而不是把所有关键词排成数组

> 字典树让有共同前缀的词共享路径。查询一个词只和它的长度有关，
> 词库越大，空间和公共前缀的复用越明显。

#### Q7　节点为什么用数组池和整数下标

> 节点集中放在 vector 里，用下标互相引用，不手动 new/delete。
> 这样不会内存泄漏，也不会因为节点扩容产生野指针。

#### Q8　孩子表为什么用 map

> 每个节点的分支通常很少，固定开很大的字符数组会浪费空间。
> map 还能按字符顺序遍历，调试树结构比较稳定。

#### Q9　为什么词库去重用 unordered_set

> 逐条两两比较是 O(n²)，哈希表平均 O(1) 判断重复，
> 词库大时更适合；代价是需要额外的哈希存储。

#### Q10　队列在项目里做什么

> AC 自动机的失配指针必须按层计算。队列做 BFS，保证父节点和浅层节点先处理完。

#### Q11　输出链 outLink 是什么

> 它指向沿 fail 链最近的词尾祖先。命中时不用一个节点一个节点爬完整条 fail 链。

#### Q12　为什么删除关键词只清词尾标记

> 一个词可能是另一个词的前缀。删 `at` 时如果连节点一起删，下面的 `ata` 也会丢。

### 三、KMP 与 AC 自动机

#### Q13　next 数组表示什么

> `next[i]` 是模式串前 `i+1` 个字符中，最长相等前后缀的长度。

#### Q14　KMP 为什么能不回退文本指针

> 失配时利用已经匹配过的前缀信息，把模式串退到 next 指定的位置，
> 文本下标继续向前，不回到起点重比。

#### Q15　你的 KMP 可视化修过什么 bug

> 最初记录写在回退之后，页面永远显示右移一格。把记录移到回退前，
> 才能保存“已匹配几格、要退到哪里”的关键状态。

#### Q16　为什么本轮 KMP 不一定比朴素快

> 这是多关键词、短模式测试。KMP 仍要逐词扫描并构建 next，预处理和循环开销明显。
> KMP 的优势在长模式串和大量可复用前缀的场景，不是所有输入都最快。

#### Q17　AC 自动机解决了什么问题

> 把“每个关键词扫一遍文本”变成“文本扫一遍，同时在字典树上转移”。

#### Q18　失配指针指向什么

> 指向当前节点所代表前缀的最长真后缀，而且这个后缀必须是树中某个节点的前缀。

#### Q19　为什么 fail 必须按层建

> 计算子节点时要用父节点或更浅层节点的 fail，BFS 能保证依赖已经就绪。

#### Q20　只看当前节点为什么会漏命中

> 当前节点不是词，但它的 fail 链上可能有词尾。例如走到 `data` 末尾时，
> `ata` 也可能同时命中。

#### Q21　为什么 AC 匹配是 O(n+z)

> 文本只扫描一遍是 O(n)；输出链枚举命中是 O(z)，与关键词总数 N 无关。

#### Q22　没有输出链会怎样

> 命中检查要沿完整 fail 链爬，最坏会退化成 O(n·m)。

#### Q31　性能实验为什么要两组

> 一组放大文本，一组放大词库。第二组才能证明 AC 的匹配耗时基本不随词库大小增长。

#### Q32　性能数字能不能直接背

> 毫秒值会随机器波动，应该背趋势和比例。当前一次测试中，
> 1000 词时朴素约 2.97ms、AC 约 0.020ms，约 151 倍。

#### Q33　测试报告为什么是自测加对拍

> 这是个人项目，没有第二名成员。用另一种独立实现做标准答案逐条对拍，
> 比同一个人重复点按钮更接近交叉验证，而且可以重复执行。

### 六、AI 辅助开发

#### Q34　代码是不是 AI 写的

> 项目使用了 AI 辅助，但需求和取舍、运行验证、问题复现、最终确认由我完成。
> 我能解释每个核心结构和关键 bug 的修改过程，git 记录也能看到迭代过程。

#### Q35　AI 最容易在哪些地方出错

> 算法主流程可能看起来正确，但边界条件、记录时机、字符编码和 UI 对齐容易出问题。
> 因此每次修改都必须跑三种算法、边界数据和浏览器实测。

#### Q36　你怎么使用 AI 才没有失去掌控

> 先写需求和验证标准，再让 AI 解释或生成小范围修改；
> 每次只改一个可验证问题，最后自己比较 diff、编译、运行和检查结果。

### 七、压力追问

#### Q37　这些算法网上都有，你的创新是什么

> 算法本身是公开的。我的工作是把三种实现统一结果、加入 KMP 和 AC 的构造过程可视化、
> 处理 UTF-8 和长文本边界、实现重叠等比例分色，并用 3000 组对拍验证。

#### Q38　如果词库增加到十万条会怎样

> 字典树结构仍可用，但 map 和字符表遍历、预处理时间会成为主要开销；
> 还可能需要改进孩子表的存储、分批构建或更紧凑的自动机表示。

#### Q39　如果页面卡住，你现场怎么排查

> 先看控制台是否生成成功和命中数量，再检查网页是否过大、过程记录是否超限，
> 最后用较小词库或短文本重现，定位在数据、算法还是显示层。

#### Q40　这个项目你最想保留的工程经验是什么

> 结果正确不等于过程正确。算法、记录、显示分开以后，才能分别验证；
> 对拍和可观察的过程，比“看代码觉得没问题”可靠得多。
