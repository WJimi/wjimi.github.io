# 答辩汇报提纲

这份材料用于 10 分钟左右的课程设计答辩。每个问题先准备“一句话版本”，
老师继续追问时再展开。答辩时先把机制和证据讲清楚，不必一次把所有细节说完。

---

## 一、开场 60 秒

可以按下面四句介绍：

> 1. 我做的是《字符串多模式匹配综合实验平台》。输入一个关键词库和一段文本，
>    找出文本中全部关键词出现的位置，并展示算法是怎么一步一步得到结果的。
>
> 2. 项目以字典树为主结构，在字典树上构建 AC 自动机的失配指针；
>    同时实现朴素匹配和 KMP 作为对照。
>
> 3. 控制台只负责加载词库、导入文本和生成网页。算法全部由 C++ 完成，
>    网页负责把字典树、匹配过程、命中结果和性能数据画出来。
>
> 4. 当前默认词库 12 个词、综合文本 126 字符时命中 47 处；3000 组随机对拍中，
>    三种算法的结果逐条一致。

如果老师关注性能，再补一句：

> 在本次两组实验中，词库从 10 个词增加到 1000 个词，
> 朴素匹配从约 0.030 ms 增加到 2.966 ms，AC 自动机从约 0.015 ms 到 0.020 ms，
> 最后朴素匹配约为 AC 的 151 倍。具体数字以现场生成的性能页为准。

## 二、项目结构

系统分成三层：

| 层 | 做什么 | 主要文件 |
| --- | --- | --- |
| 数据层 | 读词库、处理 UTF-8、去重、保存文本 | `wordbank.*`、`utf8.*`、`data/` |
| 算法层 | 朴素匹配、KMP、字典树、AC 自动机、对拍 | `matcher.*`、`trie.*`、`ac.*`、`bench.*` |
| 表现层 | 控制台调度、生成自包含网页 | `main.cpp`、`visualize.*` |

一句话：

> 算法层只产生“命中了什么、过程中走了哪一步”，显示层只负责把数据画出来。
> 两边通过 `model.h` 里的公共结构传递数据，所以换可视化方式不需要改算法。

### 2.1 可视化是怎么实现的？`visualize.cpp` 为什么这么长？

老师可能的问法：

> 可视化是怎么实现的？`visualize.cpp` 代码这么长，是往 HTML 里插入变量吗？这个文件你吃透了吗？

一句话回答：

> 不是 C++ 在运行时控制浏览器，而是 C++ 先把字典树、命中结果和过程记录序列化成
> JavaScript 数据对象，再和 HTML/CSS/JS 模板一起写进一个自包含文件。浏览器打开后，
> 才由页面里的 JS 完成播放、单步和绘制。

完整数据流：

```text
Trie / matcher / ac / bench
        ↓
公共结构 VizData（model.h）
        ↓
C++ 序列化成 const DATA = { ... }
        ↓
嵌入 HTML/CSS/JS 原始字符串
        ↓
写出 output/report.html
        ↓
浏览器执行 JS，完成绘制和交互
```

关键代码位置：

| 位置 | 作用 |
| --- | --- |
| `visualize.cpp` 的 `emitSvg()` | 递归计算树节点坐标，写出 SVG 的边、节点、词尾和 fail 编号 |
| `emitNodes()`、`emitAcSteps()`、`emitAlignSteps()`、`emitHits()` | 把 C++ 过程记录变成 JS 可以直接读的数组 |
| `emitNextSteps()`、`emitFailSteps()`、`emitNextArrays()` | 输出两种构造过程的数据 |
| `emitBench()`、`emitScale()` | 输出性能实验数据 |
| `kHtmlHead` | HTML 头部、CSS 和页面结构 |
| `kHtmlTail` | 浏览器端 JS：切换算法、播放、单步、画树、画文本、画命中 |
| `Visualizer::exportHtml()` | 最终把模板、`const DATA` 和所有数据写成一个文件 |

为什么文件长：

- `visualize.cpp` 当前约 **1429 行**；
- 其中约 **1081 行**位于两个 `R"HTML(... )HTML"` 原始字符串里，是 CSS/HTML/JS 模板；
- 纯 C++ 的序列化、树布局和文件写出逻辑约 **348 行**；
- 文件长不代表算法难，主要是因为把整套前端样式和交互都内嵌进一个自包含文件，
  避免依赖服务器、框架和网络。

可以直接这样说明自己的掌握程度：

> 我能从 `VizData` 的入口讲到 HTML 的出口。真正需要掌握的不是背下每一条 CSS，
> 而是三件事：第一，C++ 和页面之间传递哪些字段；第二，`step` 如何驱动页面状态；
> 第三，树、文本、next 和性能表分别由哪组函数渲染。页面出现问题时，我能判断
> 是数据记录错了、序列化转义错了，还是浏览器渲染错了。

两个容易答错的细节：

- `emitSvg()` 负责树形结构；页面上的失配箭头不是一棵静态 SVG 全部画满，
  而是由 JS 在每一步根据 `chain` 动态重画当前真正走过的箭头；
- 文本进入 HTML 和进入 JS 字符串使用不同转义函数。`escHtml()` 处理标签，
  `escJs()` 防止 `</script>` 和实体解码造成字符位置错位。

### 2.3 标准库使用边界

老师的问法：

> 哪些是直接引用了标准库的东西？讲解一下。

| 标准库组件 | 主要用途 | 项目位置 |
| --- | --- | --- |
| `std::string` | 保存关键词、文本、路径、页面字符串 | 全项目 |
| `std::vector` | 节点池、命中结果、过程步骤、性能结果 | `trie.*`、`model.h`、`bench.*` |
| `std::map<int,int>` | 每个 Trie 节点的稀疏孩子表 | `trie.h` |
| `std::unordered_set<std::string>` | 词库去重 | `wordbank.cpp` |
| `std::queue<int>` | AC 失配指针的 BFS | `ac.cpp` |
| `std::sort`、`std::unique` | 命中结果统一排序、去重 | `matcher.cpp` |
| `std::find`、`std::max`、`std::min` | 查找、树布局边界、采样长度 | 多个模块 |
| `std::ifstream`、`std::ofstream` | 读数据文件、写 HTML | `wordbank.cpp`、`main.cpp`、`visualize.cpp` |
| `std::ostringstream` | 拼接字符串和数字 | `main.cpp`、`visualize.cpp` |
| `std::chrono::steady_clock` | 性能实验计时 | `bench.cpp` |
| `std::rand`、`std::srand` | 可复现随机测试 | `bench.cpp` |
| `std::stoi`、`std::atoi`、`std::to_string` | 字符串与整数转换 | `main.cpp` |

`std::` 是 C++ 标准库的命名空间。例如 `std::vector` 表示“标准库里的 `vector`”，
不是本项目自己写的类。项目没有写入 `using namespace std;`，所以标准库名字前保留
`std::`，避免和项目里的 `Trie`、`MatchResult` 等名称冲突。

需要特别区分：

- `std::map` 是有序关联容器，常见实现使用平衡树；
- `std::unordered_set` 是哈希容器，平均 O(1) 查找，但无序；
- `<windows.h>`、`<direct.h>`、`<io.h>`、`<dirent.h>`、`<sys/stat.h>`、
  `<unistd.h>` 属于操作系统/平台 API，**不是 C++ 标准库**；
- 项目没有第三方 C++ 库，核心算法全部由项目代码实现。

## 三、涉及的数据结构

被问到“用了哪些数据结构”时，按“结构 → 解决什么问题”回答：

| 数据结构 | 项目中的用途 | 为什么用它 |
| --- | --- | --- |
| 字典树 Trie | 保存全部关键词，共享公共前缀 | 几千个词可以合并成一棵树，不必存几千条独立串 |
| 数组池 + 整数下标 | 字典树节点存储 | 节点集中在 `vector` 中，节点之间用下标关联，避免 `new/delete` 和野指针 |
| 有序映射 `std::map` | 每个节点的孩子表 | 每个节点的分支通常很少，比固定开 256 个格子省空间，还能按字符有序遍历 |
| 队列 | 按层构建 AC 失配指针 | 算子节点要用父节点的结果，先进先出正好保证父层先处理完 |
| 哈希表 `unordered_set` | 词库去重 | 平均 O(1) 判断重复，避免逐条两两比较 |
| 动态数组 `vector` | 节点池、命中结果、过程记录 | 规模事先未知，可以自动扩容 |
| 排序与去重 | 统一三种算法的命中结果 | 输出顺序一致，才能逐条对拍 |
| 输出链 `outLink` | 从一个词尾直接跳到下一个词尾祖先 | 让 AC 匹配阶段达到 O(n+z)，不必每步爬完整条失配链 |

对应的标准回答：

> 主结构是字典树，节点用数组池保存，孩子表用有序映射。
> 建失配指针用队列做按层遍历，词库去重用哈希表，过程记录和命中结果用动态数组。
> 三种算法的结果统一排序去重后逐条对拍。

### 3.1 字典树的结构：逻辑上是什么，最底层是什么？

老师可能的问法：

> 字典树的结构是什么？细化到最基本的数据结构又是什么？

标准回答：

> 逻辑上，字典树是一棵有根前缀树；物理上，它不是指针树，而是
> `vector<TrieNode>` 数组池加上每个节点的 `map<int,int>` 稀疏邻接表。
> 每个字符通过“字符编号 → 子节点下标”挂在当前节点下面。

节点结构在 `src/trie.h`：

```cpp
struct TrieNode {
    std::map<int, int> child;  // 字符编号 -> 子节点下标
    int fail;                  // AC 失配指针
    int outLink;               // 最近词尾祖先
    int wordId;                // 词尾标记
    int parent;                // 父节点下标
    int depth;                 // 深度
    int ch;                    // 到达本节点的字符
};
```

数组池在 `Trie` 类：

```cpp
std::vector<TrieNode> pool;   // pool[0] 固定为根节点
```

插入时在 `Trie::insert()` 中：

1. 先把关键词解码成字符编号；
2. 从 `pool[0]` 根节点出发；
3. 用 `child.find(cp)` 查当前字符的孩子；
4. 没有孩子就 `pool.push_back()` 新建节点；
5. 用 `child[cp] = 新节点下标` 建立边；
6. 最后一个节点写 `wordId`。

所以“最基本的数据结构”可以分三层回答：

1. **逻辑层**：树，每个节点代表从根到它的前缀；
2. **存储层**：动态数组 + 有序映射，分别来自 `std::vector` 和 `std::map`；
3. **引用层**：节点之间用整数下标，不用 `TrieNode*` 指针。

`std::map` 的底层实现通常是有序平衡树，但 C++ 标准只规定它是
有序关联容器，不强制某一种具体实现；答辩时不要说成“标准保证一定是红黑树”。

为什么适合这个项目：

- 公共前缀只存一份；
- 每个节点的分支通常很少，`map` 比固定大数组省空间；
- 整数下标稳定，不会出现野指针；
- `fail`、`outLink`、`wordId` 可以直接挂在节点上，后续算法不需要再建映射。

### 3.2 `unordered_set`、数组池和“排序去重”的准确关系

老师的问法里可能把“排序去重”和 `unordered_set` 混在一起，先纠正：

> 词库去重用的是 `unordered_set`；三种算法的命中结果排序去重用的是
> `std::sort + std::unique`。两者用途不同。

#### `unordered_set` 在哪里

位置：`src/wordbank.cpp`，`WordBank::load()`。

```cpp
std::unordered_set<std::string> seen;
if (seen.find(line) != seen.end()) { ++dup; continue; }
seen.insert(line);
words.push_back(line);
```

它是最基础的数据结构：

- 哈希表；
- 存储已经见过的字符串；
- 平均 O(1) 查找和插入；
- 无序，所以不负责保持原文件顺序；
- 真正的词库顺序保存在旁边的 `std::vector<std::string> words`。

如果逐条与 `words` 比较，去重是 O(n²)；哈希表把平均代价降到接近 O(n)。

#### 命中结果为什么不是用它

位置：`src/matcher.cpp` 的 `normalizeMatches()`。

```cpp
std::sort(hits.begin(), hits.end(), ...);
hits.erase(std::unique(hits.begin(), hits.end(), ...), hits.end());
```

因为三种算法的命中结果必须按统一顺序逐条比较。这里需要“先有序，再去相邻重复”，
所以用 `sort + unique`，而不是哈希表。

#### 数组池在哪里

| 位置 | 内容 |
| --- | --- |
| `src/trie.h` 的 `Trie` 私有成员 | `std::vector<TrieNode> pool` |
| `src/trie.cpp` 的 `Trie::Trie()` | `pool.push_back(TrieNode())` 创建根节点 |
| `src/trie.cpp` 的 `Trie::insert()` | 新节点追加到 `pool`，父节点的 `child` 保存新下标 |
| `src/trie.cpp` 的 `Trie::node()`、`childAt()` | 通过节点编号访问池中数据 |

数组池的本质：

> 把很多节点放进一个连续动态数组，节点之间不保存内存地址，只保存数组下标。

这样做的直接收益：

- 不需要 `new/delete`；
- 不会出现悬空指针；
- 调试时可以直接查看 `pool[17]`；
- `vector` 扩容不会改变节点编号，只可能让节点在内存中的地址变化。

这里要能答出一个陷阱：

> `pool.push_back()` 之后不能继续使用之前保存的节点引用或指针，
> 因为 `vector` 可能重新分配内存；项目里每次都重新用 `pool[下标]` 访问。

## 四、关键算法

### 4.1 字典树插入

```cpp
int cur = 0;
for (每个字符 cp) {
    if (当前节点没有 cp 这个孩子)
        新建节点并挂到 cur 下面;
    cur = child[cur][cp];
}
wordId[cur] = 词编号;
```

一句话：

> 节点代表从根到它的路径，也就是一个前缀；走完关键词后在终点盖“词尾章”。

为什么不能靠“是不是叶子”判断词尾：

> `at` 下面还可以挂 `ata`，此时 `at` 的节点不是叶子，但它仍然是一个完整关键词。

删除为什么只擦标记：

> 删 `at` 时如果连节点一起删，挂在该节点下面的 `ata` 也会丢失。所以只把
> `wordId` 改回 `-1`，节点保留。

### 4.2 KMP 的 next 数组

```cpp
std::vector<int> next(p.size(), 0);
int k = 0;
for (int i = 1; i < p.size(); ++i) {
    while (k > 0 && p[i] != p[k]) k = next[k - 1];
    if (p[i] == p[k]) ++k;
    next[i] = k;
}
```

一句话：

> `next[i]` 是模式串前 `i+1` 个字符中，最长相等前后缀的长度。

用 `abcabcabd` 举例：

> 算到第 7 个字符时，前面已经有 `abcabc`，长度为 6 的前后缀相同，
> 下一次失配可以直接保留这段信息，不把模式串移回最左边重比。

### 4.3 KMP 失配处理

```cpp
while (k > 0 && text[i] != pattern[k]) {
    int newK = next[k - 1];
    recordBeforeFallback(k, newK);  // 关键：先记录，再回退
    k = newK;
}
```

答辩时最值得讲的一个真实问题：

> 第一版把过程记录写在回退之后，结果页面上永远显示“模式串右移 1 格”，
> 看起来和朴素算法没有区别。原因是回退完成后，原来“已经匹配了几格”已经丢失。
> 把记录点移到回退前，页面才显示出 KMP 真正的跳跃。

这件事说明：

> 结果正确不等于过程记录正确。可视化调试还要检查“记录的是不是关键动作发生的那一刻”。

### 4.4 AC 自动机建失配指针

```cpp
int f = fail[u];
while (f > 0 && 没有字符 c 的孩子)
    f = fail[f];
int t = child(f, c);
if (t 存在且 t != v) fail[v] = t;
else                 fail[v] = 0;
```

一句话：

> 给每个树节点找一条退路：当前字符接不下去时，沿失配指针往回跳，
> 不再把文本重新读一遍。

为什么必须按层：

> 计算子节点的 `fail` 要用父节点或更浅层节点的 `fail`。队列按层推进，
> 用到时这些值一定已经算好。

### 4.5 输出链和 O(n+z)

```cpp
if (节点 f 是词尾)
    outLink[v] = f;
else
    outLink[v] = outLink[f];
```

一句话：

> 走到节点后不能只看脚下；失配链上任何一个词尾祖先都可能对应一次命中。
> 输出链直接指向最近的词尾祖先，检查命中时一个词一个词地跳。

复杂度：

> 文本扫描 O(n)，沿输出链枚举命中 O(z)，合起来 O(n+z)，与关键词个数 N 无关。

### 4.6 随机对拍

> 朴素算法最容易写对，所以把它当标准答案。随机生成小词库和随机文本，
> 让 KMP 和 AC 各跑一遍，逐条比较关键词编号、起点和长度。
> 当前固定跑 3000 组，全部一致。

## 七、常见追问

### Q1：为什么 AC 的复杂度是 O(n+z)，不是 O(n·m)？

> n 是文本长度，z 是命中数。文本从头到尾只走一遍，是 O(n)；
> 命中检查靠输出链直接跳到下一个词尾祖先，代价和命中数成正比，是 O(z)。
> 关键是文本指针不回退。

### Q2：为什么建失配指针必须用队列？

> 算一个节点的失配指针要用到父节点或更浅层节点的结果。
> 队列按层遍历，能保证轮到子节点时，父层已经算完。

### Q3：为什么走了当前节点还要沿失配链检查命中？

> 失配链上的每个节点都代表当前已匹配串的一个真后缀。
> 例如文本走到 `data` 结尾时，`ata` 也恰好结束，只检查当前节点会漏掉它。

### Q4：KMP 在性能表里为什么没有明显快于朴素匹配？

> 这组实验是多关键词匹配，KMP 仍然是“每个词扫一遍文本”，而且每个词都要先建
> next 数组。关键词又很短，预处理和循环开销会占较大比例。
> KMP 的价值主要体现在长模式串、失配频繁且能大量复用已匹配前缀的场景。
> 项目保留它，是为了和 AC 的“一次扫描”形成结构上的对照，不是强行证明它在所有数据上都最快。

### Q5：为什么用网页显示？这还算 C++ 项目吗？

> 网页是 C++ 程序生成的一个静态文件，算法、数据和对拍全部在 C++ 中完成，
> 浏览器只负责绘制和交互。生成的文件不联网，也不需要安装额外环境。

### Q6：中文怎么处理？

> 先把 UTF-8 字节流解码成字符编号，再建树和匹配。一个汉字是一个字符、一个节点。
> 早期按字节处理时，一个汉字占三个下标，树上会出现半个字符，位置也会错位。

### Q7：关键词太长时为什么曾经错位？

> 对齐视图最初只按文本窗口裁剪，模式串没有跟着窗口裁剪。
> 当关键词头部落在窗口左侧时，偏移量算成负数，整条模式串被顶到最左边。
> 修复时分别计算窗口左右边界对应模式串的第几格，只绘制落在窗口内的部分，
> 并让两行格子弹性均分，避免横向溢出。

### Q8：超过 2 万字符为什么只记录命中附近？

> 每一步都要保存状态，长文本会产生大量过程对象，网页体积和浏览器内存都承受不了。
> 2 万字符以内记录全程；超过后只记录命中附近的区域，但命中清单仍能跳到对应位置。
> 这是“完整可视”和“可打开、可操作”之间的取舍。

### Q9：一个人做工作量够吗？

> 项目源代码 3249 行，包含数据读写、UTF-8、字典树、三种匹配算法、
> 两种构造过程可视化、性能实验、自动对拍和课程文档。
> 我把主要时间放在可视化暴露出的边界问题和验证上，不是只写了三个算法函数。

### Q10：最值得讲的调试经历是什么？

> KMP 过程记录时机的问题。算法结果一直正确，但页面看不出 KMP 的特点。
> 最后定位到“记录发生在回退之后”，把记录移到回退之前才解决。
> 另外还有 UTF-8 按字节导致中文错位、长关键词对齐溢出、长文本记录量过大等问题，
> 都能在 git 提交记录里看到逐步修改的过程。

### Q11：项目还有哪些不足？

> 一是字典树很大时构造演示会拥挤，目前用节点数 50 作为可读性提示；
> 二是超过 2 万字符后中间过程不完整；
> 三是词库目前只从文本文件加载，没有做增量更新。
> 这些是明确的后续改进方向，不影响当前版本的演示和正确性验证。

### 一、项目与需求

#### Q1　一句话介绍项目

> 输入一个词库和一段文本，使用朴素匹配、KMP、AC 自动机找出全部关键词位置，
> 并把运行过程和 next、失配指针的构造过程导出为可交互网页。

#### Q2　为什么选这个题目

> 它能把树、队列、哈希表、字符串匹配和复杂度分析放进同一个工程。
> 同一份数据还能让三种算法互相对拍，结果不是只能“看起来对”。

#### Q3　项目的输入输出是什么

> 输入是 UTF-8 词库和文本；输出是命中清单、高亮文本、过程动画、
> 两组性能实验和 3000 组随机对拍结果。

#### Q4　一个人完成，工作量在哪里

> 不只是三个算法函数，还包括 UTF-8 按字符处理、词库去重、数组池字典树、
> 过程记录、自包含网页、长文本策略、性能实验、自动对拍和课程文档。

#### Q5　项目的边界是什么

> 当前只从文本文件加载词库；超过 2 万字符只记录命中附近；字典树超过 50 个节点时，
> AC 建失配仍能运行，但页面会提示可读性下降。

---

### 二、数据结构

#### Q6　为什么用字典树而不是把所有关键词排成数组

> 字典树让有共同前缀的词共享路径。查询一个词只和它的长度有关，
> 词库越大，空间和公共前缀的复用越明显。

#### Q7　节点为什么用数组池和整数下标

> 节点集中放在 vector 里，用下标互相引用，不手动 new/delete。
> 这样不会内存泄漏，也不会因为节点扩容产生野指针。

#### Q8　孩子表为什么用 map

> 每个节点的分支通常很少，固定开很大的字符数组会浪费空间。
> map 还能按字符顺序遍历，调试树结构比较稳定。

#### Q9　为什么词库去重用 unordered_set

> 逐条两两比较是 O(n²)，哈希表平均 O(1) 判断重复，
> 词库大时更适合；代价是需要额外的哈希存储。

#### Q10　队列在项目里做什么

> AC 自动机的失配指针必须按层计算。队列做 BFS，保证父节点和浅层节点先处理完。

#### Q11　输出链 outLink 是什么

> 它指向沿 fail 链最近的词尾祖先。命中时不用一个节点一个节点爬完整条 fail 链。

#### Q12　为什么删除关键词只清词尾标记

> 一个词可能是另一个词的前缀。删 `at` 时如果连节点一起删，下面的 `ata` 也会丢。

---

### 三、KMP 与 AC 自动机

#### Q13　next 数组表示什么

> `next[i]` 是模式串前 `i+1` 个字符中，最长相等前后缀的长度。

#### Q14　KMP 为什么能不回退文本指针

> 失配时利用已经匹配过的前缀信息，把模式串退到 next 指定的位置，
> 文本下标继续向前，不回到起点重比。

#### Q15　你的 KMP 可视化修过什么 bug

> 最初记录写在回退之后，页面永远显示右移一格。把记录移到回退前，
> 才能保存“已匹配几格、要退到哪里”的关键状态。

#### Q16　为什么本轮 KMP 不一定比朴素快

> 这是多关键词、短模式测试。KMP 仍要逐词扫描并构建 next，预处理和循环开销明显。
> KMP 的优势在长模式串和大量可复用前缀的场景，不是所有输入都最快。

#### Q17　AC 自动机解决了什么问题

> 把“每个关键词扫一遍文本”变成“文本扫一遍，同时在字典树上转移”。

#### Q18　失配指针指向什么

> 指向当前节点所代表前缀的最长真后缀，而且这个后缀必须是树中某个节点的前缀。

#### Q19　为什么 fail 必须按层建

> 计算子节点时要用父节点或更浅层节点的 fail，BFS 能保证依赖已经就绪。

#### Q20　只看当前节点为什么会漏命中

> 当前节点不是词，但它的 fail 链上可能有词尾。例如走到 `data` 末尾时，
> `ata` 也可能同时命中。

#### Q21　为什么 AC 匹配是 O(n+z)

> 文本只扫描一遍是 O(n)；输出链枚举命中是 O(z)，与关键词总数 N 无关。

#### Q22　没有输出链会怎样

> 命中检查要沿完整 fail 链爬，最坏会退化成 O(n·m)。

### 四、可视化与工程实现

#### Q23　为什么用网页而不是控制台动画

> 页面能同时显示树、文本、匹配面板和命中清单，还能缩放、回放和控制速度。
> 网页是 C++ 生成的自包含静态文件，算法仍在 C++ 里。

#### Q24　一个汉字为什么不会变成三个节点

> 程序先把 UTF-8 字节解码成字符编号，再建树和匹配；位置也按字符计数。

#### Q25　长关键词对齐问题怎么解决

> 主串、模式和 next 使用相同总列宽；窄屏时三行一起在局部横向滚动。
> 滚动位置按整格吸附，左侧标签不会遮住半个单元格，页面本身也不横滚。

#### Q26　字符颜色怎么分配

> 统计当前位置覆盖的关键词数量，再把字符格按数量等分：
> 一个关键词 100%，两个各 50%，三个各约 33.3%，四个各 25%。

#### Q27　四词重叠怎么保证颜色不混

> 按关键词长度和词库编号稳定排序，每个关键词占用同样面积的色块；
> 鼠标悬停还能列出当前位置的全部关键词。

#### Q28　超过 2 万字符为什么只记命中附近

> 每一步都要保存状态，长文本会产生大量过程对象，网页体积和浏览器内存承受不了。
